## 公開停止と保存データの回収

公開表示と非公開原本は別に管理します。スレッドを一覧から外すだけなら、管理画面のスレッド状態変更で「アーカイブ」を選びます。

| 操作・処理 | 公開・投稿への効果 | 保存データへの効果 |
| --- | --- | --- |
| 投稿停止 | 終了レスを保存して返信を止める | 本文と原本を残し、保持期限を変えない |
| アーカイブ | スレッド一覧から外して返信を止める。DATは保持期限まで読める | 本文と原本を残し、保持期限を変えない |
| スレッド全体の公開停止 | 公開閲覧と返信を止める | 公開用コピーを回収する。原本の保持期限は変えない |
| レス削除 | 対象レスを削除表示にする。レス番号は維持する | 公開用データを変更する。非公開原本は書き換えず、保持期限も短縮しない |
| 期限による回収 | 期限切れの本文を公開しない | 対象データを検証付きで回収する |
| 容量不足時の回収 | 対象スレッドを一覧から外し、閲覧・返信を止める | DAT・本文ファイルと対象投稿の原本を、通常期限前でも回収する |

アーカイブしたスレッドも、容量不足時の回収条件を満たせば早期回収される場合があります。公開停止の確定と物理回収の完了は同時ではありません。途中停止からの復旧を含む保存順序は[内部設計](../architecture.md#削除と期限回収)を参照してください。

## レス削除（あぼーん）と原本

あぼーんは、対象レスの公開用の名前・本文などを削除表示へ置き換える操作です。非公開の受理原本を書き換えたり、原本の保持期限を短くしたりする操作ではありません。

| 確認したいこと | 動作 |
| --- | --- |
| 公開本文 | 指定レスを削除表示に置き換える。画面から元の公開表示へ戻す機能はない |
| レス番号 | 維持する。削除後も後続レスの番号を詰めない |
| 非公開原本 | 元の受理記録を保持する。照会には担当板・追加権限・再認証が必要 |
| 原本の保持期限 | 通常の期限を維持する。永久保存ではない |
| 専用ブラウザーに保存済みの本文 | サーバー側の削除だけでは端末のコピーは消せない。再取得が必要 |

原本が必要な場合は、保持期限内に「提出用ログ」で案件保全します。[通常の保持期限](#通常の保持期限)と[容量不足時の早期回収](#容量不足時の自動回収)は、公開レスの削除とは別の処理です。削除の画面操作は[レスとスレッドの管理](../admin-guide.md#レスとスレッドを管理する)を参照してください。

## 通常の保持期限

| 記録 | 通常の保持期限 |
| --- | --- |
| 公開用DAT・本文 | スレッド作成から日本時間の6暦月 |
| 受理済み投稿の非公開原本 | 各投稿の確定から日本時間の6暦月 |
| 投稿試行・閲覧などの接続と処理結果 | 通常7日 |
| 未受理本文の一時保存 | 準備から24時間 |
| 案件の保全コピー | 明示した保全期限 |

6暦月は180日固定ではありません。日本時間で6か月後の同時刻を使い、その月に同じ日がなければ月末へ丸めます。例えば2026年8月31日12:00に確定した原本の期限は、2027年2月28日12:00です。

再送・閲覧では期限を延ばしません。通常の管理操作による公開削除・アーカイブも、原本の保持期限を短縮しません。容量不足時には、次の条件で別の回収記録を残して早期回収します。

公開起動の `serve` は公開本文・満了原本の自動回収と容量不足時の回収を有効にします。検証起動の `validation-serve` は容量不足時の回収を自動では有効にしません。必要な保存形式と更新時の注意は[現在の保存形式](../operations.md#現在の保存形式)を参照してください。

### 接続記録とバックアップ

非必須HTTP記録は通常7日で回収し、日別64MiB・全日合計128MiBの上限も設けます。上限に達した場合は新しい非必須記録を省略して欠測を記録します。受理投稿の必須原本とは別の制限です。容量の数え方は[圧縮範囲](../architecture.md#ログ関連の圧縮範囲)を参照してください。

Dockerの標準出力ログは、同梱Composeでは5MiBを2世代に回転します。通常バックアップは本文の元の期限に従い、署名計画とCLIで回収します。手動で退避したアーカイブは自動回収に含めません。[バックアップの保管と回収](../operations.md#保管と回収)も確認してください。

## 容量不足時の自動回収

### 回収対象と順序

対象は、最終ユーザー投稿から7日以上経過したスレッドです。スレッドの作成日や最終閲覧日では判定しません。

1. 容量回収を始めたスレッドに原本が残っていれば、その処理を優先します。
2. 未満杯のスレッドを、最終投稿の古い順に回収します。
3. 満杯のスレッドを、最終投稿の古い順に回収します。

満杯はレス数またはDAT容量の上限で判定します。固定スレッド、システム報告スレッド、案件で保全されている原本を含むスレッドは除外します。通常の管理操作で公開用コピーを回収済みのスレッドは、この早期回収の対象に追加しません。

### 開始・終了の空き容量

保存先の実空き容量から、処理中の保存予約を差し引いて判定します。圧縮率やディスクの公称容量だけで、保存できる件数を固定しません。

| 基準 | 計算 |
| --- | --- |
| 投稿用の最低空き容量 | 全体容量の10%と1GiBの大きい方 |
| 自動回収の余裕 | 最低空き容量の10%と256MiBの大きい方 |
| 回収を開始 | 最低空き容量＋余裕＋8MiBを下回ったとき |
| 回収を終了 | 最低空き容量＋余裕の2倍＋8MiBまで回復したとき |
| 新規投稿を停止 | 最低空き容量＋8MiBを下回ったとき、または容量を確認できないとき |

全体容量200GiBなら、回収開始は空き約22GiB、回収終了は約24GiB、投稿停止は約20GiBです。いずれも投稿処理用の8MiBを別に加算します。販売時の200GBと200GiBは異なるため、実際の値は管理画面で確認してください。

投稿受付を停止した後は、最低空き容量＋256MiB＋8MiB以上を30秒続けて確認してから再開します。回収の終了基準と、投稿の再開基準は別です。

### 回収の進め方と限界

スレッド一覧とDATの公開を停止し、DAT・本文ファイル、対象投稿の非公開原本を順に物理回収します。通常の6暦月の期限は書き換えず、容量回収の署名付き記録を別に残します。再送索引・規制の消費履歴・管理監査は必要な引継ぎを保存し、回収途中の再起動でも公開本文を復活させません。

監視は約5秒ごとで、一回一スレッド・一日分の最大128原本まで処理します。投稿処理中の板では延期します。容量不明や保全確認の失敗では削除しません。別途保存した手動バックアップや案件コピーも削除しません。

回収対象がない場合は7日未満のスレッドなどへ対象を広げず、最低空き容量で新規投稿を止めます。大量の新規投稿や、同じディスクを使う他のデータが増え続ける場合は、運営側で容量の追加や不要な退避データの整理が必要です。[容量不足時の確認手順](../operations.md#保存容量を確認する)を参照してください。

## 状態の確認

管理画面の「保存の自動整理」で、空き容量・投稿受付・容量回収の状態と起動後の件数を確認できます。管理APIの `GET /api/v1/maintenance` では `posting_capacity.storage_pressure` に同じ状態を返します。管理パスを使用する場合はURLの先頭にそのパスを付けます。

| 回収状態 | 次に確認すること |
| --- | --- |
| 空き容量を監視中 | 通常の待機状態 |
| 容量回収中 | 空き容量と回収件数の推移 |
| 投稿処理中のため延期 | 次の監視周期で処理が進むか |
| 候補が保全中のため待機 | 保全対象以外の保存量や、ディスクの追加余地 |
| 回収できる古いスレッドなし | 7日未満のデータ、対象外データ、手動バックアップの使用量 |
| 容量を確認できないため待機・回収でエラー | 保存先の状態、権限、サーバーログ |

## 原本の照会と案件保全

非公開原本は、IP・ポート、観測時刻、要求・接続情報、秘密除去済み入力、設定版、保存結果を署名記録へ結合します。取得不能・欠測は理由を残し、現在の設定から過去の観測値を補いません。

案件保全は明示した別の保全期限で管理します。記録の照会・保全・署名ZIP出力は、現在の権限と保持期限を検査します。権限は[管理者の権限](../admin-permissions.md)を参照してください。

Cookie全文、Authorization、管理パスワード、トリップ・CAP秘密、CSRFなどは記録へ残しません。

管理操作の記録は、投稿原本とは別の要約です。誰が何を操作したかは分かりますが、投稿本文やIP、設定項目ごとの変更前後の値は保存しません。検索や表示の読み方は[管理操作の記録の使い方](../admin-guide.md#管理操作の記録を調べる)、認証の成否は[認証監視](../security-operations.md#認証監視)を参照してください。

表示用の操作種別を元ログから補える場合も、監査正本や移管証明は書き換えません。認証情報の値や自由記述の理由は転記しません。

## 提出用ファイル

### 作成と取得

管理画面の「提出用ログ」で板・スレッド・期間を指定して案件を作成し、「ZIPを作成してダウンロード」を実行します。必要な原本の保全とZIPの作成を続けて行います。詳しい操作は[提出用ログを取得する](../admin-guide.md#提出用ログを取得する)を参照してください。

ZIPは記録種別ごとに提出可能な全項目を含みます。管理画面では保全・作成・取得を一つの操作にまとめています。通常投稿と未受理・閲覧ログは入口を分けています。

投稿のZIPを作成する際は、保存済みの関連HTTPログも案件用コピーとして保全します。原本の7日の保持期限は延長しません。案件で保全済みのHTTP記録は、その固定した集合を使います。保存されていない値を現在の設定や別の日時から補完することはありません。

### ZIPに入るファイル

| ファイル | 内容 |
| --- | --- |
| `records.csv` | 投稿・接続記録。投稿者本人の1投稿につき1行。未受理・HTTP観測は1記録につき1行 |
| `readme.txt` | CSVの読み方、このCSVに含まれる全列の意味・型、記録の範囲 |
| `manifest.json` | 案件・対象範囲・生成日時・出力項目・CSVのデータ行数・原本参照・欠落記録・同梱ファイルのハッシュ |
| `manifest.sig` | manifestの元バイトのSHA-256に対するEd25519署名 |
| `public-keys.json` | 署名検証用の公開鍵。別途信頼済みの鍵と照合する |

管理画面の「架空サンプルをダウンロード（ZIP）」で形式を確認できます。サンプルは `records.csv` と `readme.txt` の2ファイルからなる未署名の見本で、実データや案件は作成しません。取得には管理画面の認証が必要です。

### 投稿と接続の列

| 区分 | 主な列 | 意味 |
| --- | --- | --- |
| 投稿先 | `board_key`、`thread_key`、`post_number` | 投稿時に使用された板キー、スレッド番号、レス番号。板キーはURL別名を含む |
| 本文 | `public_body` | 正規化・秘密除去後の投稿者本人の本文 |
| 公開表示 | `public_title`、`public_name`、`public_mail`、`public_date_text`、`public_id`、`public_slip`、`public_trip`、`public_cap` | 受理時に確定した件名・名前・メール・日時表示・識別表示 |
| 確定日時 | `committed_at_jst` | 投稿・記録の確定時刻 |
| 要求受付 | `time.received_at_jst` | 投稿要求を受け付けた時刻 |
| 応答終了 | `time.response_finished_at_jst` | 同じ要求と照合できたHTTP処理の終了時刻 |
| 接続元 | `client.resolved_ip`、`client.resolved_port` | 保存時に解決された利用者のIP・ポート |
| 逆引き | `client.reverse_dns.names`、`client.reverse_dns.confirmed_name`、`client.reverse_dns.status`、`client.reverse_dns.observed_at_jst` | PTR名の一覧、正引き一致を確認した名前、確認状態、DNS観測日時 |
| User-Agent | `connection.user_agent` | 受信した申告値。本人確認には使えない |
| Cookie由来ID | `cookie.id`、`cookie.status` | 投稿時の匿名Cookie検証結果と、検証済みCookie由来の照合用HMAC |
| 公開ホスト | `request.canonical_host` | 投稿時に保存されたホスト名 |
| 受理結果 | `result.attempt_result` | 投稿の受理判断 |
| HTTP応答 | `response_http_status`、`response_outcome`、`response_source_event_sha256` | 同じ投稿要求に対応するHTTP応答の状態コード、処理結果、原本参照 |
| 原本参照 | `source_event_sha256`、`proposal_event_sha256`、`decision_event_sha256` | 対応する元署名イベントのハッシュ |
| 記録の範囲 | `completeness` | `partial`・`partial_observation` は部分記録であることを示す |
| 欠測理由 | `missing_fields`、`connection_missing_reason` | 未観測・未記録の項目と理由 |

実際の列は記録の種類と保存状況によって決まります。同名・同値の項目は1か所にまとめるため、受付日時が `received_at_jst`、受理結果が `attempt_result` に出る場合もあります。出力された列の正確な名前と意味は同梱の `readme.txt` で確認できます。

本人の投稿と公開表示は受理時の記録です。終了案内などの自動投稿は含めません。後からレスをあぼーんしても、この記録の本文は変わりません。未受理ログと閲覧などのHTTP観測には投稿本文を含めず、スレッドへの所属も推測しません。

Cookie由来IDは同じ匿名Cookieによる投稿の照合に使う補助情報です。同一人物であることは保証せず、Cookieの削除・再発行で変わります。Cookie原文や再利用できる認証値は含めません。

### 日時と欠測の読み方

CSVはUTF-8（BOM付き）、カンマ区切りで、先頭行が列名です。日時の `_jst` 列はRFC3339の日本時間（`+09:00`）です。配列はセル内のJSONで、配列内の日時も日本時間です。manifestの `count` はCSVのデータ行数で、セル内の改行は件数に含めません。

| セルの表示 | 意味 |
| --- | --- |
| 空欄 | その記録に項目がない |
| `\N` | null。不明・未記録など |
| `\E` | 保存された空文字 |
| 先頭のアポストロフィ | 数式実行や長い数字文字列の桁落ちを防ぐ接頭辞。元値を読むときは先頭から1つだけ除く |

正確なID・時刻・ハッシュを扱うときは、表計算で列を文字列として読み込んでください。時刻の桁数は時計精度を保証しません。署名検証用manifestの数値時刻はUnix epochからのナノ秒です。

HTTP応答の列は、サイト・板・起動・接続・要求・受理操作が一致する別保存の記録から取得します。終了日時は `time.response_finished_at_jst` に出力し、UA・IP・ポート・受付日時は投稿側の列だけに出力します。再送・確認・閲覧など別要求のHTTP記録は投稿CSVへ含めず、manifestの原本参照も提出した投稿と応答に限定します。

対応記録がない投稿の応答終了時刻は `\N` で、全投稿が欠測なら列自体を省略します。欠測は応答が終了しなかった証明ではありません。この日時はサーバーのHTTP処理が戻った時刻で、相手先の受領や送信完了を証明しません。

### 逆引きの読み方

投稿時に観測したDNS結果を使い、提出時には再照会しません。キャッシュを使った場合も元の観測日時を残します。逆引き名は本人や所属を証明しません。

| DNS確認状態 | 意味 |
| --- | --- |
| `confirmed` | PTR名の正引きが接続元IPと一致 |
| `absent` | PTRなし・NXDOMAIN |
| `mismatch` | PTR名が不正、または正引きが接続元IPと不一致 |
| `unchecked` | DNSの一時障害などで確認未完了。有効なPTR名は一覧に保持 |

未観測なら `reverse_dns: null` と欠測理由 `not_observed` を残します。内部IPなどの照会対象外、取得待ちの上限、DNS処理の混雑では名前を推測せず、DNSだけを理由に投稿を拒否しません。原本が作られなかった要求にはDNS結果も保存されません。

### 原本と署名の扱い

CSVは提出先が読むための記録です。要求・接続・起動などの内部ID、受信ヘッダの元バイト、文字変換・TLS・設定の詳細、認証秘密、保存処理の内部ハッシュは含めません。保存原本には照合・障害復旧・二重投稿防止・規制判定・監査に必要な情報も保持します。

原本の保存形式はサイトschema 5、`form-post-v8`、`http-observation-v4`です。CSVの表示形式とは別に管理します。原本の観測時刻や経過時間はそのまま保持し、時計の逆行でも書き換えません。時計の同期元・補正値は観測していません。

ZIPは出力したファイルのハッシュをmanifestにまとめ、その元バイトのSHA-256へ署名します。原本参照ハッシュは元記録との対応付け用であり、CSV自体が原本の署名を持つわけではありません。ZIPは暗号化されません。取得済みのファイルは提出先で適切に管理してください。
