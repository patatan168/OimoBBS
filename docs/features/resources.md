# CPU・メモリ・帯域の管理

CPU・メモリに合わせて、公開本文の保持量や同時処理数を自動調整する仕組みです。設定する場所と入力範囲は[設定一覧](../configuration.md#管理画面の運用設定)、負荷を掛けて確認する方法は[性能の検証手順](../testing/performance.md#cpuメモリの自動調整と圧迫時の回復)を参照してください。

## 管理者が設定するもの・自動で決まるもの

| 対象 | 決め方 | 確認・変更する場所 |
| --- | --- | --- |
| 送信予算 | 管理者が設定。実回線の速度そのものは増えない | 管理画面の運用設定 |
| 本文・圧縮結果の保持量 | CPU・メモリと観測した余裕から自動計算 | 運用設定で現在値を確認 |
| HTML生成・圧縮の同時処理数 | CPU・メモリから自動計算 | 運用設定で現在値を確認 |
| コンテナのCPU・メモリ上限 | 必要な場合に運用者が指定 | Composeの環境変数。変更後はコンテナを再作成 |

以下は計算と受付制御の詳細です。記載した数値は実装上の予算で、実回線で達成できる速度を示す測定値ではありません。

## 自動調整されるもの

公開本文・圧縮結果の保持上限と、HTML生成・圧縮の同時処理数は常に全自動です。管理画面・API・起動JSONから手動値を指定することはできません。以前に保存された手動値も現在の計算には使いません。画面に表示する現在値は、表示時点のCPU・メモリと観測した余裕から決めます。空きが減ると縮小し、回復すると再び増やします。

| 対象 | 計算・動作 |
| --- | --- |
| GoのGC目標 | 物理メモリとcgroup祖先制限の小さい方の75%。明示した `GOMEMLIMIT` は維持 |
| CPU並列数 | Goの `GOMAXPROCS` の検出・追従を利用 |
| 本文・圧縮結果の保持上限 | メモリ予算の8分の1。キーと管理領域もbyte予算に含め、件数の固定1024件制限は設けない |
| HTML・gzip・Zstandardの生成数 | CPU並列数と「メモリ予算の8分の1 ÷ 生成器1つ8MiB」の小さい方。待機数も生成数に応じて制限 |
| 検索の並列数 | CPUとメモリから決定 |

### 処理ごとのメモリ予約

| 処理 | 予約する量 |
| --- | --- |
| 検索 | 1要求32MiBを送信完了まで予約 |
| 公開要求の読取り等 | 1MiB |
| POST入力 | 4MiB |
| 投稿候補 | `4MiB + 16 × (frame長 + capture長)`。サイズ不明の内部予約は16MiB |
| HTML・圧縮等の表現生成 | 8MiB |

共有台帳で予約を管理し、新しい要求で空き全量を使い切らないよう、開始済みの処理が進むための余裕も残します。新規の公開要求では8MiB、POST入力と投稿待機中の読取りでは16MiBを温存します。これらは作業量の見積もりで、プロセス全体の厳密なメモリ上限ではありません。

## 投稿中にメモリが足りなくなった場合

バッチ途中で次の投稿候補を予約できない場合は、準備済み分を確定して予約を解放し、残りの未保存操作をFIFOのまま続けます。確定済み操作は再実行せず、メモリに合わせて一回のバッチを縮めます。確定した分は後続の分割群を待たずに応答し、HTTP側の入力予約も解放できるようにします。準備済み候補がなく、新規作業の予約もできない場合だけ受付を抑えます。

## 圧迫の検知と受付の再開

監視は1秒ごとにGo管理領域、cgroupの現在使用量、ホストの `MemAvailable` を照合します。Go内で再利用できる空きページと、再利用できるファイルキャッシュを圧迫量から区別します。メモリ予算の十六分の一（最低16MiB）を余裕として残し、その手前で保持量と生成数を縮めます。

新しい生成に8MiBを確保できなくなると、キャッシュと待機生成器を解放して新規生成を止めます。予約できない公開要求は `503` と `Retry-After: 1` を返し、開始済みの処理は完了まで扱います。受付を止めたことで通常のGC開始に必要な割当も止まる場合は、予約中の処理がなく、直前GC以後のヒープ割当増分が余裕分以上あるときだけGCを一度実行して再観測します。増分なしに同じ回収を繰り返しません。空きが戻ると自動的に再開します。管理経路は公開要求の予約から分けて残します。

## 状態の確認とコンテナ上限

`/api/v1/maintenance` と管理画面の稼働状況に、実際の並列数、Go管理領域、観測した余裕、処理中の予約、予約できなかった回数（バッチ分割も含む）を表示します。GC目標・周期監視・見積もりによる抑制なので、起動時の復旧や管理操作、外部プロセスによる急激な圧迫まで含めてOOMを完全に防ぐ保証はありません。

ComposeのBBSはCPU・メモリを固定せず、ホスト資源へ追従します。必要なら `OIMO_CPUS` と `OIMO_MEMORY` でコンテナ上限を指定できます。例えば `OIMO_CPUS=4 OIMO_MEMORY=3g docker compose ... up` とすると、その範囲から自動計算します。公開入口とBBSはホストのCPUを共有します。入口と証明書処理にはそれぞれ256MiBの上限があります。


## APIと保存形式の互換性

管理APIの `settings` は `maintenance`、`egress_budget_bits_per_second`、`reports`、`report_interval_minutes` だけを受け付けます。`cache_bytes`・`cache_workers` を含む要求は未知項目として拒否します。HTMLフォームにも手動入力や隠し値を設けません。新しい運用設定の保存時は、削除依頼の送信間隔にも対応する最低reader100を宣言します。`report_interval_minutes` は1〜1440分で、省略または0の場合は現在の間隔を維持します。初期値は10分です。送信予算を増やしても実回線の速度は増えず、100Gbpsでの実測を示すものではありません。

コンテナ設定変更には再作成が必要です。旧起動JSONの `cache_bytes` は削除してください。新バイナリはこの項目を受け付けません。切替時は旧設定を退避し、停止中に一度だけ項目を取り除きます。署名付きの過去の運用記録は検証用に元の形で保持し、内容を書き換えません。
