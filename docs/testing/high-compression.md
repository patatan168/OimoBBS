# Zstandardの高圧縮化とgzipレベル9との比較

2026-10-24。比較元は`d8153ea`。配信Zstandardの符号化表を列ごとに選び、pack・snapshotの高圧縮候補を最大2workerで比較します。稼働サービスへの反映は行っていません。[全標本・資源・失敗試行](high-compression.json)を保存しました。

**3種類のDATでは変更後もgzipレベル9より小さく、圧縮は約4.2〜6.6倍速くなっています。実テンプレートの最終50レスも約2.3〜2.7倍速く、約9〜12%小さい結果でした。** 既存zstdもこの圧縮率をほぼ達成しており、今回の追加削減はDATで最大約0.7%です。圧縮CPUは増えています。

## 実装

- 配信zstdはliteral長・offset・一致長ごとにFSE精度5〜9を比較します。offsetは形式上限8です。header・最終状態・実際の全遷移bitを合計し、小さい設定を選びます。文字列探索とHuffman literal生成を繰り返しません。記号数が状態数を超える精度は比較から除きます。
- 32KiB以上・複数候補・2CPU以上の保存圧縮は、呼出元と補助worker一つで候補を比較します。保存用の共通mutexは維持し、同じ長さなら候補の入力順で選びます。WALと回線分類の単一候補は補助workerを使いません。
- 16KiB以上の保存Level 9は精度自動選択を使い、同じ文字列探索を行っていた2候補を一つにまとめます。3種類のprefix方針を比較します。Level 1/6と小さい保存入力の方針は維持します。このLevelは公式zstdの圧縮レベルとは別です。
- 配信の生成枠・8MiBの作業予約・キャッシュ上限・逼迫時の受付制御は維持します。HTTP圧縮内では補助workerを増やしません。圧縮byteが変わるため、強いETagの接尾辞を`-zstd-v8`へ更新しました。
- 展開器、保存CRC、署名原本、保存順序、保存形式は変更していません。新しい精度も既存の展開器が扱う範囲です。追加依存はありません。

## 単体比較の条件

AMD Ryzen 5 5500U、Go1.27.3、Linux amd64、GOMAXPROCS=2。単体測定にはcgroup CPU・メモリ制限を設けていません。既存サービスが動く共有ホストで、性能測定中にビルド・テスト・他の性能試験は重ねていません。

変更前→後、次に後→前の2組で、各条件250msを3回、合計6標本の中央値です。CPU時間はgetrusageによる全threadのuser+system合計です。圧縮器を再利用し、返却byteの確保・GCを含めます。gzipはGo標準のレベル9だけを実行します。製品gzipの複数候補比較とは別です。HTML生成・初回圧縮器生成・復号検証は圧縮計時の外です。

DATは同じ合成1000レスのShift_JIS byteです。HTMLは同じDATの最終50レスを製品のthreadRows・threadTemplateで生成したUTF-8です。バイト入力の一致した比較で、実HTTP・WANの時間ではありません。

配信圧縮の総CPUは入力によって約17〜86%増えています。キャッシュ非命中1回の値で、HTTP全体のCPU増加率ではありません。少しのbyte削減にも追加CPUを使う方針なので、既存版よりCPU効率がよくなったとは扱いません。

独立したbenchmarkプロセスの最大RSSは、2組の中央値で配信・gzip比較が約15.11→18.13MiB、保存比較が約15.93→18.55MiB、実HTML比較が約36.52→37.32MiBでした。fixtureとtest runtimeを含む値で、稼働BBSへ加算できる増分の保証ではありません。各操作の割当量と全RSS標本はJSONにあります。

## WAF有効の実HTTPS

隔離Docker、loopback TLS HTTP/1.1、2CPU。1000投稿を10件/秒で準備し、40読者、専ブラ80%・Web20%、予定投稿20件/秒を重ねました。通常4秒200閲覧/秒、ピーク12秒2000閲覧/秒、回復5秒200閲覧/秒です。全文とWebにzstd、DAT差分にidentityを指定しています。追加容量試験とクラッシュ復旧は含みません。

1GiBでは両版とも全予定投稿成功、HTTPエラー・OOM・本文破損・採番不一致は0。変更後の回復投稿の予定起点p95は専ブラ約28.9ms、Web約35.6msでした。非必須ログも全件保存し、欠測・停止後の残件は0です。

**512MiBの変更後はピーク閲覧2件が503で失敗しました。** 全投稿は保存され、欠落・重複・OOMはありませんが、この試行は検査不合格として残しています。メモリ受付抑制との関係が考えられますが、原因の特定まではしていません。512MiBで高負荷を安定運用できる結果にはしません。

この失敗の後に、未回収ヒープと作業予約に関するGC判定を修正しました。[512MiBでの原因特定と再試験](memory512-recovery.md)を参照してください。上表は修正前の試行として保持しています。

各セル1試行です。1GiBでもピーク閲覧の予定は大量に未発行で、2000閲覧/秒の処理達成や長期SLOの証明ではありません。CPUの200ms標本最大値もJSONにあります。HTTPのDATには起動ごとの日時・IDがあるため、その圧縮サイズは前後の圧縮率比較には使いません。

## 検証と不採用候補

圧縮・展開・store・compat・webuiの通常試験とrace、bootstrap関連22親試験、全製品のvet・CGO無効ビルド、3種類各30秒のfuzz、依存検査、設計検査が成功しました。fuzzは圧縮2,464件、保存候補940件、復号217,380件を実行しました。全製品通常試験はbootstrapの関連外保存検査中に647秒でSIGINT中断し、bootstrap全件の完走とは扱っていません。他パッケージは成功しています。実行結果はJSONのvalidationへ記録しています。独立Go復号器と実HTTPのlibzstdで元byteとの一致を確認し、旧ETagからの200、新ETagの304、無圧縮Range 206も実TLS試験で検査しています。既存pack fixtureの再生成・復号検査も含みます。

二候補の履歴表、短いprefixの追加探索、一致内部の登録、hash-chain、Go製zstdライブラリ、精度比較用の小さい状態表も試しました。圧縮率改善が小さい、DATが大きくなる、またはCPU増加に見合わないため不採用です。初期の精度5試作で記号数が状態数を超える入力のpanicを検出し、候補除外と31/32/33/53記号などの回帰検査で修正しました。試作の失敗記録も生データに残しています。

主な再実行コマンドです。前後比較時は同じ入力・CPU条件を使い、他のビルドや負荷試験を重ねません。

```sh
GOMAXPROCS=2 mise exec -- go test ./internal/zstdencode -run '^$' -bench '^BenchmarkCompressionTarget$' -benchtime=250ms -count=3
GOMAXPROCS=2 mise exec -- go test ./internal/store -run '^$' -bench '^BenchmarkPackCompressionTarget$' -benchtime=250ms -count=3
GOMAXPROCS=2 mise exec -- go test ./internal/bootstrap -run '^$' -bench '^BenchmarkThreadCompressionTarget$' -benchtime=250ms -count=3
GOMAXPROCS=2 mise exec -- go test ./internal/zstddecode -run '^$' -bench '^BenchmarkDecode$' -benchtime=250ms -count=3
```

比較元のソース、overlay、全benchmark標本、CPU/RSS、隔離HTTPの要求別記録は非公開の`var/measurements/high-compression-20261024/`に保持し、SHA-256をJSONへ記録しています。実NIC・WAN・実ブラウザー・実専ブラ・長期運用・稼働環境での負荷は未検証です。
