# HTTP/3の起動選択と通信量比較

2026-11-03。HTTP/3の本文サイズ削減は **0%** です。既存HTTP/2比で全用途に共通する削減・高速化は確認できませんでした。圧縮DATでは双方向通信量が中央値で0.7%減りましたが、304・非圧縮DAT・Range・毎回の再接続では増えました。ルーターのUDPが開いていない稼働環境は、HTTP/2を使う既定値を維持します。稼働反映は行っていません。

全試行・環境・ソースとログのSHA-256は[機械可読記録](http3-20261103.json)に残しています。

## 起動時の選択

- HTTP/2は既存のHTTPS待受で有効です。TLSのALPNにより、クライアントとHTTP/2・HTTP/1.1を選択します。HTTP/3もTCP待受と併存させます。
- `public.http3` は省略時 `false`。外部UDP到達性を確認して `true` とした起動で、TCPと同じ実portへUDP/QUIC待受を確保します。UDP使用中・使用不可の場合は理由を出し、TCPを継続します。
- OSでのUDP待受成功は、ルーター・Docker公開port・ファイアウォールの外部到達性を証明しません。設定例と有効化手順は[Dockerセットアップ](../../deploy/README.md#http3を使う場合)を参照してください。
- HTTP/3が稼働している間だけ、公開URLのportを使う `Alt-Svc: h3=":443"; ma=60` をTCP応答へ追加します。内部8443・公開443のような構成でも内部portを案内しません。待受停止後は案内を止めます。
- 認証edge構成の保存側はmTLS/TCPを維持します。`oimoedge --http3` で公開入口を有効化し、保存先への転送ではHTTP/2を試行します。
- 直結HTTP/3の起動時に最低reader107を同期保存し、旧版がUDP・HTTP/3の必須観測記録を誤って読み込まないようにします。HTTP/3未起動のサイトはこの更新を受けません。

## 接続・投稿・保存の境界

Go1.27.3の標準 `net/http` には、HTTP/3待受を有効化する公開APIがありません。[標準のprotocol設定](https://pkg.go.dev/net/http#Protocols)はHTTP/1・HTTP/2を扱い、[crypto/tlsのQUIC API](https://pkg.go.dev/crypto/tls#QUICConn)はQUIC向けのTLS処理を提供します。今回のQUIC・HTTP/3通信には `quic-go v0.65.0` と `qpack v0.6.0` を固定し、依存一覧と配布ライセンスへ追加しました。QUICのTLS設定は既存の証明書再読込・検証を共有します。

UDP接続はIPv4単位・IPv6 /64単位で接続枠と新規接続頻度を制限します。QUIC Retryで接続元を検証した後、TLS処理前に接続枠を予約します。失敗したTLS接続もcontext取消で枠を解放します。TCPとは独立した有限枠です。

HTTP/3の接続枠は全体256・回線別16、双方向streamは最大32、制御用の一方向streamは最大3、受信窓は接続256KiB・stream64KiBです。ヘッダー読取前に5秒、本文受信と応答にも既存相当の期限を設定します。期限付きstream受理と停止処理をアプリ側で管理し、HTTP/3の解析・QPACK・応答処理はライブラリを使います。接続の受理にはQUIC Retryによる追加の往復が必要です。0-RTTとDatagramは無効です。接続元が変わった場合は再接続を必要とし、初期endpointと異なる接続元を同じ観測として保存しません。

停止時はTCPとHTTP/3の新規受付を同時に止めます。要求handlerの完了直後にQUIC接続を閉じると、送信待ちの応答が切れるため、受理済み応答の送信とpeerの接続終了を共通の停止期限まで待ちます。停止中の新しいstreamは拒否します。HTTP/3の接続をクライアントが閉じない場合、直結CLIでは最大25秒、公開入口では最大30秒待って残存接続を中断します。

業務handler・WAF・要求枠・送信予算・圧縮・公開リースを共有します。必須投稿記録には実UDP endpoint、`transport=udp`、`HTTP/3.0`、TLS1.3を保存し、非必須HTTPログもHTTP/3を受け付けます。TCPの記録とUDPの記録を取り違える値は拒否します。未確定の圧縮HEAD長にライブラリが `Content-Length: 0` を補わないようにし、既存のHEAD契約を維持します。

## 測定条件

| 項目 | 条件 |
| --- | --- |
| CPU・メモリ | サーバーと発行側をそれぞれ2CPU・512MiBの別Dockerコンテナへ制限 |
| 通信 | 外部接続のない専用Docker bridge。公開port・稼働volumeは不使用 |
| 実装 | 製品のHTTP/3起動部品・DAT圧縮/条件取得/Range・要求枠・送信予算を使用する合成DATサーバー |
| TLS | 同じ短命Ed25519証明書、TLS1.3。QUICはRetryあり・0-RTTなし |
| データ | 固定64KiB DAT。圧縮後11,007bytes、Rangeは1,024bytes |
| 発行 | warmは8並行・各10,000要求。coldは1並行・20要求、要求ごとに新規接続 |
| 回数 | 各protocolを3周。各周で開始protocolを回し、同時に他の負荷試験を実行しない |
| 照合 | 全応答のprotocol・status・本文を照合し、失敗を含む全試行を保存 |
| 計測 | サーバープロセスCPU時間、発行側CPU時間、仮想NICの送受信byte差分、取得時間 |

本測定は計360,180要求、360,180成功、0失敗でした。先行した各1,000要求の短い試行36,180要求と、間接依存更新前の360,180要求もすべて成功し、機械可読記録へ残しています。停止時の応答完了を修正する前の360,180要求もすべて成功し、探索試行として残しています。最終測定は修正版の `golang.org/x/net v0.62.0` と、停止処理修正後のソースを使います。

## HTTP/2とHTTP/3の結果

表は3周の中央値です。通信量はサーバー仮想NICの送信＋受信byteを要求数で割った値です。個別の送受信量・CPU・p50/p95・処理量と全試行は機械可読記録を参照してください。

| 用途 | HTTP/2 通信量 bytes/要求 | HTTP/3 通信量 bytes/要求 | HTTP/2比 | サーバーCPU µs/要求 HTTP/2 → HTTP/3 | p95 ms HTTP/2 → HTTP/3 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 304 | 182.65 | 283.63 | +55.3% | 67.82 → 71.25 | 0.535 → 0.573 |
| 非圧縮64KiB | 67,399.32 | 67,822.85 | +0.6% | 319.83 → 372.94 | 2.365 → 2.801 |
| Zstandard圧縮64KiB | 11,717.33 | 11,633.08 | -0.7% | 132.23 → 128.42 | 1.111 → 1.105 |
| DAT差分1KiB | 1,301.58 | 1,401.67 | +7.7% | 81.95 → 82.44 | 0.621 → 0.672 |
| 毎回再接続1KiB | 6,327.70 | 11,027.00 | +74.3% | 816.50 → 1,067.05 | 1.241 → 1.903 |

圧縮DATではHTTP/3の受信量がHTTP/2比66.1%減る一方、送信量は1.8%増えました。合計の0.7%減やCPUの2.9%減を、一般的な改善保証には使いません。非圧縮64KiBのCPUは16.6%増え、再接続1KiBのCPUは30.7%増えました。p95の中央値は圧縮DATで0.6%短縮し、ほかの用途ではHTTP/2より遅くなりました。

同じ本文は全protocolで同じbyte数です。64KiBから11,007bytesへの83.2%削減は既存のZstandard圧縮によるもので、HTTP/3追加の効果ではありません。HTTP/1.1からHTTP/2への304の双方向通信量削減は約68.3%でしたが、公開側HTTP/2は既存機能です。今回有効化したedgeから保存先へのHTTP/2転送の、実稼働環境全体の削減量は測定していません。
