# 304のHTTP/2・HTTP/3差の内訳

2026-11-03。前回の[HTTP/3比較](http3-20261103.md)で304の双方向通信量が約55%増えた主因は、採用したQPACK実装が動的テーブルを使わないことです。設定変更だけで動的テーブルを有効にする項目はありません。実通信のヘッダーフレームを調べ、アプリ側の調整候補も比較しましたが、削減を確認できず不採用としました。稼働用コード・設定・稼働環境は変更していません。

本文を送らない304も、キャッシュ検証用の要求・応答ヘッダーと接続制御を送ります。前回の値はHTTP/2が約183bytes、HTTP/3が約284bytesという小さな通信量同士の比率です。同じ試験の非圧縮64KiB DAT全文取得はHTTP/3で約67,823bytesなので、304はそれでも約99.6%の通信を省きます。55%は本文量やCPU時間の増加率ではありません。

## ヘッダーフレームの実測

隔離サーバーへ100回の304と1回の準備要求を送り、HTTP/2は標準Transportのフレームログ、HTTP/3はclient側のqlogから符号化後の長さを取得しました。診断ログの出力は負荷になるため、性能比較とは分けています。101回の要求・応答をすべて復号して確認しました。

| 符号化後のヘッダー | HTTP/2の繰り返し取得 | HTTP/3の全101回 |
| --- | ---: | ---: |
| 要求 | 7bytes | 75bytes |
| 応答 | 8bytes | 59bytes |
| 合計 | 15bytes | 134bytes |

HTTP/2の初回要求は71bytes、初回応答は121bytesでした。その後はHPACKの動的テーブルで繰り返し値を短い参照にできます。HTTP/3の採用実装は静的テーブルと文字列だけを使い、`If-None-Match`、User-Agent、Date、ETagなどの値を要求ごとに送り直します。[QPACK実装の公式説明](https://quic-go.net/docs/http3/qpack/)、[対応状況](https://github.com/quic-go/qpack/issues/33)

ヘッダー本体の差は119bytesです。この試験でのフレーム先頭部分はHTTP/2が要求・応答で計18bytes、HTTP/3は計5bytesなので、HTTPフレームとしては33→139bytes、差は106bytesです。下の仮想NIC差約106bytes/要求とほぼ一致します。ここから、今回の差の大半をヘッダー圧縮の違いで説明できると判断しました。TCP側にはHTTP/3を案内するAlt-Svcも含みます。

## 100,000要求×5回の再測定

前回と同じ合成DAT・TLS1.3・2CPU/512MiBの別コンテナ・8並行・専用Docker bridgeです。各周でHTTP/2とHTTP/3の開始順序を交替しました。qlogとHTTP/2デバッグログは無効です。全応答のprotocol、304、空の本文を照合しました。

| 版・protocol | 双方向 bytes/要求 | サーバーCPU µs/要求 | p95 ms | 成功件数 / 発行件数 |
| --- | ---: | ---: | ---: | ---: |
| 現行 HTTP/2 | 182.60 | 62.00 | 0.485 | 500,000 / 500,000 |
| 現行 HTTP/3 | 288.62 | 71.03 | 0.600 | 500,000 / 500,000 |
| 不採用候補 HTTP/2 | 182.31 | 62.40 | 0.485 | 500,000 / 500,000 |
| 不採用候補 HTTP/3 | 287.62 | 71.22 | 0.614 | 500,000 / 500,000 |

表は5回の中央値です。両方の版を合わせて2,000,000要求、すべて成功、失敗0でした。現行HTTP/3の送受信packet数は要求あたり中央値で約0.965・0.927、HTTP/2は約0.725・1.029です。HTTP/3が大量の余分なpacketだけを送っていたわけではありません。

不採用候補は、stream受理時とhandler開始時に指定する応答期限のうち後者を除く変更です。HTTP/3のCPUは0.3%増、p95は2.3%増で、改善を確認できませんでした。通信量の0.3%減も、ヘッダー表現を変更していないため、packet化などの試行差として扱います。後者の期限設定にはヘッダー読取後の応答処理へ時間枠を与える役割もあり、削除すると期限の意味が変わります。測定後に候補と探索用試験を取り除き、現行実装へ戻しました。

## 今回の判断

- ETag、Date、Vary、キャッシュ方針、セキュリティヘッダーを削って通信量だけを小さくする変更はしていません。
- 現行ライブラリの設定だけで、この約100bytesの差を消すことはできません。根本的な短縮には、ライブラリ側のQPACK動的テーブル対応が必要です。
- 既定のHTTP/2を維持します。UDP未開放の稼働環境でHTTP/3を有効化していません。
- 採用した変更は、比較ツールの用途・protocol選択、仮想NICのpacket数計測、診断ログ保存とqlog完了待ち、およびこの検証記録です。

今回も仮想NICと合成DATの結果です。実際の掲示板のWAF・認可・非必須ログを含む全処理負荷、ブラウザー、WAN・packet loss・ルーター外部到達性は測っていません。ヘッダー量はこの試験の固定したUser-Agent・ETagによる値です。
