# HTTP/3の追加性能・鍵管理強化

2026-11-04。[前回の追加強化](http3-hardening-20261104.md)を含む作業ツリーを変更前として、
比較用バイナリを保存してから改善した。HEADは`55bfb9b`だが、前回の未コミット変更も含むため、
再現時はコミット番号だけでなく[全試行・環境・source hash](http3-more-20261104.json)を使用する。
本番反映・設定変更は含まない。

## 実装

- UDPの宛先制御情報が完全一致した場合、前回解析した不変の宛先情報を再利用する。一件・最大256byteだけを保持し、kernelの作業bufferは複製する。宛先が変われば再解析し、wildcard待受で宛先情報がなければ従来どおり破棄する。
- 受信再構成で、末尾へ届いた非重複の断片は既存区間の走査を省く。消費済みslotの本文参照を消し、空になった領域を再利用する。食い違う再送・最終長・64KiB/256区間の制限は維持する。
- packetごとのACK/ACK_ECN処理を合計8frameまでに制限する。9個目は資源制限としてQUICの`INTERNAL_ERROR`で接続を終了する。Initial・Handshake・Applicationの全番号空間で同じ枠を適用する。
- peerが現在の受信phaseへのACK送信より前に再び鍵を更新した場合、認証成功後に`KEY_UPDATE_ERROR`で拒否する。自分が先に鍵を更新した際のpeerからの応答は許可する。
- 旧受信鍵の保持期限に再送backoffを掛けず、通常のPTOの3倍を使う。期限後は復号に使わず、接続loopとtimerで参照を破棄する。

WAF、Retry前の頻度制限、接続・要求枠、0-RTT無効化、flow control、輻輳制御、
POST・Cookie・Range・圧縮・期限・取消・16KiB field上限を維持する。
製品の`go.mod`・`go.sum`に変更はない。

## 性能比較

同じ変更後clientで両バイナリへ接続し、順序を交互にして4周比較した。
性能測定中にはbuild・race・fuzz・profileを並行実行していない。
全本文のhash・status・HTTP/3を検査し、自動再試行は行わない。

## 単体のコストと修正前の再現

診断用profileではUDP送信のOS呼出しがCPU標本の約28.5%を占め、
宛先解析は標本上の割当個数の約8.3%を含んでいた。profileは性能比較の集計に含めない。

| 単体の対象 | 変更前 | 変更後 |
| --- | --- | --- |
| 同じUDP宛先の解析 | 288byte・7割当/回 | 0byte・0割当/回 |
| 1KiBを16断片で順次受信 | 16,904byte・33割当 | 16,424byte・18割当 |
| 64個のACKを含む入力の解析 | 約2.50µsで全件処理 | 約0.35µsで上限超過を拒否。エラーに32byte・1割当 |

これは対象関数だけの測定であり、UDP受信全体が無割当になるという結果ではない。
単一断片では割当個数は3個のままで、大きい本文ほど再構成領域の再利用が効く。

修正前に、未ACKの連続鍵更新、PTO backoffで延長された旧鍵期限、期限後の旧鍵参照、
9個のACK受入れ、消費済み断片の参照保持を回帰試験で再現した。
修正後は同じ入力で拒否・解放を確認した。実AEADで認証したpacketの受信も通している。

## 根拠と確認範囲

鍵更新は[RFC 9001の更新条件](https://www.rfc-editor.org/rfc/rfc9001.html#section-6.1)と
[旧鍵の保持](https://www.rfc-editor.org/rfc/rfc9001.html#section-6.5)、資源制限は
[RFC 9000のDoSに関する考慮事項](https://www.rfc-editor.org/rfc/rfc9000.html#section-21.1)を確認した。
鍵の更新条件は暗号認証後に検査し、未認証のphase bitだけで接続を終了しない。

実WAN、実NIC、UDP flood・回線帯域の飽和、分散攻撃、本番の投稿・保存I/O負荷に対する性能・耐性は未検証。
この合成配信の速度差を本番やWANへ一般化しない。
