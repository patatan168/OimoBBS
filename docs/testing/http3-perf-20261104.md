# HTTP/3のUDP送信と受信領域の改善

2026-11-04。変更前`ee09ef5`と変更後を隔離Dockerで比較した。
稼働環境への反映・設定変更は行っていない。[全試行・source hash・環境](http3-perf-20261104.json)を保存する。

## 変更

- サイズの異なるGSO群と小さいdatagramを同じ`sendmmsg`へまとめる。sender専有の32message分の作業領域を再利用する。
- 本文packetに入らないACKは同じ送信処理内の端数へ同梱する。残ったACKは同じ処理の末尾で送り、追加timerで待たせない。
- 接続actorに1,500byteの復号領域を持たせ、packetごとの平文領域の確保を減らす。暗号文は変更せず、鍵更新時の再試行に使える。

部分送信後のGSO失敗では送信済みdatagramを除き、未送信分だけ通常送信へ戻す。
streamに残す本文は従来どおりコピーし、別packetの復号で上書きしない。
ACKの同梱は[RFC 9000のACK送信](https://www.rfc-editor.org/rfc/rfc9000.html#section-13.2.1)の範囲で行う。
WAF・未検証入力の頻度制限・flow control・輻輳制御・公開/権限検査付き応答のI/O境界・期限と取消は維持する。

## 比較条件

serverとclientは別コンテナで、それぞれ2CPU・512MiB、同時要求8。
Docker内部bridgeだけを使用し、外部公開portや稼働volumeは使わない。
両版へ同じ変更後のclientを使い、同じ合成DAT・証明書方式・圧縮・配信予算で4周比較した。
周ごとに変更前/変更後の順序を交代し、測定中はrace・profile・build等を並行実行しない。

warm用途は各版・各周30,000要求、新規接続は各版・各周20要求。
全要求でstatus・HTTP/3・全本文のSHA-256を検査し、圧縮byteも両版で一致する。
最終比較は960,160要求すべて成功、エラー0。要求の自動再試行は行わない。

## 結果

4周の中央値。通信量は仮想NICの送受信byte合計で、実WANの通信量ではない。
GSOがあるため、NIC packet数をUDP datagram数として扱わない。

非圧縮64KiBのCPUは約7.0%、zstdは約5.6%減った。
304の速度差はばらつき内と判断し、高速化とはしない。
新規接続は各版合計80件であり、長時間・大量接続時の優位を示す結果ではない。
HTTP/2との性能比較は今回実施していない。

通信量の削減は小幅で、全用途では減っていない。既存の圧縮やQPACKの方針は変更しない。
ACKの回帰試験では「満杯のpacket＋端数＋独立ACK」の3packetが2packetになることを決定的に検査する。
実際の削減幅はACK・応答・flow更新の到着順と既存の同梱量で変わる。

途中の3周×15,000要求の試行もJSONに残す。初回比較の304は中央値で約3.2%速かったが、
交互比較では再現が揃わなかったため、最終結果には交互比較だけを使う。
ACK同梱だけの段階では非圧縮64KiBが4,174→4,158要求/秒、zstdが12,751→12,643要求/秒と下がった試行も残す。

## 検証

変更前に失敗する回帰試験を作り、次を確認した。

- 混在サイズの7datagramをIPv4/IPv6で送受信し、本文・境界・順序を維持する。GSO有効時のOS呼出しは3回→1回。
- GSO無効時の通常送信、部分送信後のGSO失敗、途中の部分送信、空送信/通常送信エラーを確認する。
- ACKを端数へ同梱する場合と、同梱先がなく同じ送信処理の末尾で独立送信する場合を確認する。
- AES128/256-GCM・ChaCha20-Poly1305で復号領域の再利用、誤鍵からの再試行、暗号文・保存済み本文の保持を確認する。

関連製品packageのrace、外部QUIC clientによる相互接続raceが通った。
損失/重複・MTU縮退・小さい受信窓・鍵更新・並行応答の混線防止・期限/取消・shutdown・UDP停止後のHTTP/2継続、
WAF、実サイトの投稿/返信・板分離・DAT・条件付き/Range・再起動後の取得を含む。

関連packageのvet、全製品packageのCGO無効build、455packageの許可依存検査、文書検査も通過した。
全リポジトリの通常/race試験は今回の検証範囲に含めない。
この合成配信の性能は実サイトの認証・公開リース・板検索・保存I/Oを含まず、WAN・実機・本番負荷での差は未確認。
