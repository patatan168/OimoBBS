# 512MiBでのメモリ受付と回復

2026-10-24。[高圧縮化の試験](high-compression.md)で発生した閲覧503を、同じ2CPU・512MiB・WAF有効の条件で調べました。稼働サービスは変更していません。[全記録・失敗試行・ソースSHA-256](memory512-recovery.json)を保存しています。

## 原因と修正

診断付きの変更前試行では、ピーク後の回復区間に閲覧60件が503になりました。全420投稿は保存され、採番・本文prefix・OOMは正常でした。拒否時の同じ観測値が60件のログへ記録されています。

| 観測 | 値 |
| --- | ---: |
| Go soft limit | 384MiB |
| 受付の空き予算 | 約60.47MiB |
| Goの前回GC時の生存ヒープ | 約158.54MiB |
| 現在の割当済みヒープ | 約299.15MiB |
| GC後の割当増分 | 約140.61MiB |
| 既存の作業予約 | 20MiB |
| 安全余裕＋投稿の進行分＋既存予約＋次のGET | 61MiB |

受付計算に従うと60.47MiBでは次のGETを受け付けられません。一方、旧GC判定は「予約がゼロ」かつ「空きが56MiB未満」の場合だけでした。未回収の増分が大きくても回収を始めず、通常GC前に受付だけが止まっていました。

修正後は、安全余裕・最大の次作業・表現生成一枠・現在の予約を含めて早期GCの必要性を判定します。512MiBでは基準64MiBに予約量を加えて比較します。割当済みヒープが前回GC時より安全余裕分以上増えた場合だけ回収し、GC後に再観測します。

**予約を残したままGCを行い、生存中の処理やデータは保持します。** メモリ上限、384MiBのsoft limit、キャッシュ予算、要求の予約量、進行用の余裕、受付拒否条件は緩めていません。実メモリが足りなければ引き続き拒否します。圧縮器・保存圧縮方針・ETagのソースも前回から不変です。

## 同じ負荷での再試験

隔離Docker、loopback TLS HTTP/1.1、2CPU・512MiB、swapなし、WAF有効、80Mbps。1000投稿を10件/秒で準備し、40読者・専ブラ80%/Web20%・予定投稿20件/秒を重ねました。通常4秒200閲覧/秒、ピーク12秒2000閲覧/秒、回復5秒200閲覧/秒です。全文とWebにzstd、DAT差分にidentityを使います。

| 試行 | 投稿成功 | 発行済み閲覧エラー | メモリ予約拒否 | 全期間最大MiB | ピーク区間平均CPU コア分 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 変更前・診断再現 | 420/420 | 60 | 60 | 396.99 | 0.523 |
| 修正後・通常1 | 420/420 | 0 | 0 | 373.63 | 0.554 |
| 修正後・通常2 | 420/420 | 0 | 0 | 358.63 | 0.538 |
| 修正後・SIGKILLあり | 420/420 | 0 | 0 | 365.41 | 0.531 |

修正後の3試行で、HTTPエラー・OOM・欠落・重複・不正本文・prefix不一致は0。非必須ログは各最終bootの停止集計で欠測・保存失敗・残件0です。

3回のHTTP再試験では通常GCの範囲で動作し、追加GCの発火は0回でした。修正条件の発火と受付回復そのものは、次の実cgroup試験で直接確認しています。この3回の数値だけからGCによるCPU・メモリの改善幅は推定しません。

SIGKILL試行では、準備した1000投稿への応答後に強制停止し、同じvolumeから約3.36秒で1001行のDATとETagの一致を確認しました。WAF設定も維持しています。電源断・媒体故障の試験ではなく、SIGKILL時の未保存の非必須ログは保証しません。

2000閲覧/秒は予定値で、待機による未発行が多数あります。エラー0は発行済み要求についての結果です。各試行は短時間で、長期安定性や任意の負荷での無拒否を保証しません。

## 実メモリと保護の検証

- 拒否時の観測値を回帰試験へ追加。旧GC判定では失敗し、修正後は予約ゼロ・観測時の予約・拒否時の予約の各条件で回収を判断します。生存ヒープから増分がなければGCを繰り返しません。
- ネットワーク無効の別512MiBプロセスで、64MiBを予約し、生存データと未回収領域を実際に割り当てました。通常GCを一時停止して、回収前は503であることを確認し、refreshMemoryによるGC後は204へ回復しました。
- 実測の空き予算は約74.76→178.81MiBへ増え、GC回数は3→4。64MiBの予約と生存データは維持されました。再試行や予約の破棄で受付を通していません。
- 別の512MiB圧迫プロセスで、生存領域がメモリを占める場合のキャッシュ縮小・生成停止・投稿/閲覧拒否と、領域解放後の回復も成功しました。

関連通常試験、関連race、全製品のvet・CGO無効ビルドを通過しています。bootstrap全件は再実行していません。前回の圧縮・展開fuzzは[高圧縮化の記録](high-compression.md)を参照してください。

## 再実行

次のimageは、今回の修正を含むビルドを指定します。

```sh
mise exec -- python3 scripts/probe-thread-resources.py \
  --image oimobbs:memory512-fixed-20261024 --cpus 2 --memory 512m \
  --waf --prepare-post-rate 10 --peak-mix --peak-no-capacity \
  --peak-post-workers 5 --peak-full-coding zstd --peak-web-coding zstd \
  --optional-log-stats --collect-server-log --output var/memory512-check.json
```

強制再起動の試行だけ`--crash-recovery`を追加します。診断時は要求ごとの予約拒否とGC前の数値をログへ残します。今回追加した診断項目は、予約量・ヒープ・GC判定の数値だけです。

生データ・サーバーログ・実cgroup試験・旧判定の失敗記録は非公開の`var/measurements/memory512-20261024/`へ保持しています。共有ホストのI/Oと外部feedの時刻は固定していません。稼働環境・WAN・実ブラウザー・実専ブラでの負荷は未検証です。
