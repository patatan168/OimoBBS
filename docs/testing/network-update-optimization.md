# 回線分類更新の高速化

2026-10-24に、固定した実配信データで更新処理を比較した。対象はバックグラウンドの回線分類更新で、外部配信元からの通信時間と、ローカルの解析・検証・圧縮・耐久保存を分けて扱う。

## 変更内容

ASN・日本・VPNの両family・全世界の登録国を、共通の最大8取得workerで処理する。国別JSONの解析は利用可能なコア数に合わせて最大4並列とし、展開済みarchive全体の保持を避けた。展開32MiB、国別JSON1MiB、登録国30万prefix、通常分類4万prefixの検査は維持する。

保存圧縮は既存のZstandard実装へ変更した。設定は`zstd-config-v1`、大きい分類表は`zstd-json-v1`を使い、圧縮値は展開長とCRC32Cを持つ`ONZ1`の単一frameとする。辞書は使わない。展開長を割当前に検査し、破損・連結frame・後続データ・非正規base64を拒否する。外部配信元のtar.gzは引き続きgzipとして展開する。

回線分類の制御操作JSONだけを1MiBから2MiBへ広げた。分類値は管理receiptなどの外枠用に128KiBを残して1920KiBまでとする。拡張操作には分類・サイト状態と、小さい回線設定変更の再送記録だけを許可する。他のcollectionと通常のJSON入力は1MiBのままである。保存はreader 102を要求する。gzip保存値の読取り経路は削除し、旧codec名・gzip本文・Zstandard名に偽装したgzip本文を拒否する。

同じ圧縮前byteの再圧縮と、同じ国・日本/VPN表の索引構築をそれぞれ最大2版まで共有する。入力は複製し、変更した入力は完全検査する。上書き設定は別に検証・複製する。大きい分類表の復号では、行の出力先を先に確保して余分な割当てを減らし、複数コアでは独立した行検証を並列に行う。単一コアでは逐次復号し、未復号本文をまとめて保持しない。

## 測定条件

AMD Ryzen 5 5500U、Go1.27.3。同一の公開配信byteをファイルへ記録し、HTTP transportで再生した。外部通信の揺れや配信元の更新を比較へ混ぜていない。取得元のURL検査・本文上限・解析・分類衝突検査は製品経路を通る。耐久保存の測定は実際のRepositoryとcontrol WALを使う。

固定データは分類22937件、日本8777件、VPN IPv4 10942件、VPN IPv6 498件。復号した国表の正規byteと分類・日本/VPN配列をまとめた内容のSHA-256は、変更前後とも次と一致した。

```text
f303839dbe408c6e9d7f099b9d94fd51e5fb9026720f5c6dbed9203907800405
```

1条件につき3更新の平均を3回測り、その中央値を比較する。準備処理は取得byteの再生・解析・索引検査・保存表現生成まで。耐久保存には既存表の復号、候補検査、制御操作の生成・検証、WALのSync、分類表の公開を含む。cacheありと、圧縮・Access索引のcacheを空にした更新を分ける。国表の復号cacheはどちらも通常の更新経路に従うため、cold欄はprocess全体の初回起動を意味しない。

| CPU | 変更前・耐久保存まで | 最終版・cacheあり | 最終版・cacheを空にした更新 |
| --- | ---: | ---: | ---: |
| 1 | 1442.064ms | 679.706ms | 712.183ms |
| 2 | 1314.890ms | 495.464ms | 534.726ms |
| 4 | 1273.554ms | 453.731ms | 503.394ms |

cacheありでは変更前比で単一コアが約2.12倍、4コアが約2.81倍速い。最終版の1→4コアは約1.50倍、2→4コアは約1.09倍で、コア数に比例した高速化にはならない。4コアでの1更新あたりの割当て量は504.68MiBから258.03MiBへ約49％減った。これは累積割当て量であり、同時に使用するメモリ量ではない。

4コアでGoのヒープ目安`GOMEMLIMIT`を128MiBから512MiBへ変えた場合、最終版のcacheあり更新は461.315msから449.020ms、cacheを空にした更新は518.713msから497.307msだった。メモリの余裕による改善は小さく、物理RAM増設やcontainerのハード上限を比較した試験ではない。別processを使った1/2/4コア表とはGC条件が異なる。

CPU profileでは、旧版で大きかったgzip最高圧縮の探索が主因から外れ、厳密JSON復号・prefix整列・割当て/GC・保存操作の直列部分が残った。外部通信、更新中の実HTTP投稿のp95、稼働中の最大更新時間はこの表から推定しない。

[全試行・中間候補・条件](network-update-optimization.json)に、生の数値と不採用の中間測定も含める。

## 圧縮の比較

国表の正規byteを1回ずつ符号化した診断では、gzip最高圧縮が424214bytes・約310ms、Zstandardが531517bytes・約16msだった。圧縮単体は約19倍速い一方、国表の保存サイズは約25％増える。分類とAccess表を合わせたJSONも831562bytesから1010966bytesへ増えた。設定と制御操作の外枠はこの数値に含めない。容量拡張により、最高圧縮のCPU負担を避ける余裕を確保した。

この診断の単発時間は、更新全体の倍率や実際の配信元からの取得時間を示すものではない。

## 検証範囲

国の重複による不明、日本優先、最長prefix一致、IPv4/IPv6、VPN、手動上書きの分離を検証する。取得の一部失敗・取消では候補を公開せず、前回成功表を保持する。古い表の失敗記録を新codecで再保存する場合も、reader境界を同じ制御操作に含める。

1MiBを超える分類値のWAL・snapshot往復、通常collectionでの拡張拒否、約1.42MBの国表付き状態に対する実HTTPでの管理設定変更・同一要求の再送・再起動を検証する。Zstandardは製品decoderと、Go標準ライブラリの独立decoderの復号結果を照合する。

製品Go試験の全範囲を実行し、reader番号の期待値が旧値だった2件を更新後、bootstrap全体を再実行して640.085秒で通過した。他の製品package、Go vet、designcheckも通過した。回線更新と固定feedによる管理変更・復旧のrace検査は165.672秒、store全体のrace検査は30.515秒で通過した。strictjsonとidentityの全race試験も通過した。

稼働データ412417536bytes・527項目の全退避を別volumeへ復元し、新版での起動、固定feedによる更新と全投稿を含む再読込、新版と復旧用imageでの起動を確認した。更新は4CPU/4GiBの隔離環境で558.673ms、保存値は1027942bytesだった。旧imageは新形式を拒否し、その試行でどの保存fileの内容も変えなかった。旧imageと旧退避の組み合わせも起動した。

隔離2CPU/4GiBでのサービス起動は新形式で25.896秒、旧imageと旧退避で32.062秒だった。各1回・別volumeの単発値で、cacheとI/Oの差も含むため、起動時間の差を回線最適化だけの効果として扱わない。

## 再実行

記録した公開データを使う場合は次を実行する。通常の試験は外部通信を行わない。

```sh
OIMO_NETWORK_FIXTURE="$PWD/var/network-update-perf/feeds" mise exec -- go test ./internal/bootstrap -run '^TestNetworkRecordFixture$' -v -count=1
OIMO_NETWORK_FIXTURE="$PWD/var/network-update-perf/feeds" mise exec -- go test ./internal/bootstrap -run '^$' -bench '^BenchmarkNetworkUpdate$' -benchtime=3x -count=3 -cpu=1,2,4
```

公開データを新規に記録する場合は保存先を作り、`OIMO_NETWORK_RECORD=1`を明示する。配信内容が変わるため、異なる時点の記録を同一入力の比較として扱わない。復元したvolumeへ更新する検証用の`OIMO_NETWORK_REHEARSAL_CONFIG`は、稼働volumeを指定して実行しない。

測定の生データ、profile、記録したfeed、検証ログは`var/network-update-perf/`へ保存した。

## 保存互換の削除と履歴の移行

最初にZstandardで保存する版を稼働反映し、公開11経路・HTML・設定・鍵・保護fileを照合した。その後、gzip保存互換を削除した版を用意した。外部配信元のtar.gz展開とHTTP配信のgzipは、分類の保存codecと別の用途である。

移行は停止した複製volumeだけで行う。過去の操作を現在の権限ルールで新規付与として再実行せず、当時の値・操作ID・seq・状態のrevision・監査要約を保持して保存表現だけを変える。保持されている全世代の元/変換後WALを順序・CAS・状態の意味で照合する。既に保持終了したprefixは、認証済みanchorの検査値を起点にする。各世代と監査receiptの元のhashを確認してから、新しい保存byteへの参照を更新する。

複製で分類値72件、ハッシュ参照174件、認証済みanchor3件を変換し、35fileを更新した。現在のサイト・板の設定行は完全一致し、対象外の全fileは内容とmodeが一致した。全投稿の署名検査と監査の連続性検査を含む通常のRepository再読込も通過した。変換後のデータでgzip非対応版と切戻し用のZstandard版のサービス起動を確認した。変換前のデータはgzip非対応版が拒否し、その試行で保存fileを変更しなかった。

二度目の変換は、更新file・分類値・hash参照・anchorがすべて0件となった。互換削除後のbootstrap全体試験は628.865秒、回線更新のrace検査は120.354秒で通過した。移行用のgzip読取りは一時的な隔離工具だけに置き、製品には残さない。

稼働環境にもgzip保存非対応版を反映した。sourceは`1674e255ae73976e8de5419064cffd347dedc139`、imageは`oimobbs:network-zstd-only-20261024`（`sha256:908fb28818376db22b8f2b53aadb8ace42734407d7fa7b98a6929fea48661772`）、data volumeは`oimobbs-network-zstd-only-20261024`である。

最終の全退避は414268928bytes・527項目。最新の全退避を別volumeへ復元して変換し、切替前にも現在のサイト・板の57行を完全一致で照合した。最終変換も分類72値・hash参照174件・anchor3件・35fileとなった。全投稿・監査を含む再読込後にBBSだけを切り替え、139.74秒でhealthyを確認した。変換と追加の全検査を含む一回限りの保守時間で、通常起動時間の測定値ではない。

切替後はhealthy・再起動0・OOMなしを継続確認し、公開11経路の本文・ETag・304/HEAD/Rangeと、HTMLのidentity/gzip一致・条件要求を確認した。現在の設定・認証情報57行、鍵・案件保持物・ZIPなどの保護73fileの内容・mode・所有者を保持した。edge・証明書containerとCPU/メモリ上限は変更していない。実Originの管理login GETは200/no-store/CSP、未認証の管理APIは401を確認した。稼働実アカウントのログイン・変更操作は行っていない。

移行用の一時source・実行物・imageは確認後に削除した。通常の起動経路と製品sourceにgzip保存互換は残さない。旧imageと対応する旧volume・全退避は復旧用に保持する。作業記録・一覧・SHA-256は`var/backups/deployments/network-zstd-only-20261024/`に保存した。
