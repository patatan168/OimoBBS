# 投稿の短い同時枠競合を待機で吸収する

2026-11-02。変更前は`636c1c0`です。[前回の攻撃混在試験](attack-mix-20261102.md)で20投稿/秒の正常投稿が2件失敗したため、同時枠の一時的な競合を改善しました。[全試行・失敗・条件・ソースhash](posting-admission-wait-20261102.json)を記録しています。稼働環境は変更していません。

## 原因の確認と変更

元の2件は当時のHTTP status・段階の記録が不足しており、原因を後から断定できません。同じ条件を変更前へ3回流すと各440/440件が成功し、I/O競合の追加だけでも失敗は再発しませんでした。そこで短い投稿枠競合を明示的に加えました。正常投稿のWebフォーム取得は200、その後の投稿は503で、応答本文がWAF頻度・同時処理制限のエラーであることを記録しました。投稿32枠を保持する回帰検査でも、次の4件が空きの発生を待たず即時503になることを確認しました。

公開の専ブラ・Web投稿に`AcquirePosting`を適用します。投稿の**全体同時枠だけ**が満杯で、通常枠・全体頻度・回線の頻度/同時処理に余裕がある場合、枠の解放通知を最大500ms待ちます。固定間隔の再試行は行いません。期限は最初の待機時に一度だけ作り、通知のたびに延長しません。

- 投稿の実行上限は既定32件、回線別8件のままです。毎秒・瞬間の上限も維持します。
- 待機は全体32件または投稿の全体同時枠数の小さい方までです。回線別制限ON時は同じIPv4・IPv6の/64ごとに1件までです。OFF時は全体の待機上限だけを適用します。
- 取得できた要求だけがトークンを消費し、本文処理・業務処理へ進みます。待機中は実行数へ加えず、待機用の回線キーは終了時に除去します。
- 待機上限・期限・取消で従来の503へ戻ります。頻度や回線枠の超過、通常要求の全体枠超過は待機対象にしません。
- 枠の解放と待機登録が同時に起きても、登録後に空きを再確認して通知の取り逃しを防ぎます。設定変更でも待機へ通知し、ON/OFFでトークンや実行数はリセットしません。

待機のない通常の枠解放は従来どおり受付mutexを取りません。待機がある投稿だけ通知のために排他を取ります。管理APIの投稿集計に`waiting`と累計`queued`を追加しました。保存方式・Sync・確定記録・成功応答の順序は変更していません。

## 実HTTPSの比較条件

2CPU・2GiB・送信予算80Mbps、Go1.27.3・CGOなし、同じruntime image、共有ホスト・共有SSDです。新規volumeと自動割当loopback TLSポートの直接BBS接続を使い、製品既定のWAFを有効にします。全体の通常枠は毎秒300・瞬間600・同時128、投稿枠は毎秒60・瞬間120・同時32、回線別投稿枠は毎秒10・瞬間30・同時8です。

各試行は通常5秒・攻撃12秒・回復5秒、正常20主体×各1投稿/秒で440件予定、専ブラ80%・Web20%、4スレッドです。攻撃は別IPの構文上正しい投稿100要求/秒×12秒（8接続）、さらに別IPの本文未送信16接続、別IPのヘッダー未完64接続を混ぜます。正常IP・Cookieは攻撃者と分離しています。

「通常到着」は前回と同じ等間隔の20投稿/秒です。「短い枠競合」は1秒分の正常20件を各秒+100msに同時投入し、攻撃開始時の大量投稿8接続だけ最初の本文送信を250ms遅らせます。平均の正常投稿数・攻撃予定件数・WAF上限は同じですが、前回と異なる追加条件であることを区別します。新旧それぞれ同じ入力条件で各3回、実行順を交互に比較しました。最終比較中はGo検査・build・別の負荷試験を重ねていません。

正常全件成功・未発行ゼロ、予定時刻から完了までのp95が1秒以内、ACKと全DATのprefix/本文/名前/重複/ACKなし保存の照合、OOMなしを要求します。大量投稿は95%以上の予定発行、受理数155件以下、429を要求します。低速本文は429または503による早期拒否を8件以上・全件1秒以内、16/64接続すべての発行・終了と誤ACKゼロを要求します。過負荷による503を429と混ぜずに保存し、HTTP200のエラー画面は成功に数えません。

## 再実行と回帰検査

通常到着の20投稿/秒は以下です。短い枠競合には`--attack-capacity-pulse`、追加I/O競合の診断には`--io-contention --io-contention-workers 2`を加えます。I/O競合は隔離された小さい一時ファイルへの同期だけで、デバイスや稼働環境の設定は変更しません。

```sh
mise exec -- python3 scripts/probe-thread-resources.py \
  --attack-mix --attack-normal-rate 20 --waf \
  --image <検査するローカルイメージ> --cpus 2 --memory 2g \
  --egress-bps 80000000 --output var/attack20.json
```

実行上限を増やさずに空き通知後に受け付けること、全体/回線/IPv6の待機上限、回線別制限OFF、頻度超過と通常枠超過の即時拒否、取消・500ms期限・設定変更、解放と待機登録の競合、待機のない解放の非同期性を検査しました。回帰検査では変更前の即時503を記録しています。

```sh
mise exec -- go test -race ./internal/waf ./internal/delivery ./internal/publicedge
mise exec -- go test -race ./internal/bootstrap \
  -run 'TestWAF|TestAdmission|TestMemoryRejectsUnreceivedBody' -timeout=5m
mise exec -- go test ./cmd/oimobbs ./cmd/oimoedge
mise exec -- go vet ./internal/waf ./internal/bootstrap ./cmd/oimobbs ./cmd/oimoedge
python3 -m unittest discover -s scripts -p 'test_probe*.py'
```

上記の検査、投稿待機・関連HTTPのrace反復10回、BBSと中継のbuild、文書検査を行いました。Pythonは20件です。任意実行の性能/外部環境検査は通常どおりスキップしています。bootstrap全体、全パッケージのrace、fuzz、依存脆弱性検査は今回の対象ではありません。定期セキュリティ検査へWAFパッケージのraceを追加しました。

初期候補は同時解放時の通知取り逃しを防ぐ再確認と、回線別制限OFFへの互換性を追加する前の版です。初期候補の全測定も別枠で保持し、最終版の成功件数へ合算していません。探索時のburst-I/O試行は正常440/440件でしたが、低速側の一部503を旧判定で数えず不合格となっています。生報告は書き換えていません。探索時のI/O競合・追加条件の変更前試行も残しています。測定器には処理段階と拒否本文を追加し、過負荷時の低速側503も早期拒否として判定します。既存の429専用集計も残しています。

生データ・変更前ソース・再実行スクリプト・全ログ・イメージ条件は`var/attack20-improve-20261102/`です。共有NAT、多数IPからの長時間攻撃、外部回線、実mTLS中継を含む混在負荷、稼働環境の投稿は未検証です。短い隔離試行の結果を、任意の攻撃中の全件受理保証には使いません。
