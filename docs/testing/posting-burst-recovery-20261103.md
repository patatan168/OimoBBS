# 投稿集中後の応答速度の回復

2026-11-03。変更前は`a7a743b`です。対象は「集中が収まった後、通常の応答速度へ戻るまで」であり、再起動時間ではありません。[全50比較試行・5診断試行・失敗・条件・原出力hash](posting-burst-recovery-20261103.json)を保存しています。稼働環境には反映していません。

集中直後の復帰開始は候補6試行すべてで最初の1秒区間から確認できました。ただし候補2試行にはその後の再悪化があり、**再悪化を含めた安定回復時間の短縮は未達です**。全件成功と応答速度の回復を分けて評価します。

追加の[120秒観測・再悪化の同期I/O診断](posting-recovery-regression-20261103.md)では、製品版の復帰に13秒かかる試行と、攻撃を外しても再悪化する試行を確認しました。ここでの最初の1秒区間という結果を、長い観測や本番の回復上限へ一般化しません。

## 保存開始の競合を減らす変更

非必須HTTPログには投稿を優先する背景I/O枠がありましたが、WAF・類似文・連投の検出ログはその外で時間別ファイルを同期保存していました。検出ログも同じ一つの背景I/O枠へ接続しました。

- 通常は受付済み投稿の完了を優先し、背景保存同士を直列にします。投稿は開始済みの背景保存の終了を待つ構造にしません。
- 管理画面の取得、正常終了、受付列128件以上で投稿優先の待ちを解除します。最長1秒の延期後も保存へ進み、検出履歴を無期限に延期しません。ほかの背景保存が使用中の枠は引き続き待ちます。
- 同じ時間帯の直前に保存したsnapshotが64KiB以上の場合だけ、枠の取得前に最大100ms・256件まで収集します。管理画面・終了の通知で打ち切り、収集中は背景I/O枠を占有しません。
- 検出件数・本文例・有界列・満杯時の件数集約・保存形式は維持します。一時ファイルSync→rename→ディレクトリSyncの成功後に表示・終了へ完了を返します。

`securitylog.Open`単独の既存利用は従来どおりです。Repositoryが`OpenWithAdmission`で投稿優先を接続します。背景保存の延期でメモリ内の検出イベントが長く残り得るため、強制終了時の未保存履歴まで保持する保証はありません。署名付き投稿原本、proposal→本文WAL→decision→公開/成功応答の順序、WAFの上限、投稿収集の16ms/2msは変更していません。

## 測定条件と回復判定

Go1.27.3・CGOなし、同じruntime、隔離Dockerの直接BBS実TLS HTTP/1.1、2CPU・2GiB・送信予算80Mbpsです。新規volumeと合成データを使い、WAFは製品既定で有効です。正常20主体×各1投稿/秒、専ブラ80%・Web20%、4スレッドへ等間隔に投稿します。通常5秒・攻撃12秒・回復30秒の計940件です。

攻撃は別IPの正規形式の投稿100要求/秒×12秒を8接続で発行し、別IPの本文未送信16接続、別IPの未完ヘッダー64接続を加えます。正常主体と攻撃主体は分離します。回線分類の自動更新は隔離サイトだけで停止し、無効・取得終了・読込0行を管理経路で確認してから開始しました。実行順は新旧交互です。測定中はbuild・Go検査・別の負荷試験を重ねていません。

`io2`は同じSSD上の独立した一時ファイルを2workerで同期します。各64KiB・予定合計400Sync/秒、攻撃区間だけです。実際の完了数は旧版1,401〜4,646回、候補4,639〜4,678回であり、**完了したI/O量まで同一ではありません**。`quiet`はこの追加I/Oを発生させない条件で、共有ホスト全体の無負荷を意味しません。

回復判定は集中終了を基準に1秒ごとに集計し、その秒の正常20件が全件成功・失敗なし・未発行なし、予定時刻から完了までのp95が100ms以下なら正常とします。発行待ちも含みます。100msはこの比較の固定目標であり、すべての環境の通常速度を保証する値ではありません。

「最初の復帰開始」は正常が3秒続いた区間の先頭です。「末尾まで安定」はその後に一度も再悪化せず、観測末尾まで3秒以上正常だった区間の先頭です。0秒は最初の1秒区間から正常だったという1秒粒度の遡及判定で、0msで応答したという意味ではなく、確認には少なくとも3秒かかります。観測終了は正確な回復時間やその下限ではありません。

## 再悪化の切り分け

製品の候補バイナリとは別に、隔離コピーへ同期時間と監視状態の診断だけを足しました。この2試行は性能の合否比較へ混ぜません。

- quiet診断は終了後21〜29秒区間で再悪化し、回復区間の投稿保存Sync群は最大177.020ms、個別のcontrol WAL Syncは96.660ms、本文共有WAL Syncは73.281msでした。
- io2診断は22〜29秒区間で再悪化し、同じ値は542.370ms、141.935ms、445.933msでした。
- 両方とも回復区間に本文WALのcheckpointはありません。検出ログsnapshotも最大311.855ms/224.915msと遅れていました。

定期監視の投稿遅延集計にはファイル書込みがなく、容量回収は空き容量が十分なら回収へ進みません。今回の診断では、同期保存そのものに長い待ちがあることを確認しました。SSD・OS・他プロセス等のうちどれが原因かはこの測定だけで確定していません。同期保存の省略や、未同期の成功応答は採用しません。

## 回帰検査と再実行

変更前へRepositoryの共通I/O枠の検査だけを移した試験は待機登録で失敗し、変更後では成功しました。変更後は検出ログの表示・終了による起床、301件の件数保持、期限後の保存、保存失敗時の枠解放、未保存件数の再利用防止、大きいsnapshotの対象条件、有限収集と通知順序を検査しています。

最終ソースで対象パッケージのrace、Repositoryの実管理HTTP・投稿優先・WAF・非必須ログの対象race、vet、Pythonの26検査、設計検査を実行しました。再buildしたバイナリは測定候補とSHA-256が一致しました。詳細な検査結果はJSONに記録しています。

```sh
python3 scripts/probe-thread-resources.py \
  --attack-mix --attack-normal-rate 20 --attack-recovery-seconds 30 \
  --attack-pause-network-refresh --waf \
  --image oimobbs:posting-recovery-final-20261102 \
  --cpus 2 --memory 2g --egress-bps 80000000 \
  --optional-log-stats --collect-server-log \
  --output var/recovery-result.json
```

I/O競合は`--io-contention --io-contention-workers 2`を追加します。同じ条件で旧版と交互に実行し、終了直後の3秒だけでなく観測末尾の再悪化も確認します。原出力・診断ログは`var/posting-recovery-20261102/`に保持しています。実WAN・実NIC・公開edge経由の混合負荷・長期負荷・電源断・本番の安定回復上限は未検証です。
