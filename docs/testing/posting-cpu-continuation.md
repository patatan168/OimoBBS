# 投稿の継続最適化と復旧時間

2026-10-23に、[前回の約1.32倍という結果](posting-cpu-parallelism.md)から、同じ改善版の2CPU→4CPUで1.45倍以上を目指して追加検証しました。試作・不採用・失敗を含む[全測定と生データのSHA-256](posting-cpu-continuation.json)を残します。本番へは反映していません。

**同じ採用版の2CPU→4CPUは、標準到着窓で約1.478倍、固定8,000件で約1.466倍でした。両方で1.45倍目標を達成しました。** 採用イメージは`oimobbs:scaling-145-prefix-20261023`です。遅い試行も含む各3回の中央値で比較しています。

| 比較 | 2CPUの全試行 | 4CPUの全試行 | 中央値の比較 |
| --- | --- | --- | --- |
| 10秒の到着窓内完了、投稿/秒 | 461.3 / 484.6 / 472.5 | 707.0 / 686.4 / 698.4 | 472.5 → 698.4、約1.478倍 |
| 固定8,000件の全完了、秒 | 20.348 / 18.661 / 18.864 | 12.816 / 12.870 / 21.882 | 18.864 → 12.870、約1.466倍 |

全12試行でHTTP失敗・ACK済み欠落・未応答保存・重複・不正本文・prefix破損・OOM killはなく、負荷後の追加100投稿も全件成功しました。固定件数は全試行8,000件成功・未発行ゼロです。到着窓には未発行があり、毎秒800件を安定処理できた結果ではありません。

受付操作数を増やす試作や最速同士の比較は達成根拠に使いません。途中版の約1.47倍という到着窓だけの結果も、固定件数で約1.43倍だったため、両条件の達成まで追加検証しました。

## 変更と安全境界

- 不変なHTTP観測の検査と、投稿の比較署名の構築を所有列の外へ移します。並行可能な標準検査器だけを対象とし、停止・板名・認可・受理枠の判定順は維持します。
- 検出履歴は同じ一括処理内で公開状態のidentityと最短履歴期限を毎要求照合します。変化がなければ全履歴の掃除を共有し、変化・明示的削除・一括処理終了で破棄します。未確定件数は予約・確定・取消時に更新し、連投件数はIPとtokenの和集合を数える索引で照合します。期限列を更新し、取消・削除・置換は一度だけ減算、窓幅・CAP免除変更とスレ立て採番時は再構築します。類似度の判定は毎要求行います。上限履歴の先頭削除は、最大8,192要素の領域を使い回し、毎投稿の全履歴コピーを避けます。消去済み署名のprefixも、古い未確定候補の確定・取消に合わせて補正します。掃除後は直近129確定件で保持境界を求め、新たに除外された範囲だけを消去します。削除で境界が戻った後の古い未確定投稿の確定も、全走査と一致させます。
- 元captureの完全検証結果は、同じflushの同じ完全byteだけで共有します。変更byte・失敗した群・次のflushへ持ち越しません。私的なproposal・decisionの構築だけは明示的なAPIで並行化し、一般のBuild callbackは従来通り順番に呼びます。
- CPU構築の16MiB予約はメモリだけにし、実保存候補へ移す際に現在の空き容量とディスク安全余白を検査します。候補の構築は収集中からCPU数以内で開始します。同じ保存群内ではworkerを再利用しますが、全構築終了後だけ入力順に適用し、保存境界でworkerを閉じます。候補の予約・受理枠は全構築終了後に一度だけ引き渡し、取消・失敗時に返します。
- 主体・要求HMACとframe対応の確認では同じ完全復号を共有し、保存時のHTTP観測も完全検証済みmetadataから取り出します。元byteからの検証、frame・観測・板・日時・IPの対応確認は維持します。
- 大きい必須記録の圧縮を既存の小さなWAL blockへ分けてCPUへ分担します。全符号化後に一度のWrite・Syncを行います。正規frame、署名、保存形式version 2、合計64frame・8MiB、準備記録→本文WAL→確定記録→公開の順序は維持します。
- 収集待ちは通常16ms、高い受付が続く間は2msへ切り替えます。250msに96操作を観測したら500msだけ短縮し、同じ群の再試行を重複計上しません。予算は次の群から適用します。16ms固定は標準条件で約1.33倍へ低下したため不採用です。
- HTML・圧縮の同時生成数と8MiB作業予約は維持し、異なる公開表現を待たせる有界枠にCPUと保持予算を反映します。受理後のWeb遷移先の503も別に数えます。
- 起動は各保存blockの独立新規行を並行検証し、更新・削除・同じキーは順序通り検証します。署名・元byte・source・seq・連鎖も全件照合します。`OpenJournalInspected`は同じ読込みの私的状態でreaderと回収時計を検査してから同期と回収を再開し、不完全末尾は拒否します。snapshotも境界検査成功後に必須長とSHAを再照合して同期します。

## 条件と判定

共有SATA SSD・新規隔離Docker volume・4GiB・80Mbps・実TLS HTTP/1.1です。標準条件は1板16スレッド・80主体・毎秒800投稿予定を10秒間です。予定入力は専ブラ80%・Web20%で、Webはフォーム・CSRF・303とgzip遷移先まで含めます。負荷後に100投稿を追加し、全DATのACK済み番号・重複・旧prefix・本文・OOMを照合します。

全試行を残し、同じ採用版のCPU別中央値で倍率を判定します。変更前2CPUとの比較、最速試行だけの比較、異なる主体数の混合は行いません。未発行がある到着窓の値を安定最大投稿数や毎秒800件達成と扱いません。

120主体は受付上限内で並行性を増やす別条件です。80主体と分けて記録します。同じ固定件数を比較する場合も、両CPUで主体数・入力比率・スレッド数を一致させます。CLIが拒否した条件は性能試行へ含めません。ビルド・テスト・CPUプロファイルと負荷測定は重ねていません。

共有ホストの他処理は変更しておらず、I/O変動が残ります。遅い試行も除外しません。媒体の専有、長期運転、大きな実履歴、WAN・実NIC、本番切替、電源断・媒体故障の証明ではありません。

## 試作と不採用

- 検出履歴・同じ元capture・HTTP観測を段階的に最適化しました。途中版の80主体の中央値は2CPU458.5、4CPU632.3投稿/秒で約1.38倍でした。受理後のWeb遷移失敗も記録しています。
- 収集待ち8msと0msを比較しました。全試行を記録し、最速の組合せで目標達成とは判定しません。
- 収集する受付操作を128件へ増やす試作は、保存上限64frame・8MiBを保ったものの、Web遷移先の503が増え、処理量の一貫した改善も示せませんでした。製品へは追加していません。
- CPU構築前のディスク枠予約の削減と、私的Buildの並行化も個別イメージで比較しています。
- WALを4frameごとに圧縮する試作は、固定8,000件の中央値で約1.44倍、到着窓では約1.40倍でした。採用版は8frameごとの分担を維持します。
- 受付操作を96件にした試作は固定8,000件で約1.53倍でしたが、標準到着窓では約1.43倍で、両CPUの絶対処理量も下がりました。標準条件の達成根拠にはせず、製品の64操作上限を維持します。
- 連投索引の最初の試作は通常返信で毎回索引を破棄しており、処理量が低下しました。全試行を記録し、スレッドキーが変わる時だけ再構築する修正版と分けています。
- プロファイルは診断専用です。関数のCPU内訳を調べる用途とし、採取中の値を通常の容量測定へ混ぜません。

## 継続負荷と復旧

同じ採用版で60秒の到着負荷を掛け、追加100投稿と全DATの照合後に正常再起動しました。全試行でHTTP失敗・整合性異常・OOM killはなく、再起動後の全DAT・ETagが一致しました。既定の待機上限は60秒です。

| 条件 | 成功 / 予定 | 未発行 | 予定起点p95 | 再起動から全件照合 |
| --- | --- | --- | --- | --- |
| 4CPU・2GiB・毎秒100投稿 | 6,000 / 6,000 | 0 | 約249.7ms | 約17.0秒 |
| 2CPU・4GiB・毎秒200投稿 | 11,936 / 12,000 | 64 | 約431.2ms | 約33.4秒 |
| 4CPU・4GiB・毎秒300投稿、32スレッド | 17,337 / 18,000 | 663 | 約476.5ms | 約39.3秒 |

前回は毎秒100投稿のp95が約336.2ms・再起動約28.4秒、毎秒200投稿は未発行145件・p95約592.0ms・再起動約55.1秒でした。今回の100投稿は250ms基準をわずかに満たしましたが、200／300投稿は未発行と遅延が残っています。100投稿も別の16ms固定試作ではp95約324.4／45.4msと変動しており、余裕のある安定能力や長期運用の保証にはしません。

前回の毎秒300投稿は既定60秒では起動待ちに失敗しました。180秒待機へ延ばした別試行は17,683件成功・p95約327.1ms・再起動約78.0秒です。今回は17,337件で、既定60秒以内の照合に成功しましたが、同じ保存件数の比較ではありません。p95は前回の速い試行より悪く、全条件で遅延が改善したとは扱いません。

収集待ちの単独比較では、元の2ms版の毎秒100投稿がp95約393.3／394.8ms、物理書込み回数16,056／18,287回でした。16ms固定試作はp95約324.4／45.4ms、書込み10,330／13,170回でした。全て6,000件成功・未発行ゼロです。高負荷では16ms固定のCPU倍率が約1.33倍へ落ちたため、採用版では受付集中時に2msへ戻します。採用版100投稿の物理書込みは10,950回でした。

4CPU・2GiB・WAF有効の混合負荷では420/420投稿、追加200/200投稿が成功しました。1,000件の成功応答後のSIGKILLからDAT・ETagの全照合まで約4.20秒で、WAF状態も維持しました。前回の約5.30秒から短縮し、5秒基準を満たしました。メモリ最大は約384.8MiB、OOM killはありません。

一方、混合試験の投稿p95は通常が専ブラ約29ms／Web約530ms、閲覧ピーク中が約972ms／約6,029ms、ピーク後が約301ms／約2,304msでした。前回より悪い段階もあります。ピーク閲覧は24,000予定のうち3,194件を発行し、別一時ファイルへの同期も予定2,400回に対して148回だけでした。予定負荷を全て供給した試験や、毎秒2,000閲覧を処理できた結果ではありません。交互の旧版対照試験も下記の測定記録に追加します。

## 回帰検査

bootstrapは878個のTestと1個のFuzz初期ケースを8分割し、全区分を通過しました。他42パッケージの通常検査と`go vet`も通過しています。保存・証跡・投稿・圧縮・capture・bootstrapの関連6パッケージは対象を絞ったrace検査を通過しました。全パッケージの全race実行ではありません。測定器のPythonテスト10件、設計fixture・Markdown/JSON・ローカルリンクの検査も通過しました。

追加検査では、収集中のCPU構築、全構築終了前の適用・予約返却禁止、保存群内のworker再利用と保存前の終了、取消・再構築のFIFO、同じ元byteだけの検証共有、主体HMACとframeの二段検証との同値性を確認しました。連投索引は18,000回の追加・取消・削除・期限・設定変更を全履歴走査と照合し、保持上限とIP/tokenの和集合、通常返信での索引維持、削除後の古い未確定署名の確定も検査しました。

起動境界で拒否した場合のfile不変、独立行と逐次適用の同値性、全workerの終了後だけの書込み、WALの元frameと既存readerでの復号、短い書込み・同期失敗時の停止も確認しています。正常再起動・SIGKILL試験は合成データでの実HTTP検証であり、電源断・媒体故障の証明ではありません。
