# 検出ログの重複復号と投稿CPU

2026-10-27。[専用JSON復号](posting-json-typed.md)を含む`f1830bd`と比較し、並列投稿とCPUを取り合っていたWAF検出・拒否ログの重複読込みを減らしました。2/4CPUの各版3回の中央値では、固定8,000投稿の完了速度が約4.8%/1.7%増え、CPU時間は約4.9%/1.9%減りました。2→4CPUの伸びは約1.42倍から1.38倍で、CPU増設時の伸び率は改善していません。

[全試行・検査・ソース識別・生データのSHA-256](posting-cpu-lanes.json)を保存しています。ソース、イメージ、測定器、全成否、CPUプロファイルは`var/posting-cpu-lanes-20261027/`にあります。稼働サービスは置き換えていません。

## 実装

変更前は、ログwriterが待機列から取り出す一群ごとに、同じ時間帯のJSON全体を読み直していました。4CPUの診断では、writerのCPU標本が約12.6%を占めました。既存の投稿候補構築・検証・署名・WAL符号化には、CPU数に応じた並列処理があります。今回はそれらと競合するCPU消費を削減しています。

writerだけが、直前に同期保存した1時間分の集計行を再利用します。毎回ファイルを開いて読み取り権限を確かめ、保存時のinode・権限・サイズ・更新時刻と照合します。保存用一時ファイルのidentityをrename前に取得するため、保存後に別ファイルへ置き換わっても、その内容を検査済みとして保持しません。

再利用は1時間分・512行・保存JSON8MiB以内です。上限超過は従来の完全読込みへ戻します。保存失敗時は更新済みmapを破棄し、未保存の件数を次へ持ち越しません。別の時間帯、ファイルの削除・置換・メタデータ変更、保持期限でも破棄します。標準JSONが置換する不正UTF-8を含む行も保持せず、従来の再読込みとの件数・値の一致を保ちます。画面へmapを共有せず、画面はflush後の保存済みファイルを読みます。

ログの一時ファイルWrite/Sync→rename→ディレクトリSync、待機列256件、本文例256組、7日の保持期限とoverflow集計を維持しています。投稿のproposal Sync→全本文WAL Sync→decision Sync→公開・成功応答、64候補・8MiBの保存枠、署名・入力検証、受付条件も変更していません。診断版にSync回数の計測は追加していないため、実際の群数・Sync回数が両版で同じだったとは主張しません。

## 比較条件

同じGo1.27.3・runtimeイメージ、WAF有効、4GiB、同一板16スレッド、80%専ブラ・20%Webの実TLS HTTP/1.1です。2/4CPUは両方120主体、1CPUだけ両版80主体で比較します。CPU quotaと同じ`GOMAXPROCS`を明示しています。ホストCPUの専有ではなく、他の既存サービスは動かしたままです。基準の通常版・診断版は、前回候補と全製品GoソースのSHA-256一致を確認して再利用しました。

fsyncによる媒体待ちを外してCPU側の上限を比べるため、隔離コンテナのデータだけ8GiB上限のtmpfsへ置いています。製品のSync呼出しは残し、実ディスクの比較も別に行います。tmpfsは永続運用の提案ではありません。ビルド・テスト・プロファイル解析を通常計時に重ねていません。初回は基準→候補、2回目は候補→基準、3回目は基準→候補です。

固定8,000件は発行が遅れた要求も最後まで実行する方式です。完了速度にはdrainを含み、1,600投稿/秒の継続到着やp95の目標達成には読み替えません。主負荷のCPU・I/Oは初期化、追加回復投稿100件、最後の非必須ログdrainを含みません。診断版の値は通常版の中央値へ混ぜません。

## 単体と診断

同じ256本文例を入れた時間帯ファイルに、1件追加してflushするベンチマークをtmpfs・`GOMAXPROCS=1`で各5回実行しました。中央値は約1.722→0.723ms/op、427,284→191,856B/op、1,039→319allocs/opでした。単体の時間は約58%、割当byteは約55%、割当回数は約69%減ですが、投稿全体の改善率とは別です。

4CPUの診断各1回では、CPU標本の総量が26.53→25.73秒、ログwriter配下が3.34→2.65秒（12.6%→10.3%）でした。所有ワーカー経由の標本は5.48→5.55秒で、今回その経路は削減されていません。所有ワーカーには呼出元として行う並列処理も含み、全てを直列の処理時間とは扱いません。カテゴリは子孫関数を含む重複した累積値です。

同じ診断の総割当byteは約7.296→7.305GBで削減はなく、割当回数は約2,694→2,631万回でした。単体の割当量削減をHTTP全体のメモリ削減には読み替えません。tmpfsのmemory peakにはデータページも含むため、Goヒープ単体の指標にしません。

## 検証と境界

24試行すべてで受理済み投稿の欠落・余分な保存・重複、DAT本文・名前の不一致、OOM killはありませんでした。各試行の負荷後100投稿は全件成功し、混合負荷4回の正常再起動後も16スレッドのDATとETagが一致しました。再起動のreadyは約13.2〜14.0秒です。正常終了時の非必須HTTPログのqueue状態もJSONへ記録しています。これはWAF検出ログ自体の件数と混同しません。

securitylogの全race、bootstrapのSecurityEvent/GlobalRule/WAF/AbuseGuard/RepositoryPostingCrash/PostingBatchを含む選択試験、全製品go vet、文書リンクとdesigncheckが成功しました。新しい検査は、再読込みモデルとの960件の一致、時間帯切替・本文例上限・ダミー・overflow・不正UTF-8、ファイル置換・削除・破損、読み取り権限と保存失敗、保持上限・期限を含みます。既存の飽和待機列の非ブロック性・件数試験も通過しています。追加した読み取り権限試験を含む最終raceではskipはありません。

実HTTPコンテナでのSIGKILL・電源断・媒体故障、長期・本番負荷、WAN・実NIC、全bootstrap・全パッケージraceは追加未確認です。稼働サービス・ホストのCPUや保存設定は変更していません。
