# 投稿の追加CPU並行化と1.5倍目標の検証

2026-10-23に、同じ改善版の4CPUを2CPUの約1.5倍へ近づけるため、[前回の資源増設検証](posting-resource-scaling.md)から追加で最適化しました。採用版は`oimobbs:scaling-150-reviewed-20261023`です。試作・不採用・診断・失敗も[測定記録と生データのSHA-256](posting-cpu-parallelism.json)へ残しました。本番は未反映です。

**標準条件の中央値は2CPU約411.5投稿/秒、4CPU約544.6投稿/秒で約1.32倍です。1.5倍目標は未達です。** 変更前4CPUの同日比較約398.6／409.5投稿/秒から処理量は改善しましたが、毎秒800投稿を処理できた結果や安定最大値ではありません。

## 採用した変更

- 認可・受理枠・順位を所有列で予約し、独立スレッドのframe・capture構築をCPU数以内へ分担します。同じスレッドの後続は先行候補を待ち、全構築終了後にFIFOで反映します。一件16MiBの構築予約を保持し、完了後は通常候補の予約へ引き渡します。
- `BuildPrepared`で一度計算した次状態と復号成分を一呼出し専用の`PreparedPosting`へ保持し、所有列での再復号・再適用を減らします。元byteと保存log、元の連番・最終frame hashを照合します。保存後に同じ状態が別objectへ再生される場合も許し、同じrevisionの別履歴・改変byte・別所有者は拒否します。
- 必須記録のsource検証・hash・Base64化と、保存層での各新規行の署名・元byte・JSON検証もCPU数以内へ分担します。`AppendIndependentBatch`はkind8/10、一frame一新規行、ExpectedRevision=0、未存在の異なるキー、削除なしに限定します。全検証を待ち、連番・CAS・状態更新を所有列で確認してから同期します。
- 板設定はrevisionと元byteが同じ間だけ再利用し、更新・破損・欠落を再検証します。検出履歴は一走査内で公開状態をスレッドごとに確認し、変化のない履歴の複写と署名領域の再消去を減らします。新しい候補の番号更新・確定検索は末尾から探します。

最大64件・8MiB、メモリ予約、署名連鎖、準備記録→本文WAL→確定記録→公開の順序は維持します。保存形式・reader下限・認可・再送の契約は変更しません。通常更新・復旧では従来の完全検証を続け、検証結果を別の呼出しへ保持しません。

## 同じ到着窓での2CPU・4CPU比較

共有SATA SSD、新規隔離Docker volume、4GiB、80Mbps、1板・16スレッド、80主体、毎秒800投稿予定を10秒間です。専ブラ80%・Web20%を予定し、Webはフォーム・CSRF・303・gzip遷移先まで測ります。ビルド・検査・プロファイル採取と重ねません。共有ホストの他処理・I/O変動は残ります。

採用版の順序は2CPU-a、4CPU-a、4CPU-b、2CPU-b、2CPU-c、4CPU-cです。同じ改善版の中央値同士で1.5倍を判定し、変更前2CPUとの比較や最速試行で置き換えません。

| 条件 | 時間内完了/秒：各試行 | 中央値 | HTTP失敗 |
| --- | --- | --- | --- |
| 変更前2CPU | 338.7 / 191.3 | 265.0 | 0 / 0 |
| 変更前4CPU | 398.6 / 409.5 | 404.05 | 0 / 0 |
| 採用版2CPU | 394.7 / 416.1 / 411.5 | 411.5 | 0 / 0 / 0 |
| 採用版4CPU | 546.0 / 544.6 / 292.3 | 544.6 | 0 / 0 / 0 |

変更前2CPUと採用版4CPUには大きな遅い試行があり、単純な改善率だけで原因を断定しません。採用版4CPUのI/O待ち集計は速い2試行で約59.5／57.6ms、遅い試行で約419.0ms、平均CPUは約2.69／2.68／1.43コアでした。この差だけから全変動を説明したり、ディスクだけが原因と結論したりはしません。

採用版6試行は全てHTTP失敗なし、ACK済み欠落・未応答保存・重複・不正本文・prefix破損なし、負荷後の追加100投稿も全件成功、OOM killなしでした。ただし各8,000予定のうち2,433〜4,989件が未発行で、全試行`stable_at_tested_rate=false`です。短時間の過負荷処理量を運用SLOへ読み替えません。

追加で4CPU同士を「変更前-a→採用版-a→採用版-b→変更前-b」の順でも再測定しました。変更前は387.3／373.6、採用版は546.3／537.7投稿/秒で、中央値は約380.5→542.0投稿/秒（約42%増）でした。全4試行でHTTP失敗・整合性異常はありません。この比較は今回のコード変更の効果を調べるもので、同じ改善版の2CPU→4CPUが1.5倍になった根拠には使いません。

## 試作と診断を採用結果から分ける

候補構築だけの並行化、履歴・設定走査の削減、検算済み候補の再利用、保存層の独立検証を段階的に比較しました。途中イメージのtagに`final`を含むものもありますが、採用版のtagは`reviewed`です。

- 保存層まで並行化した途中版の4回ずつの中央値は2CPU約403.3、4CPU約522.1投稿/秒で約1.29倍でした。
- 常時workerで先行するkeyだけを待つ試作は、中央値2CPU約402.6、4CPU約523.9投稿/秒で約1.30倍でした。複雑化に見合う一貫した改善を示せず、採用版から外しました。
- RAM上の一時volumeでは、2CPU約413.4／419.5、4CPU約549.6／542.9投稿/秒でした。媒体の耐久性を持たない診断であり、実ディスクの1.5倍目標には使いません。2CPUの一試行には受理後の遷移失敗1件があります。
- 同じ8,000件を全て試す固定件数比較でも、途中版は2CPU約22.37／22.41秒、4CPU約17.46／26.73秒でした。4CPUの遅い試行には受理後の遷移失敗2件があり、保存された8,000件は照合しました。最速組だけで目標達成としません。
- 異なる物理コアへCPU割当を固定した診断も、2CPU約435.3／401.7、4CPU約346.1／553.4投稿/秒と変動し、一貫した改善を示しませんでした。CPU割当の固定は製品設定へ追加していません。
- 160主体・32スレッドの試作比較は各試行で約1,700〜1,800件のHTTP失敗があり、実用能力の根拠には採用しません。

診断用のCPUプロファイルは関数内訳を調べる用途です。採用版の速度比較へ混ぜず、プロファイル時間・負荷開始位置の異なる標本から固定のCPU改善率を作りません。

## 継続負荷と復旧

60秒の継続負荷を掛け、正常再起動後に全スレッドのDATとETagを元byteで照合します。主体数は80、毎秒100／200投稿は16スレッド、毎秒300投稿は32スレッドです。

| 条件 | 成功 / 予定 | HTTP失敗 | 未発行 | 予定起点p95 | 再起動後の照合 |
| --- | --- | --- | --- | --- | --- |
| 4CPU・2GiB・毎秒100投稿 | 6,000 / 6,000 | 0 | 0 | 約336.2ms | 約28.4秒・全一致 |
| 2CPU・4GiB・毎秒200投稿 | 11,855 / 12,000 | 0 | 145 | 約592.0ms | 約55.1秒・全一致 |
| 4CPU・4GiB・毎秒300投稿（既定待機） | 17,179 / 18,000 | 0 | 821 | 約498.9ms | 60秒で準備未完了・未照合 |
| 同条件を再試行（待機180秒） | 17,683 / 18,000 | 0 | 317 | 約327.1ms | 約78.0秒・全一致 |

全件成功した毎秒100投稿でも250ms以内の基準は未達です。毎秒200／300投稿にも未発行があり、全条件`stable_at_tested_rate=false`でした。CPUを増やすだけで毎秒300投稿を安定処理できた結果ではありません。ACK済み欠落・重複・不正本文・prefix破損・OOM killはありませんでした。

毎秒300投稿の最初の試行は、起動前のDAT照合に成功しましたが、再起動が測定器の既定60秒待機に間に合わず、後のDATを未照合のまま失敗終了しました。この失敗を残した上で、新規volumeから同じ負荷を再実行し、待機上限180秒を明示しました。17,683成功件と追加100件を含む全32スレッドのDAT・ETagが一致し、照合完了は約78.0秒でした。**元の60秒目標を達成した扱いにはしません。** 起動の遅さを保存内容の不一致と同一視せず、待機上限と実測時間を両方記録します。

4CPU・2GiB・WAF有効・80Mbpsで、毎秒20投稿と閲覧200件/秒を4秒、閲覧2,000件/秒予定を12秒、閲覧200件/秒へ戻す5秒の混合負荷も実行しました。ピーク中の別一時ファイルへの64KiB同期は毎秒200回予定に対し2,093回完了しました。計画2,400回を全て供給した試験ではありません。

- 投稿420/420件と追加200/200件が成功し、HTTP失敗・未発行・ACK済み欠落・重複・不正本文・prefix破損はありませんでした。
- 通常閲覧は800/800件成功。通常投稿の予定起点p95は専ブラ約16.2ms、Web約28.3msでした。
- ピーク閲覧は24,000予定のうち3,227件を発行し、20,773件は未発行でした。発行分のHTTP失敗はありません。毎秒2,000閲覧を処理できた結果ではありません。ピーク投稿p95は専ブラ約576ms、Web約1.43秒でした。
- ピーク後1秒目の閲覧は49件未発行、その後4秒は各200/200件成功でした。ピーク後5秒のWeb投稿p95は約2.07秒で、低遅延を維持した結果でもありません。
- 最大メモリ約386.8MiB、OOM killなし。事前に1,000投稿の成功応答後にSIGKILLし、同一volumeで再起動したDAT・ETagが一致しました。停止から照合完了まで約5.30秒で、5秒目標は未達でした。

これらは合成入力・隔離HTTP・短時間の結果です。長期運用、大きな実履歴、WAN・実NIC、本番切替、実機の電源断・媒体故障の実証ではありません。


## 回帰検査

bootstrapは866個のTest親項目と1個のFuzz初期ケース親項目を8分割して全区分通過し、他42製品・ツールパッケージの全通常テストと`go vet`も通過しました。全パッケージの全race実行ではありません。投稿・資格・規制・再送・取消・候補分割・署名・保存層・子プロセス停止を含む関連race検査も実施しました。

追加検査では、全workerの終了前の書込み禁止、独立行の検証失敗・不正連番・既存行・重複キー・nullの保存前拒否、一回の同期、不明結果の非公開、古いsnapshotの不変性、保存byteと署名の一致、取消・受理枠・容量予約、候補の同一履歴／別履歴識別を確認しました。構築時の次状態は100ケースの匿名・資格付き投稿で元frameの完全再検証結果と一致しました。
