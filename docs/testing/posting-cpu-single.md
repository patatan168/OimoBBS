2026-10-27。`7b6b71b`から、投稿captureの種別判別と完全復号の重複、およびHMAC計算の一時確保を削減しました。**局所処理は短縮しましたが、単一スレッドの実HTTPS全体は中央値でCPU約0.6%減・完了速度約0.4%増に留まり、ばらつきを超える最大速度の改善は確認できませんでした。**

## 実装

- 現行captureは完全型と業務制約を一度で復号・検証し、成功時はschema判別の全体走査を省きます。失敗時は従来の種別判別へ戻し、別形式の委譲、重複schemaの選択、不正入力の拒否を維持します。保存済み・外部入力の完全検証は省きません。
- HMACは用途名と項目を結合する一時sliceを作らず、長さを記録する4byte領域を各項目で再利用します。結果も戻り値の領域へ直接書きます。用途分離、項目順、長さ付き署名対象、鍵、HMACの値は同じです。

依存の追加、内部並列数の増加、保存形式、署名検証、fsync、準備記録→本文WAL→確定記録→公開の順序、受付上限の変更はありません。

## 単一スレッドの実HTTPS

AMD Ryzen 5 5500U、Go1.27.3、CGO無効、同じruntime image、4GiBの隔離コンテナです。DockerのCPU枠1に加え、`GOMAXPROCS=1`を明示し、実行ログのCPUsも1であることを確認しました。CPU枠はquotaで、専有物理コアではありません。

fsync待ちの影響を抑えるため、この比較の保存先だけ8GiB上限のtmpfsを使います。fsync呼出しは維持しますが、電源断に耐える保存先や本番設定の提案ではありません。全6試行の主負荷区間で物理書込みとI/O pressureは0でした。

1板16スレッド、80主体、専ブラ80%・Web20%、固定8,000投稿です。予定1,600投稿/秒を5秒間発行し、全件の完了まで待ちます。Webはフォーム、CSRF、確認、303、l50 gzip取得を含みます。送信予算80Mbps。WAF検査を有効にし、試験だけ頻度枠を緩和しています。内側の10POST/秒・burst20、全体同時128枠、保存・メモリの予約は維持します。

## 通常ディスクと混合負荷

共有SATA SSD・ext4、2CPU・`GOMAXPROCS=2`、120主体の固定8,000投稿は、候補→基準の各1回で全成功でした。CPUは2.7061→2.6310ms/投稿、完了速度は616.95→626.41投稿/秒です。CPU約2.8%減ですが、一組の測定から安定した速度向上は主張しません。

## 先行試行と失敗

- 最初の1GiB tmpfsは空き容量の安全余白に抵触し、負荷準備の投稿が拒否されました。製品の余白を変えず、後続は8GiB上限へ変更しました。
- 1CPU quotaだけを指定した先行3試行は、Goの自動設定でCPUsが2でした。実行ログで識別し、明示的な単一スレッド比較へ混ぜていません。
- CPUsが1・120主体の基準版は一回8,000件成功しましたが、別の一回は46件の503があり、それらの未応答保存も照合で検出しました。変更前の版で起きた失敗を残し、8,000成功という効率比較へ使っていません。80主体は別条件として両版を測りました。
- 追加試行の90主体指定は測定器のCLIで拒否されました。6回の引数拒否ログを保持し、実HTTP試行と区別しています。
