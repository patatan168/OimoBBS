# 間隔の空いた返信の収集待ちを省く

2026-11-01。通常の返信が少量ずつ届くときの応答時間を短縮した。比較元は `e45f403855f18934b0735d62a4978807127fc2b1`、最終候補は全試行記録のV3。本番には反映していない。[全30試行・測定器・検査結果](posting-idle-latency.json)に、不採用候補、遅い試行、未発行も残した。

## 変更と保存条件

返信保存のための収集待ちは通常16msだった。最後の保存から100ms以上空き、群の開始時に後続操作が待っておらず、集中受付の500ms期間外なら、この追加待ちを零にする。到着済みの同種操作は収集する。最初の保存群は従来どおり待ち、フォーム表示とCookie確認は最終保存時刻を更新しない。

予算の選択は板の所有列で群の開始時に一度だけ行う。それ以外の群では、前群の終了時に選んだ従来の2/16ms予算を保持する。保存が遅くても、十分な間隔があり後続がいない場合は、将来の到着を待つための16msを追加しない。

proposalのSync、本文WAL/currentのSync、accepted decisionのSync、公開・成功応答の順序は変更していない。受付制限、Cookie確認、同一内容制限、保存形式も変更していない。

## 測定条件

隔離コンテナの実HTTPS/HTTP1.1、2CPU、1GiB、送信予算80Mbps、通常ディスクの新規volumeを使用した。合成データを専ブラ形式80%・Web20%で送った。WebはフォームGET、CSRF・同意付きPOST、303、gzipのl50取得までを含む。計測器が確認済みCookieを保持するため、初回Cookie取得の往復は含めない。

WAFを実際に有効化し、両版同じ投稿global rate 100000、global concurrent 256、client rate 1000とした。通常の新規隔離fixtureでは一般投稿間隔制限を無効にするが、投稿試行上限と同一内容制限は残り、本文はすべて異なる。本番設定の処理量試験ではない。各試行の後に100件を追加し、成功応答した本文の欠落・重複・DAT内容を照合した。試行は逐次実行した。

既存測定器のWeb GETが圧縮必須仕様に未対応で、最初の `baseline-low-a.log` はready判定で失敗した。以降は指定省略のGET/HEADにgzip受入れを追加し、必要時に復号する薄いラッパーを使用した。明示したRange/identity条件は保持した。管理操作も通常の認証・CSRF・再認証・CASを通した。測定器のソースとSHA-256はJSONに収録した。
