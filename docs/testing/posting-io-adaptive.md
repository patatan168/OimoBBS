# 投稿の同期待ちに応じたまとめ書き

2026-10-25。同期に10msの遅延を加えた隔離比較で、計測した主要Syncを約8%減らしました。通常時の一定の高速化や、混合負荷の無拒否は確認していません。`321186f`を基準に、成功した保存群の実Sync時間で収集待ちを調整するよう変更しました。[全試行・再現コマンド・raw hash](posting-io-adaptive.json)を保存しています。稼働環境は変更していません。

操作数が多いだけで収集を2msへ短縮すると、保存が遅いときも小さい群の同期を増やすことがあります。必須journalと本文WALのSync呼出し時間が合計8ms以上なら、500ms間は既存の上限16msでまとめます。速い状態に戻って期限が切れれば、従来の操作数による16ms/2msの選択へ戻ります。

新しい待機timerは追加せず、次群の開始時に収集予算を固定します。確認だけの要求は先に返し、到着済み操作は直ちに実行します。保存候補64frame/8MiB、論理操作128件、受付129件・待機128件、容量予約、FIFOを保ちます。実fsyncとproposal→本文WAL→decision→公開/成功応答の順序は維持しています。保存形式・readerの変更はありません。

独立本文の並行Syncは最大値を使い、必須journalの二回のSyncと合わせます。符号化・Write・checkpoint・親dir同期は適応の判断に含めず、Sync内のスケジューラ待ちは含みます。この値は全I/Oの合計時間やデバイスの待ち時間そのものではありません。取消・保存前拒否・結果不明を成功した保存の標本にはしません。

## 同期遅延を加えた比較

両版の私的コピーだけで、計測中のWriter・共有本文・checkpointの各Sync直前に10msの待ちを加えました。実Syncも毎回実行します。通常imageには遅延や診断用signalを含めません。実SSDの競合や帯域制限を直接再現した試験ではなく、同期待ち増大への応答を切り分ける条件です。

4CPU・4GiB、予定600投稿/秒を10秒、全6,000件を完了まで流します。各版二回で順序を反転しました。より集中した試験は予定1,600投稿/秒を5秒、全8,000件です。通常の計時と分けます。
