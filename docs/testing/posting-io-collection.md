# 投稿I/Oの収集待ち拡張の再検討（不採用）

2026-10-27。投稿の必須Syncが長いときだけ収集待ちを延長する二つの試作を検証しました。**最終候補も再試行でp95約947ms・7件未発行となり、安定した改善を確認できなかったため、製品コードを元へ戻しました。** [全試行・識別情報](posting-io-collection.json)には、不採用試作と未発行も含めています。

## 試した動作（製品には不採用）

成功した群の必須journal・本文WALのSync合計を観測します。保存件数は確認往復や操作数ではなく、実際の保存候補ID数を使います。

| 観測したSync合計と保存件数 | 次群の収集待ち上限 |
| --- | ---: |
| 8ms以上、以下の拡張条件に該当しない | 従来通り16ms |
| 64ms以上、8件以上を保存 | 32ms |
| 128ms以上、8件以上を保存 | 64ms |

遅いSyncの観測から500msだけ優先し、期限後は既存の操作数による2ms/16ms判断へ戻ります。8ms未満の保存では期限を更新しません。少量の遅い保存では16msを選び直します。追加のtimerや取得要求は作りません。収集待ちは群ごとの累計であり、投稿応答の最大時間を保証するものではありません。

一群64件・8MiB、受付列、メモリ/ディスク予約、確認結果の先行返却、取消と再構築の契約を維持します。proposal同期→本文WAL同期→decision同期→公開/成功応答を変更せず、同期失敗時のUnknown停止も維持します。保存形式の移行はありません。[収集待ちの設計](../architecture.md#確認要求と収集待ち)も参照してください。

## 比較条件

基準は`7b6b71b`。同じ通常runtimeとGoの設定から、基準・最終候補・不採用試作を構築しました。Docker CPU quota、共有SATA SSD、専用の隔離volume、実TLS HTTP/1.1です。WAF検査と内側の10POST/秒・burst20、予約・同時枠を保持し、性能試験用に頻度上限だけを引き上げています。稼働WAF設定の測定ではありません。計時前に隔離サイトの外部表更新を無効化して終了を待ちます。

`slow-*`は診断用コピーだけで、計時区間のWriter・共有本文・checkpointの各Sync前に25ms待ち、その後で実Syncも実行します。SATA命令完了の遅れをそのまま再現したものではなく、同期が長い条件での制御比較です。通常計時とbuild・Goテスト・profile解析は重ねていません。

## 保存先SSDの読み取り確認

MX500（CT1000MX500SSD1、M3CR046）を、読み取り専用デバイス指定で`smartctl -x -j`から確認しました。自己テスト開始、SMART設定変更、FW更新、OS設定変更はしていません。

| 項目 | 値 |
| --- | ---: |
| SMART総合判定 | PASSED |
| Device Statistics: Percentage Used Endurance Indicator | 96 |
| SMART 202: VALUE / RAW | 4 / 96 |
| UDMA CRC / Reported Uncorrectable | 0 / 0 |
| 現在温度 | 44°C |

これはデバイス自己申告の耐久性消費96%・残量指標4%と解釈できる値です。同じMX500に関する[smartmontools開発元の説明](https://github.com/smartmontools/smartmontools/issues/296)でも、RAWが使用率、正規化VALUEが残量指標と説明されています。[MicronのSMART定義](https://www.micron.com/content/dam/micron/global/public/products/software/storage-executive-software/msecli/storage-executive-cli-user-guide.pdf)でもID202は使用率です。故障時期や今回の待ち時間との因果は、この値だけで確定できません。再配置・保留・訂正不能・CRCカウンターとerror logは0でした。

生のSMART出力は識別情報を含むため`var/posting-io-floor-20261027/`の非公開領域に残し、この記録には限定した集計だけを含めます。
