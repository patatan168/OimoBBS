# SATA設定と保存待ちの検証

2026-10-27。アプリ内の調整から対象を下げ、共有SSDの省電力設定、キュー深さ、その組合せを計16試行しました。**実fsyncの長い待ちはどの変更条件にも残り、安定した改善は確認できませんでした。設定はすべて元へ戻しています。** [全試行・設定・監視・raw hash](posting-io-device-policy.json)を保存しました。

製品コードとBBSコンテナは変更していません。この検証はアプリを通さない保存待ちの切り分けで、投稿スループットの測定ではありません。[直前の本文準備の並行化](posting-io-bodyprepare.md)とは対象と指標を分けています。

## 測定した処理

専用の新規3ファイルへ各16KiBを追記し、その都度`os.fsync`を呼びます。最大30群/秒を30秒、各試行900群・最大2,700回の実fsyncです。1群は三つのファイルの同期であり、1投稿に読み替えません。遅れて予定時刻から一周期以上外れた群は発行せず、その件数を残します。再試行で成功件数を補っていません。

空ファイルと親dirの初期同期は計時前に済ませ、設定変更後は5秒待ってから測定します。各表のp95/p99/最大は一回のfsyncのwall時間で、投稿や群全体の応答時間ではありません。CPUはPython生成器と公開GET監視threadの合算で、アプリのCPU時間ではありません。実行群数が違う試行の少ないCPU時間を効率改善へ使いません。

AMD Ryzen 5 5500U、CT1000MX500SSD1、ext4、Linux `6.12.90+deb12.1-amd64`です。試験ディレクトリと実BBSの`/data/site`はどちらもdevice `8:2`であることを読取り専用のstatで確認しました。他サービスは停止せず、共有媒体上で測っています。固定パターンの合成payloadは最大約1.41MiB/秒で、metadataや他サービスを含む媒体全体のI/O量ではありません。

## 省電力設定の比較

[Linuxの説明](https://docs.kernel.org/scsi/link_power_management_policy.html)では、`med_power_with_dipm`はDIPMを伴う省電力方針、`max_performance`は性能を優先する方針です。sysfsの読戻しは[要求先のpolicy値を返す実装](https://github.com/torvalds/linux/blob/v6.12/drivers/ata/libata-sata.c#L882)であり、今回オンワイヤのリンク状態は採取していません。

## キュー深さの比較

元は32、変更は1です。省電力設定は`med_power_with_dipm`へ戻し、各試行中もその値を確認しました。順序は同じく元1→変更1→変更2→元2→元3→変更3です。

## 復元と稼働側の観測

設定は共有SATAデバイス全体に作用するため、変更用コンテナは対象sysfsファイル一項目だけをbindし、ネットワークなし・read-only root・全capability削除・root UIDで動かしました。trapによる終了/信号時の復元と、240秒の自動復元、制御側finallyの読戻し・復元を用意しています。先に短時間の変更・SIGTERM・元値の読戻しを検査してから本測定へ進みました。組合せは二つの独立した復元役を使います。

終了時に`med_power_with_dipm`、キュー深さ32、write-back cache、`mq-deadline`の一致と、変更役コンテナが残っていないことを確認しました。アプリのGoファイル1,452個も基準`7b6b71b`とbyte一致です。BBSのcontainer・image・起動時刻は維持され、healthy・再起動0・OOMなしでした。恒久的な設定やfirmware、mount、書込みキャッシュは変更していません。

TLSを通常検証する公開GETを約2秒ごとに監視しました。省電力比較104件、深さ比較106件、組合せ71件、計281件はすべて200です。準備・設定切替待ちも含む監視の最大経過時間は約2.01秒、各比較のp95は約79/66/77msでした。2.01秒の要求は元の省電力値が開始・終了時に読めた切替待ち区間にあり、設定変更との因果は断定しません。公開GETの成功だけで他サービス・管理操作・実投稿の健全性を検証したとはしません。

終了後に取得したカーネルログの対象時間帯にはATA/sda/EXT4関連のエラーは見つかりませんでした。SCSIの`ioerr_cnt`は終了時だけ`0x1dc`（累積476）を読み、開始値がないため今回の増加や媒体故障とは判定できません。カーネルログの生データは非公開の採取ディレクトリへ置き、公開JSONには集計とhashだけを残しています。
