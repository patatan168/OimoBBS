# 投稿JSONの符号化・検証の追加改善

2026-10-25。[前段のjournal符号化](posting-json.md)を基準に、投稿本文・観測情報・保存操作の固定スキーマ符号化と、JSON構文検査の重複走査を減らしました。[全試行・再現用ソース・検査結果](posting-json-second.json)を保存しています。稼働環境は変更していません。

## 実装

- 保存DTOの型から専用符号化関数を生成し、実行時の反射・一時文字列を減らします。標準Marshalとのbyte一致、HTML escape、不正UTF-8置換、nil、ゼロID拒否を維持します。RawMessageは標準実装で構文・正規化を確認します。
- 観測値の業務検証後、安全なJSONサイズ上界が128KiB以下ならサイズ確認の再符号化を省きます。上界だけが超える場合は正確に符号化して判定し、正当な入力を余分に拒否しません。
- 構文・Unicode・深さ・重複キーを一回の走査で検査します。大きな無escape文字列はbyte探索で読み飛ばし、型付き復号の完全キー・null・数値範囲検査も維持します。
- 種別選択のschema読取りも専用走査へ移します。未知形式を別のvalidatorへ渡す既存条件は標準復号へのフォールバックで保ち、種別選択だけで保存を許可しません。

DTO変更後は`mise exec -- go run ./tools/jsonencodegen`で再生成します。`-check`および生成器のGoテストで生成漏れを検出します。署名、保存形式、proposal→本文WAL→decision→公開/成功応答の順序、fsync、受付枠は変更していません。

## 4CPUで遅くなる試行

初めの通常3組は、前849.8〜901.8に対して後443.1〜669.5投稿/秒でした。候補のCPU単価は下がっていますが、I/O pressureは前32〜34msに対し後774〜1160msで増えています。quota抑制は両版0でした。この大きな処理量低下を削除して集計しません。

その後、元の通常条件の第4組では後939.8・前446.2投稿/秒となり、基準版にもI/O pressure約737msの遅い試行が出ました。第5組は前890.2→後945.3投稿/秒でした。追加試行も全て通常中央値に含めています。遅い側が入れ替わったため候補固有の現象とは言えませんが、実装差と共有媒体の状態を完全に切り分けた結果でもありません。

開始前に300ms待つ通常版の独立対照では、前894.2→後927.7投稿/秒、CPU3.554→3.360msでした。診断バイナリをprofileなしで動かす対照でも前880.4→後933.1投稿/秒でした。これらは通常中央値へ混ぜません。準備直後の進行状態が関係する可能性はありますが、待ちを足すだけでは保存待ちの根本原因や改善の証明になりません。
