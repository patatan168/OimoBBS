# 保存JSONの専用復号と単一スレッド投稿

2026-10-27。前回の[重複走査・HMACの削減](posting-cpu-single.md)を含む`6e27cb1`から、保存型ごとの復号コードを生成しました。**単一スレッド・固定8,000投稿を完了した通常試行の中央値で、CPUは約5.3%減、完了速度は約5.6%増でした。** 基準4回・候補3回の成功試行による比較です。候補の別の一回には混雑応答2件があり、失敗も下表に残します。

[全15試行・検査・ソース識別・元データのSHA-256](posting-json-typed.json)を保存しています。うち一回は診断の準備失敗で、主負荷を投入していません。ソース・イメージ・コマンド・生データは`var/posting-json-typed-20261027/`です。稼働BBSは置き換えていません。

## 実装と受理条件

生成対象は本文WALのOperation/Append/Create、HTTP観測、証拠Eventと非必須記録、投稿Capture、制御WAL操作の9型です。フィールドごとのreflection・map検索・独自スカラーへの保留処理を省き、型が決まったswitchと代入で復号します。配列も要素数の事前走査をせず、私的な候補へ構築します。

共通readerで構文・UTF-8・Unicode escape・深さ16・数値範囲・正規十進表記・小文字hex・nullを検査し、生成側で完全な必須キー集合と重複・未知・大小文字を照合します。RawMessage内部にも同じ構文・重複・Unicode・深さの制約を適用し、元byteを複製します。成功後だけ宛先へ代入します。入力変更後にも戻り値が変わらないことを検査しました。

専用経路は本文128KiB未満・宛先がゼロ値の場合だけです。大きな本文、既存値へのmerge、未登録型は従来経路へ戻します。型そのものも照合し、埋込みで昇格したmethodを別の型へ誤適用しません。Input/Policyの省略可能な`cap_only=false`だけは既存の純粋な復号規則として明示し、他の独自callbackを推測で迂回しません。

依存、保存形式、署名対象、fsync、準備記録→本文WAL→確定記録→公開の順序、受付・メモリ・ディスクの上限は変更していません。生成の一致は次で確認できます。

```sh
mise exec -- go run ./tools/jsondecodegen -check
mise exec -- go run ./tools/jsonencodegen -check
```

## 検査・失敗・適用範囲

専用methodを持たない同じ構造の別名型で、従来の反射復号を比較対象にしています。型付き値、任意JSON、約33万回のbyte変異、約19万回の任意入力、約16万回の構造を保った値変更で、受理・復号値・失敗時の非公開性が一致しました。最初の任意入力fuzzはcoverage縮小に時間を使ったため、縮小時間を100msに制限した別試行も記録しています。

キーの重複・大小文字・escape、未知・欠落・null、Unicode・NUL・surrogate、符号・桁数・整数端、hex、深いRawMessage、128KiB前後、サイズ上限、非ゼロ宛先へのmerge、nil宛先、method昇格、入力byteの所有権も照合しました。

strictjson・domain・postcapture・evidence・storeの全race、app・evidence・store・domain・postcapture・postinputの通常検査、bootstrapの投稿・Cookie・CSRF・WAF・ネットワーク・証拠関連検査、全製品go vet、両生成器の一致検査が成功しました。投稿・保存層の既存SIGKILL境界試験も含みます。新しいテスト追加後のstrictjsonと生成器のraceも再実行しています。

初回vetのテスト用String戻り値未使用は、受理検査として値を捨てることを明示して修正し、再検査に成功しました。診断の初回準備はtmpfs保持用の補助コンテナも選んで失敗し、負荷threadが待機したため停止しました。補助領域を回収し、サーバー専用ラベルで識別して負荷thread開始前に確認する測定器へ修正後、再実行しています。主負荷未投入の失敗を性能試行へ混ぜません。

実HTTPコンテナでのSIGKILL、停電・媒体故障、長時間・本番負荷、WAN・実NIC、全bootstrapテスト・全パッケージraceは追加未確認です。稼働サービス、ホストのCPU・保存設定は変更していません。
