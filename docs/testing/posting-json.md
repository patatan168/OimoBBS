# 投稿journalの固定スキーマJSON符号化

2026-10-25。保存同期改善後の`82cc6b4`を基準に、必須・非必須journalの一括追記で、署名イベントと制御操作を一つのbufferへ直接符号化しました。汎用Marshalで大きなbase64文字列を繰り返し走査する処理を減らします。[全試行・ソース・検査結果](posting-json.json)を保存しています。稼働環境は変更していません。

## どこが支配的か

CPUの診断ではJSONの検証・復号・符号化が最大の分類です。一方、大幅に遅い試行では保存I/O待ちが増えます。CPU標本の比率はHTTP経過時間の割合ではありません。復号側は既存の独自厳密デコーダーを維持し、今回は固定スキーマの符号化を軽くしました。

| CPU分類 | 変更前 CPU秒 / 比率 | 変更後 CPU秒 / 比率 |
| --- | ---: | ---: |
| json | 8.53 / 35.99% | 8.06 / 34.62% |
| signature | 3.07 / 12.95% | 3.19 / 13.70% |
| compression | 1.44 / 6.08% | 1.40 / 6.01% |

各版2CPUで8,000件成功の診断1回です。JSONには新しい専用符号化関数内の処理も含め、単に汎用ライブラリの外へ移した作業を計測から落としません。分類は累積stackのため重複する場合があります。診断版のprofile・Sync計時は通常版の処理量へ混ぜません。

固定8,000投稿を完了まで測った中央値です。CPUは主負荷区間のcgroup累計差で、入力準備・回復投稿・終了時の非必須キュー最終drainは除きます。前後の順序を入れ替え、遅い試行も除きません。CPU時間の差とI/O待ちを含む処理量の差を分けて読みます。1コアあたりの符号化費用は減りましたが、単体の3.3倍を投稿全体へ一般化しません。

各版の処理量の範囲：

- 1CPU：前 289.6〜300.7、後 335.7〜344.2 投稿/秒。

AMD Ryzen 5 5500U・共有SATA SSD・4GiBの隔離Docker volume、loopbackの実HTTPSです。Go1.27.3、CGO無効・trimpath・同じruntime imageです。CPUはquotaであり、専有物理コアではありません。ビルド・テスト・profile解析は通常計時に重ねていません。

一板16スレッド、120主体（専ブラ80・Web40）、専ブラ80%・Web20%の8,000投稿です。Webはフォーム・CSRF・確認往復・303・遷移先l50 gzipまで含みます。1,600/秒×5秒の全予定を完了まで流す方式で、持続可能上限の測定ではありません。準備と回復100投稿は主負荷の計時外です。送信予算80Mbps。

## 遅い試行をどう確認したか

通常4CPUの第3組では、変更前882.9→変更後859.0投稿/秒（約2.7%減）、CPU 3.598→3.666ms/投稿でした。I/O pressureは32.7→31.4ms、quota抑制は両版0で、この試行の差を保存待ちやquota増だけでは説明できません。生成器CPUも8.864→9.272秒へ増えています。

逆順の第4組では882.1→894.8投稿/秒、CPU 3.618→3.564ms/投稿で悪化を再現しませんでした。4CPUの追加profileも保存しています。元の1試行の細因をCPU周波数・cache・scheduler等のどれかへ特定できてはいません。小さな差を全て実装の効果や共有SSDのせいと断定しません。

1CPUの追加診断では、逆に変更後が334.0→292.2投稿/秒へ悪化しました。主要Syncの回数は増えず、所要時間が大きく増えています。

| Sync対象 | 回数 前→後 | 所要時間合計 秒 前→後 | 最長 ms 前→後 |
| --- | ---: | ---: | ---: |
| writer_commit | 349 → 343 | 1.912 → 7.108 | 56.5 → 124.6 |
| shared_thread_group | 138 → 134 | 0.372 → 2.850 | 52.2 → 153.9 |
| group_body_checkpoint | 48 → 32 | 0.218 → 1.553 | 8.0 → 99.9 |

この診断のCPUは2.991→3.011ms/投稿、I/O pressureは約203→1021ms、GC停止合計は約3.8→74.2msでした。両版GOMAXPROCSは2で、1CPU quotaによる抑制も発生しています。Sync計時はscheduler待ちを含み、並行writerの時間をHTTP経過秒へ単純加算しません。物理SSDの遅延源まで特定した結果ではありません。

通常版の1CPUで大きく見える差も、この変動から切り離せていません。JSON符号化の単体70%削減を、投稿全体の16%改善と読み替えません。

混合負荷の最初の基準版でWAF503が44件出て、実行制御の全成功assertでいったん停止しました。失敗を残し、同じ保護・負荷の候補版へ継続しました。拒否本文・設定・コードから、投稿120主体＋閲覧40主体と全体128同時枠の競合と判断しています。受付枠を広げて成功扱いにしていません。

## 変更と検証の境界

- 本文と署名は元byteからbase64化します。可変文字列は標準JSONのescapeと不正UTF-8置換を使い、任意文字列をそのまま引用符内へ挿入しません。
- 既存のキー順・数値の正規文字列表現・null・署名・frameのbyteを維持します。必須記録と非必須記録で異なる結果コードとtarget配列も維持します。
- 巨大payload、符号付き時刻・最大連番、escape・Unicode・任意byteを旧Marshalと差分照合しました。差分fuzzは30秒・137,934件、並行署名を含む旧frameとのbyte一致も確認しています。
- evidence・storeの通常試験、evidence全race、bootstrapの投稿・Web・復旧・共有WAL・資源境界、go vet、CGO無効のcmdビルドが成功しています。
- 保存前のJSON構文・UTF-8・完全型・重複キー・深さ・署名の検査、proposal→本文WAL→decision→公開/成功応答の順序、fsyncを維持します。一般のJSON APIや保存形式の互換性は変更しません。

生データ・通常/診断imageのソース・実行コマンドは`var/posting-json-20261025/`にあります。初回のimage buildはDockerfileのbase image指定に失敗し、既存ローカルruntimeのIDを照合してからtag指定で再実行しました。失敗したbuildをHTTP試行に使っていません。

基準imageは前回の最終版を再利用しました。バイナリのVCS刻印は`b78b1bf+dirty`ですが、全製品Goソースとgo.mod/go.sumを今回の`82cc6b4`へ照合し、同値を確認しました。Go・CGO・trimpath・アーキテクチャのbuild情報も全記録へ保存しています。
