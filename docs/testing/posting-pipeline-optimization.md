# 投稿シーケンスを変更した1.6倍への再挑戦

2026-10-24。基準は`3343d89`、稼働イメージ`oimobbs:post-boundary-20261024`です。**同じ改善版の2CPU→4CPUで投稿1.6倍を再現できず、製品コード・稼働イメージは変更していません。** 改善を確認できない複雑な実装を残さず、全試作を隔離領域へ退避しました。

[38回の実HTTP試行、検査結果、ソース・元データのSHA-256](posting-pipeline-optimization.json)を保存しました。生データ・試作ソース・実行スクリプトは`var/posting-pipeline-160/`にあります。[前回106試行](cpu-mutex-gc-optimization.md)とは別の再挑戦です。

## 試した変更

1. 同じスレッドの先行処理までだけを投稿順に待ち、独立した後続のCPU構築を継続する方式。保存前には全件を合流させました。初期の`sync.Once`による合流で所有列が残りの作業へ参加できなくなる停止を試験で検出し、CAS・完了通知へ修正して再検査しました。改善を確認できず不採用です。
2. journalのpayload構築・検証とsource/hash計算をまとめ、署名・frame符号化・復号・値検査も同じCPU作業へ統合する方式。段階ごとの全件待合せを減らしました。
3. 2の構築経路内だけで私的byteを生成・完全検証し、圧縮直前の同じJSONの再走査を省く方式。一般の符号化・書込みAPIと復旧の厳密検査は維持しました。
4. 検証・署名・圧縮済みの私的候補を、構築元・header・seq・一度だけの確定へ束縛する方式。これを使い、本文WALの保存中に決定記録のCPU構築を重ねました。実際のWrite/Syncはproposal→本文WAL→decisionの順序を保ち、成功応答・公開も全耐久境界の後に限定しました。標準の入力非依存validatorだけで並行構築を有効にし、外部の独自validatorは従来順序のままにしました。
5. 取得した合成負荷のCPUプロファイルを使うGo PGO。同じプロファイル・同じバイナリで2CPUと4CPUを比較しました。
6. 低・中負荷の16ms収集待ちを維持し、高負荷時の2msだけを0へ変更する方式。一般の受付上限・保存上限・同期は変えていません。

いずれも採用できる実ストレージ性能の改善を確認できませんでした。WAF、署名検証、Sync、保存ログを無効化する変更や、2CPUを意図的に遅くする設定は使っていません。GoのCPU・メモリ自動調整、GOGC、ホストのクロック・CPU affinity・他サービスの設定も変更していません。

共有SATA SSD上の測定です。I/O待ちの大きい試行でCPU使用量も下がっています。ただし、変動をすべて他サービスのせいにしたり、各候補の小さな差とI/Oの変動を分離できたとは扱いません。

## CPU・Mutex・GC

SSD待ちを除くtmpfs診断でも、基準版は15.213→10.578秒（約1.438倍）、Cは15.506→10.376秒（約1.494倍）でした。各1回の診断であり、耐久ストレージの性能・復旧性能ではありません。

Cのtmpfsでは平均CPU使用量が約1.968コア分から約3.629コア分へ増えました。一方、同じ8,000投稿の総CPU時間は約30.51→37.66 CPU秒へ増えています。コアを使ってはいますが、投稿あたりのCPUコストが一定にはなっていません。この結果だけで特定のCPU周波数・メモリ帯域・スケジューラーを原因と断定しません。

Aの4CPU診断では、標本化したMutex待ちの全goroutine合計は約91ms、GC停止合計は約6.12ms、確保量は約6.78GB、約3,163万回、GC32回でした。C診断はGC停止約7.60msでしたが、前述の429を含むため8,000成功の同一仕事量の診断とは扱いません。GC停止や共通Mutexだけを減らして解決する状況ではなく、CPU作業間の待合せ・直列区間とI/O待ちが残ります。

正常再起動から全16スレッドのDAT・ETag照合完了までは基準版29.03秒、C28.96秒でした。どちらも本文・ETagが一致しましたが、この差を再起動高速化の実績とはしません。強制停止・停電・媒体故障の新しい実証ではありません。

基準版・B・Cの初回4CPU固定仕事量試行では、終了時の非必須HTTPログも受理19890・保存19890・失敗0でした。ただし再起動を含む継続試行の終了時集計は最後のbootだけで、両版とも受理17・保存0・失敗17でした。物理容量と別に日別64MiB・全体128MiBの展開量上限もあるため、この集計だけで原因や新規回帰を断定しません。**継続試験を非必須ログ無欠測の実用上限とは認定しません。**

## 検証と不採用の保存

- store・evidence・appの通常試験に加え、投稿の入力形式・重複送信・CSRF・バッチ・復旧を実HTTPで確認しました。
- store・appの全race、evidenceの全race（候補A）と変更箇所の関連race、bootstrapの関連raceを確認しました。evidenceの全raceは最初の180秒制限に達したため、600秒制限で再実行し282.7秒で成功しました。
- 従来の独立追記と新しい構築経路で、受理結果・状態・圧縮後の保存byteが一致する差分fuzzを30秒実行しました。重複キー、不正Unicode、NUL、深すぎるJSON、古い状態・別所有者・二重確定、元入力の改変、同期失敗の拒否も検査しました。
- 複数スレッドの取消、proposal、本文の一部、最初のthread、全thread、decisionの各境界で停止させ、復旧結果と公開前の非公開性を検査しました。本文の同期完了前にdecisionを書かないことも確認しました。

これらは試作の整合性・並行性の検査です。性能上の採用条件まで満たしたという意味ではありません。最終的に17ファイルがビルド済み試作と一致することを確認して退避し、製品ソースを基準コミットへ戻しました。稼働BBSは元のイメージでhealthy・再起動0回を確認しています。今回の稼働環境への投稿・負荷試験、設定変更、サービス切替は行っていません。
