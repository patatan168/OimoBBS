# 投稿回復の再悪化を同期I/Oまで追跡する

2026-11-03。[前回の回復測定](posting-burst-recovery-20261103.md)で残った「一度速くなった後に遅くなる」現象を追加調査しました。**攻撃のない通常投稿でも再悪化し、アプリを起動しない同期書込みだけでも遅延を再現しました。今回の再悪化では、ext4の同期とSATA命令の完了待ちが先行しています。**

[試行結果・時系列・対応する同期とSATA命令・原出力hash](posting-recovery-regression-20261103.json)を保存しています。SSD内部、制御装置、ドライバー、割り込み処理、電源管理のどこで完了が遅れるかまでは特定していません。故障判定や、特定の別サービスを原因とする判定ではありません。

## 今回分かった悪化の形

通常速度の目標は前回と同じで、1秒ごとの正常20件が全件成功・未発行なし、予定時刻から完了までのp95が100ms以下の状態が3秒続くことです。単位は1秒で、0秒は最初の区間から正常だったという遡及判定です。観測末尾までの安定は、その後の再悪化を含めて別に確認します。

| 条件 | 正常投稿 | 遅い区間 | 通常速度への復帰・維持 |
| --- | ---: | --- | --- |
| 製品版・攻撃あり・回復120秒 | 2740/2740 | 集中終了後0〜12秒、p95 202〜374ms | 13秒後から観測末尾まで約28〜31ms。後の再悪化なし |
| 同期診断版・攻撃あり・回復120秒 | 2740/2740 | 集中終了後42〜57秒、p95 247〜472ms | 最初は正常。再悪化後は58秒後から観測末尾まで正常 |
| 同期診断版・攻撃なし・通常投稿137秒 | 2740/2740 | 試験開始40〜55秒、p95は最大488ms | 集中自体がなくても再悪化。56秒以降は観測末尾まで正常 |
| アプリなし・3ファイルへ同期書込み90秒 | 1618/1800群 | 開始約64〜80秒に同期待ちが増加 | 80秒以降は再び2〜3ms程度の同期へ戻った |

「集中終了から13秒かかる」と「一度戻った後に再悪化する」は区別して残します。製品版の今回の試行は通常5秒のp95が29.5ms、攻撃区間が339.8ms、集中終了後の遅い13秒が202〜374msでした。通常版の内部工程は追加計測していないため、この13秒の試行の内部原因を他の診断試行だけで断定しません。

実投稿の3条件は計8,220/8,220件成功、失敗・未発行・ACK後の完了エラー・DATの欠落・重複・不正本文・OOMなしです。各試行で準備済みprefixと名前・本文・ACKの整合性を照合しています。攻撃なし対照では攻撃拒否の判定`flood_limited`をfalseのまま残し、攻撃混在試験全体の合格へ読み替えていません。

製品版の大量投稿は1,200件予定中1,199件発行・1件未発行、142件ACK・1,057件429でした。正常投稿の成功数とは分けています。

## 実投稿と同期待ちの対応

攻撃ありの同期診断では、集中終了直後の42秒間は速く、その後の16秒間だけ遅くなり、通常20投稿/秒を続けたまま再び速くなりました。

| 集中終了後 | 秒ごとの投稿p95 ms | 処理中投稿の最大 | 対象として照合できたext4同期の最大 ms | 独立ファイル同期の最大 ms |
| --- | ---: | ---: | ---: | ---: |
| 0〜41秒 | 27.7〜38.3 | 1 | 40.2 | 42.7 |
| 42〜57秒 | 247.1〜471.5 | 6 | 188.3 | 118.0 |
| 58〜119秒 | 27.9〜31.8 | 1 | 31.0 | 21.9 |

遅い区間では、投稿保存の三つの同期の合計が最大347.833msに増えました。計測時刻から確認した具体例は次のとおりです。

- 試験開始74.312秒の本文共有WAL同期は150.028msでした。同じ区間でSATAのフラッシュ命令が発行後114.389ms待ち、journalの確定処理が126.237msかかっています。
- OSのthread標本では、その本文WALの`fsync` syscallが`jbd2_log_wait_commit`で待機していました。検出ログの同期も同じjournal待ちに入っています。
- それより前の73.546秒の本文WAL同期は188.259msで、独立した8KiBファイルへの同期も同じ区間で118.013msでした。
- 投稿を保持する数は速い区間の0〜1件から最大6件へ増えました。発行待ちp95は約0.106msで、負荷生成器が発行をためた結果ではありません。

これらは重なった時間であり、150＋114＋126msの直列待ちとして足しません。本文WALのcheckpointは当該回復区間で発生していません。

```mermaid
flowchart LR
  A[ストレージ命令の\n完了待ち] --> B[ext4の同期完了待ち]
  B --> C[投稿の必須保存が遅延]
  C --> D[処理中の投稿が増加]
  D --> E[投稿応答のp95が上昇]
```

## 集中を外した対照

攻撃なしの対照では、WAFを有効にし、正常20主体・20投稿/秒・同じ4スレッド・同じ時間の投稿を続けました。大量投稿・低速本文・未完ヘッダーだけを発生させていません。

試験開始40〜55秒に再悪化し、処理中投稿は最大7件へ増えました。45.540秒の必須原本WAL同期は208.740msで、同じ区間に192.531msのSATA書込み完了待ちと121.954msの独立ファイル同期が重なりました。対象WALの`fsync`がjournal確定を待つthread標本も残しています。

さらに、隔離BBSを起動せず、専用3ファイルへ各16KiBを追記し、各回で実`fsync`する試験を90秒実行しました。予定は毎秒20群・合計60同期、1,800群で、完了1,618群・未発行182群です。遅れた分を無制限に連続発行する処理はありません。

| 単独試験の開始後 | 同期待ちp95 ms | 最大 ms |
| --- | ---: | ---: |
| 0〜10秒 | 2.8 | 19.8 |
| 50〜60秒 | 2.7 | 7.8 |
| 60〜70秒 | 63.3 | 132.7 |
| 70〜80秒 | 40.3 | 83.7 |
| 80〜90秒 | 3.0 | 4.7 |

69.260秒の132.697msの同期では、SATA書込み命令の104.149msとjournalの110.968msが重なっています。Pythonの単独試験プロセスが、専用ファイルの`fsync` syscallでjournal確定を待っているthread標本も確認しました。

したがって、今回の再悪化を、集中終了後だけ動くアプリ内の後処理やWAFの待機解除だけに結び付けることはできません。別プロセスの約30秒間隔・約20MBの書込みもありますが、先行する同じ書込みのたびに同じ遅延が出てはいません。特定の別サービスだけを原因とする判断はしていません。

## 条件と計測の限界

製品は`1e781ca`のバイナリで、SHA-256は前回の候補と同じです。同期診断版はその私的コピーへSync時間・checkpoint・投稿保持数の出力だけを加えた別イメージです。Go1.27.3・CGOなし、2CPU・2GiB・80Mbpsの隔離Docker、直接BBSのloopback実TLS HTTP/1.1、専ブラ80%・Web20%・既定WAFを使いました。回線分類更新は隔離サイトだけで停止し、取得終了を確認しています。

同期診断では8KiBの専用ファイルを最大2Hzで4KiB更新＋同期する観測も併用します。OSの統計は100ms、プロセスのI/O集計は1秒ごとです。対象ディスクだけをfilterした専用trace instanceでext4・journal・SATAを記録し、RAMに蓄積して終了後に書き出しました。診断には追加I/Oと監視の費用があるため、製品版との性能改善率へ使いません。

完全に採れた3診断試行は、traceの容量上限超過・CPU別overrun・dropped events・ATA tagの対応衝突が0でした。観測中の`ata_qc_complete_failed`も0です。対象threadは100ms標本から照合しており、その間に終了した短命なthreadが対象集合に含まれない可能性は残ります。

初期の単独観測は末尾約15秒が次の準備と重なり、その次の長時間試行も古い照合用接続の切断でHTTP集計を保存できなかったため、比較から外しました。負荷後のDAT照合に使う接続は事前に開き直すよう測定器を修正しています。投稿の再試行は加えていません。通信エラーが残る場合も整合性の失敗と共に測定結果を保存します。初期試行と単独書込み試行には、収集終了後のroot所有ファイルの権限変更でもwrapperが失敗した記録があります。所有権を修正し、採取値とtraceの完全性を別に検証しました。失敗出力は削除していません。

媒体・制御装置・ドライバー・電源管理の最終的な区別、別物理ディスクでの比較、WAN・公開edge経由、本番の回復上限は未検証です。今回の13秒・58秒等は各観測の結果であり、本番の保証値ではありません。
