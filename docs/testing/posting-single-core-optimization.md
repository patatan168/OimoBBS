# 単一コアを含む投稿処理の再検討

2026-10-24。基準は`0dae6db`（製品処理は`3343d89`・稼働イメージ`post-boundary-20261024`）。同じ改善版の2CPU→4CPUで**1.6倍は未達**です。今回は投稿一件のCPU仕事量と絶対性能を減らす変更を検証しました。

[全試行・失敗・検査・元データのSHA-256](posting-single-core-optimization.json)に集計します。生データ、実行コマンド、試作、プロファイルは`var/posting-single-160/`に保持しています。[前回の38試行](posting-pipeline-optimization.md)とは別の実験です。

## 実装

- 厳密なJSON復号では、初期値がゼロの保存DTOに限り、型・必須項目の検査と値の復号を一緒に行います。候補を非公開で構築し、成功後だけ復号先へ反映します。既存値のmerge、特殊タグ、Text復号器などは従来の型検査・標準復号を使います。構文・UTF-8・サイズ・重複キー・大小文字・NUL・surrogate・深さ・整数・配列長の制約は維持します。
- 同じ追記内で完全検証した必須・非必須記録の元byteとsourceを、その呼出しだけで再利用します。正規base64との一致、元byteのSHA-256、sourceを含む署名対象、Ed25519署名は保存前に再検査します。失敗・終了時に共有情報を破棄し、再起動では通常の完全検査を行います。
- 証拠の署名対象を同じ長さ付き列の局所bufferへ組み、SHA-256を一度で計算します。保存byteと署名対象は変わりません。通常追記では読込専用の署名共有mapがないため、そのmapのMutexを取得せず毎回署名を検証します。
- Webフォームでは、正規Cookieに対して同じCSRF値を二度計算していた処理を一度にします。
- 返信可能なスレッドのHTMLは、一回のlevel1 gzipで圧縮します。本文の内容は同じです。通常の強いETagとは`-gzip-live-v1`で分離し、同じLRU・作業枠・容量・取消・公開検査を使います。DAT・停止後のHTML・zstdは従来の圧縮方式です。

proposal→本文WAL→decision→公開・成功応答の耐久境界、署名検証、WAF、本文形式、保存形式、reader条件は変更していません。CPU・メモリ自動調整、GOGC、ホストの設定も変更していません。

## 単一コアと同一仕事量

主な試験は隔離loopbackの実HTTPS、4GiB、送信予算80Mbps、一板16スレッド、8,000投稿です。専ブラ80%・Web20%で、Webはフォーム、CSRF、確認往復、303、遷移先l50のgzip取得まで含みます。CPUはDocker quotaとGoの並列数で、専有物理コアではありません。

1CPUの各3回比較は、基準版32.201・30.896・30.746秒、改善版25.106・32.340・25.037秒でした。中央値は**30.896→25.106秒**で、同じ仕事量の処理量は約23.1%増えました。CPU時間の中央値も約30.80→25.05 CPU秒へ約18.7%減っています。遅い改善版の32.340秒も除いていません。完了時間には共有ストレージの待ちが含まれます。

短いJSONの単一コア比較は従来約7.56µs→約5.15µsでした。一方、非公開候補の分離により、この小さいfixtureの確保は560B・11回から792B・16回へ増えています。確保だけが全経路で減る変更とは扱いません。署名対象の計算は約335.6ns・40B・2回から約193.8ns・0B・0回になりました。

## 2CPU→4CPUの比較条件

従来の80主体固定割当は全結果を残しています。I/O待ちで遅れた要求の集中や、速く処理できた際に投稿元の制限へ達する試行がありました。429を返した試行を「8,000成功の高速化」とは認定しません。

## CPU・Mutex・GCと残る処理

改善版4CPUの8,000成功診断では、CPU標本合計30.07秒のうちJSON復号は約5.08秒でした。独立CPU作業を除いた板所有列の標本は約2.51 CPU秒あり、採番・状態照合・受理枠・保存順序の直列処理が残ります。共有SSDの待ちもあります。 割り当て累計は約6.70GB、確保約3,291万回、GC32回、GC停止合計約6.52msでした。専用GCのCPU時間は約0.641秒、補助GCは約0.081秒で、この診断ではGC停止が大きな待ちではありません。

120主体比較のCPU時間は、2CPUで約23.83〜24.03 CPU秒、4CPUで約28.93〜29.42 CPU秒でした。コアは使っていますが、同じ仕事の総CPU秒も増えます。周波数、cache、スケジューラーのどれが原因かをこの測定だけで断定しません。1.6倍をハードウェア上不可能と判定した結果でもありません。

旧JSON実装へ切り替える`GOEXPERIMENT=nojsonv2`も単体比較しましたが、今回のfixtureでは遅くなり不採用です。ホストのクロック、CPU affinity、他サービス、同期保証を変更して倍率を作る方法は使っていません。
