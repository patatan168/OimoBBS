# 閲覧のCPU・メモリ利用と共有ロックの改善

2026-10-23。基準は `2b4f56e`。変更前もDAT・Web取得は複数コアで動いていましたが、サイト共通mutexとsubject.txtの全板メタデータ作成が並列処理を妨げていました。板参照を共有ロックにし、板別フィードの不要な設定復号・全板一覧作成を省きました。稼働サービスは変更していません。[全試行・診断・コマンド](reading-resource-scaling.json)を保存しています。

## CPUとメモリの使い方

板解決・投稿先参照・公開制限参照を共有ロックで並行実行します。板作成・設定変更・停止は書込みロックで直列化します。公開リース、期限、閲覧制限、ETagと本文、投稿の保存順は維持します。スレッド一覧の確定した要約は引き続き板所有列から取得します。

GoのCPU並列数はcgroupに追従します。HTML・圧縮の生成枠はCPU数とメモリの両方から決めます。この枠はキャッシュ非命中時の生成に適用し、キャッシュ命中の応答はHTTP要求ごとに並行処理します。メモリ余裕が減れば、保持量と新しい生成枠を縮めます。

明示GOMEMLIMITなし・十分な余裕がある場合の上限は次のとおりです。実HTTP試験のruntimeログでもGOMAXPROCS=2/4とsoft limitを照合しました。キャッシュ上限はその観測値から計算される予算で、実保持量とは区別します。

| コンテナ | Go soft limit | キャッシュ上限 | 2CPU / 4CPUの生成枠 |
| --- | ---: | ---: | ---: |
| 512MiB | 384MiB | 48MiB | 2 / 4 |
| 2GiB | 1536MiB | 192MiB | 2 / 4 |

## メモリによる保持効果

CPUを4に固定し、200レス表示の実HTMLで96MiB分の独立した公開版を巡回する部品測定を3回ずつ行いました。メモリ予算は実行時と同じ75% soft limitと8分の1キャッシュから計算します。実cgroup圧迫・TLS・公開許可・ログ・投稿は含みません。

| コンテナ相当の予算 | 保持量 | 再生成/取得 | 時間の中央値 |
| --- | ---: | ---: | ---: |
| 512MiB | 47.87MiB | 1回 | 3.775ms |
| 2GiB | 96.36MiB | 0回 | 61.76ns |

作業集合を保持できる増設では、再生成と割当を省けます。少数の同じスレッドだけを読む場合は、少ないメモリでも既に保持できるため、増設による速度差は小さくなります。表の時間をHTTPの速度向上率へ読み替えません。

## ログ無欠測の予定到着率試験

4CPU・2GiB、各経路1500予定取得/秒を4秒ずつ、合計12秒・18,000要求で比較しました。全要求成功、不一致・OOMは0。準備を含む非必須記録は両版とも20,097件を全件保存し、容量欠測・保存失敗・停止時欠測・終了後の残件は0。日別ファイル量は約8.64MBで容量上限に達していません。

## 診断と検証範囲

診断専用イメージで、準備投稿後の閲覧と背景ログを短時間採取しました。mutexの累積待ちの約64%がwebBoardsを含む経路にあり、全板メタデータ作成の除去を選びました。待ち時間は複数goroutineの合計で、個別応答の遅延ではありません。プロファイルを有効にした結果は容量比較から除外しています。

通常試験はcmd、compat、app、board、parallel、textcodec、webui、toolsとbootstrapの関連経路。板追加との並行読取り・停止、一覧・条件付き取得・隠し板・転載制限・閲覧制限・公開失効・投稿保存を確認しました。関連race、全製品パッケージのvet、負荷生成器の本文破損・検証子不一致・外部URL拒否・非正常終了の検査、Python試験16件を含みます。記録追加後の設計検査も合格し、再実行結果をJSONに保存しました。bootstrap全試験を完走した結果ではありません。

帯域で制約される無圧縮全文は送信量が変わりません。板所有列での一覧要約と非必須ログの署名・保存には直列処理が残ります。実NIC、WAN、ブラウザ・専ブラ実機、長期間の高頻度運用は未検証です。
