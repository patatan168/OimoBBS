# 共有本文WAL復旧の再停止とI/O障害

2026-10-27。`157bb70`から、共有本文WALの復旧で一致済み本文を保持し、全本文のSync・Close成功後に復旧用WALを消すようにしました。[検査・ソース識別・全HTTP試行](recovery-resilience.json)を保存しています。生データと凍結ソースは`var/recovery-resilience-20261027/`にあります。稼働BBSは置き換えていません。

## 変更した復旧条件

旧処理は、復旧を始めるたびに全対象を開始位置へ切り詰め、共有WALの全blockを書き直していました。再停止すると、正しく戻せた本文も毎回やり直します。本文ファイルのClose結果を確認する前に共有WALを削除するため、Close失敗が判明した時点で復旧元がなくなる経路もありました。

現在は、全frameの署名付きproposal/decisionとの対応、全対象の世代・必須prefix・開始位置の検証を終えてから、既存本文と再実行元をbyte比較します。一致する完全blockを保持し、最初の未完了・不一致block以降だけを修復します。途中までのblockは保持しません。作業領域は全対象で再利用する64KiBです。

本文末尾の比較読込みが失敗した場合は、そのblock以降を検証済みWALから再構築します。これは破棄可能な未checkpoint末尾の修復であり、必須prefixの読込・構造検証や署名検証を省く動作ではありません。追加のStatは行わず、所有排他下で必須prefixを検証した時のfile長を使います。

一致済み本文も必ずSyncします。全対象のSyncとCloseが成功してから共有WALを削除し、親ディレクトリを同期します。書込・Sync・Close失敗では復旧元を保持し、descriptorを一度ずつ閉じて、同じ起動経路で再開できます。複数の保存・Close失敗も併記し、一つを隠しません。

通常の投稿保存、proposal→本文→decision→公開の順序、保存形式、署名・未知frame・世代・上限の検査は変更していません。アプリは全復旧を終えるまで公開起動しません。本文を書き直さない場合も、空き容量の問題やSync失敗を無視して起動する保証ではありません。

## 再現と障害注入

補助関数へ分割した旧相当の処理で、次の3件を失敗として再現してから修正しました。

| 条件 | 旧相当 | 修正後 |
| --- | --- | --- |
| 3本文の一致blockが1個・2個・0個 | 全6block・8,982byteを書込み | 未完了3block・4,491byteのみ。各本文のSync・Closeは実施 |
| 全本文が一致し、新しいWriteにENOSPCを返す | 切詰め後の書込で失敗 | 本文のWrite/TruncateなしでSync・Closeを完了 |
| 本文Closeの失敗 | エラー判明時には共有WALが削除済み | 共有WALを保持し、次回の復旧が成功 |

これは実fileへの論理Write byte数の小さい合成例です。物理I/OやHTTP全体の高速化率とは扱いません。

書込先の容量不足相当、短い書込、Truncate/Seek/Sync/CloseのI/O失敗、末尾読込失敗と書込失敗の併発を注入しました。失敗時の共有WALが元byteのまま残り、故障を外した後の公開復旧入口で、3本文すべての採番とDAT byteが一致します。読み込めない末尾だけを検証済みWALから修復する試験も通過しました。保存とCloseの同時失敗を併記すること、全本文Syncの後にCloseし、全Closeの後にだけ共有WALを消すことも検査しています。

実ディレクトリを読み取り専用にしてWAL削除を失敗させ、権限を戻して再開する試験も成功しました。この権限試験は非rootで実行し、skipはありません。実ディスク全体を満杯にする操作は行っていません。ENOSPCとEIOはI/O境界への注入です。

## 復旧中の連続SIGKILL

実ファイルを使う復旧子プロセスを、最初の本文Write直後に毎回SIGKILLしました。6回の再実行で戻せた本文byteは1,497→2,994→4,491→5,988→7,485→8,982と増え、7回目は追加WriteなしでSync・Closeを終えました。同じ位置で止め続けても、先頭blockの書き直しへ戻り続けません。

最初の本文Sync直後と、最初の本文Close直後のSIGKILLも別に検査しています。どちらも共有WALが残り、再開後の全DATが一致しました。これはSIGKILLで同じOSのpage cacheが残る試験です。復旧済みの未同期byteまで電源断後に残ることを示すものではなく、再開時には必ず再照合・同期します。

既存のstore/appの全通常試験、関連するrace、署名付きproposal・複数本文・decisionの実プロセス停止と再送、誤owner・重複key・offset・世代・block・必須prefix・余分な末尾の拒否、bootstrapの投稿停止点・回復・一括投稿、全製品go vetが成功しました。

同じruntime・Go1.27.3、2CPU・512MiB・通常ディスク・fsync有効の隔離コンテナで各版1回です。専ブラ方式の利用者投稿1,000件に成功応答した後でSIGKILLし、同じデータで再起動しました。WAFを有効にし、同一の合成試験用頻度枠を使っています。ホスト設定や稼働BBSは変更していません。

| 版 | 成功応答済み投稿 | SIGKILL終了 | 復旧DAT | ETag | 強制終了→一致確認 | 再起動後のmemory peak |

| 基準 | 1,000 | 137・OOMではない | 1,001行・byte一致 | 一致 | 2.583秒 | 269.0MiB |
| 修正版 | 1,000 | 137・OOMではない | 1,001行・byte一致 | 一致 | 2.617秒 | 280.9MiB |

両版でWAFの保護パス403が維持され、再起動前後のOOM killは0です。復旧後のDAT全文・304・末尾差分・Web gzip・一覧の各200取得、計1,000取得も全件成功しています。memory peakは再起動後の読取り試験までのcgroup値で、旧プロセスのpeakは含みません。

各1回の全体復旧時間に短縮は確認できませんでした。今回の改善は、復旧途中の再停止でのやり直し削減と、保存・Close失敗時の復旧元保持です。通常の復旧速度や512MiBでの大規模アーカイブの容量保証へは読み替えません。HTTP試験は1スレッドの専ブラ投稿で、Webは閲覧を確認した範囲です。個々の復旧境界の障害注入はstore/appの試験で別に検査しています。

停電、実媒体故障、ファイルシステムやcontrollerの異常、長時間・本番負荷、複数板の同時障害は追加未確認です。SIGKILL時の非必須HTTP記録の待機列は保全保証の対象ではなく、本文の必須原本と分けて扱います。
