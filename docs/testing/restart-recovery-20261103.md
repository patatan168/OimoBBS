# 起動と通常更新の停止時間を短縮する

2026-11-03。変更前は`3e5ccda`です。DoS対策の本番切替では、切替開始から公開200の確認まで68.08秒かかりました。BBSの開始時刻と切替観測を照合すると、プロセス開始前に約37秒、開始後の公開確認までに約31秒です。これは退避・復元を含む更新時の時間で、DoS終了後の自然回復時間ではありません。

## 原因と変更

本番と同じ完全バックアップからの診断では、`OpenPostingRepository`に28.79秒、非必須HTTPログを開く段階に約9.46秒かかりました。CPU profileでは署名検証、制御WALの再生、JSONと回線表の検査が主要な処理でした。

非必須HTTPログの通常起動では、WALの独立した新規行の検査が直列でした。`OpenJournalConcurrent`を追加し、この経路へ既存の有界並列検証を適用します。保持するblock数・byte上限を増やさず、CPU数以内で処理します。同一キー・更新・削除は既存の順序検証へ戻し、全workerの終了後に連番・前hash・sourceを照合します。全行の署名・本文・CRCを検査し、保存・Sync・修復条件を維持します。既存の`OpenJournal`は直列の契約を維持し、並行呼出し可能なvalidatorだけを新しい入口へ渡します。

また、今回の本番更新では保存形式が変わらないのに別volumeへ移し、停止中に全データの復元・再退避・再照合を行っていました。通常更新は同じvolumeで再開し、旧イメージと停止後の完全バックアップを保持します。別volumeでの復元リハーサルは停止前に済ませます。保存形式の移行や明示した保存先変更には従来どおり別volumeへの復元・照合を使います。

## 実mTLSによる起動比較

同じ482,539,520bytes・649項目の停止時完全バックアップを毎回復元します。Go1.27.3、CGO無効、同じruntime image、共有ホスト・共有SSDです。CPU・メモリは現在の本番と同じく明示上限なしです。ループバック専用の別port・検証volumeを使い、稼働サイトの保存先には書き込みません。検査・build・別の性能試験は測定に重ねていません。

実CLIの`serve`を起動し、同じmTLS証明書・公開Host・固定した日本のIP fixtureでメニューHTTP200とJSON内容を確認します。既存の閲覧制限・日本限定・逆引き必須・WAF・保守を有効のまま測ります。外部DNS・背景更新とホストの負荷は変動し得るため、遅い試行も保持します。コンテナ起動操作からHTTP200までと、プロセス開始から受付ログまでを分けます。

## 停止中の退避・復元の比較

本番切替時と同じ停止済み原本を読取り専用で使い、退避→検証→新volume復元→復元内容の再検証を3回測ります。全内容・型・モード・UID/GID・リンク先と649項目を照合します。正常更新で不要だった後半の復元・照合は約18秒でした。これを停止中に行わず、同じvolumeで再開する手順を採用します。完全バックアップとその検証は引き続き行います。

原本のtarを退避ファイルと復元先へ同時転送する試作も測りましたが、全検証を維持すると中央値31.78→29.54秒、7.0%の短縮でした。通常更新では復元自体を省けるため、この追加ツールは採用していません。試作品と全失敗・測定結果は`var/testing/recovery-startup-20261103/`に残しています。

各工程の中央値を足して、本番の停止時間が確実に何秒になるとは扱いません。BBSの停止・コンテナ再作成・公開確認も含む全体の時間は、実際の切替観測で別に確認します。

同じ初期バックアップから旧BBSを起動し、公開200を確認した後で、停止・完全退避・切替・次の公開200までを通した1組の隔離比較も行いました。

| 方式 | 停止秒 | 完全退避・検証秒 | 復元・照合秒 | 新コンテナ起動→公開200秒 | 全体秒 |

| 変更前・別volume | 0.15 | 14.44 | 18.42 | 30.97 | 63.97 |
| 候補・同じvolume | 0.65 | 15.48 | 0.00 | 31.28 | 47.41 |

この1組では全体が16.56秒、25.9%短くなりました。両方式とも482,537,984bytes・649項目の停止後完全バックアップを取り、公開メニューの一致・正常終了・再起動ゼロ・OOMなしを確認しています。停止直前までのHTTP記録には試行ごとの時刻が入るため、更新時のバックアップSHAは異なります。候補の新コンテナ起動はこの組では短くなっておらず、全体の短縮は不要な復元をなくした効果です。起動単体3組の中央値による改善と区別します。

## 検証範囲

非必須HTTPログの全署名・本文検査、並列再生と直列再生の内容一致、追記後の再起動、異なる署名鍵の拒否、CRC・個別署名が正しくても壊れた連番・連鎖の拒否を確認します。既存の非必須原本の保全・回収・再開、バックアップと起動検査も回帰検査の対象です。

```sh
  -run 'TestOptional|TestRequired|TestPostingRequired|TestBackupReplay|TestCaseRetirement|TestWAF|TestMemory' -timeout=15m

mise exec -- bash scripts/build.sh
mise exec -- python3 tools/designcheck/check.py
```

測定スクリプト・CPU profile・全ログ・同じ入力の全結果は`var/testing/recovery-startup-20261103/`、集計と各生報告のSHA-256は[全試行JSON](restart-recovery-20261103.json)です。HTTP比較の元データには秘密のバックアップが含まれるため、作業領域は非公開として扱います。本番の攻撃負荷、実投稿、認証後管理操作、電源断・媒体故障はこの隔離比較の対象外です。

上記のevidence・store・CLI全件のrace、関連bootstrapのrace、並列復旧の10回反復と1CPUでの検査、vet、CGO無効build、文書検査が通りました。候補の測定用バイナリと最終buildのSHA-256は一致しています。bootstrap全件・全パッケージのrace、fuzz、依存の再診断は今回の対象外です。
