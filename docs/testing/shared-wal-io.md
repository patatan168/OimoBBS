# 共有本文WALの試作

2026-10-23の初期試作の隔離試験です。**この測定時は既定無効で、稼働環境には反映していません。** 現在の標準有効化・保存形式・運用条件は[後続の実用化検証](shared-wal-practical.md)を参照してください。 全試行の件数・遅延・I/O・メモリ・失敗は[測定記録](shared-wal-io.json)に保存しています。

## 結果

同じ板の16スレッドへ、専ブラ80%・Web20%の実HTTPS投稿を40主体で分散しました。2CPU、SATA SSD上の新規Docker volume、WAFなし、各負荷区間10秒です。ビルド・他の試験とは速度測定を重ねず、前後の実行順を入れ替えています。

| 条件 | 現状版 | 共有WAL版 |
| --- | --- | --- |
| 1GiB・毎秒400投稿を予定したときの時間内完了/秒 | 138.4 / 254.2 | 261.5 / 268.9 |
| 同条件の予定時刻から完了までのp95 | 517.8 / 268.3ms | 262.0 / 256.8ms |
| 同条件の物理書込件数 | 1,247 / 2,158 | 754 / 728 |
| 同条件の時間内に発行できなかった投稿 | 2,575 / 1,418 | 1,313 / 1,260 |
| 512MiB・毎秒200投稿を予定したときの時間内完了/秒 | 187.6 / 187.4 | 190.8 / 198.9 |
| 同条件のHTTP完了失敗 | 117 / 117 | 52 / 5 |
| 同条件の未発行 | 0 / 0 | 30 / 0 |

各欄の二つの数値は別試行です。共有ホストで現状版の結果が大きく変動しているため、一定の改善率や最大処理能力は断定しません。毎秒400投稿の予定は両版とも処理し切れていません。512MiBも安定した毎秒200投稿の条件を満たさず、共有WAL版の一試行では、受理後のWeb遷移に失敗した投稿が1件あります。

最初の共有WAL版はcheckpointを直列に行っていました。1GiB・毎秒200投稿では予定起点p95が現状版161〜221msに対して76〜83msへ短縮しましたが、512MiBでは138.9投稿/秒まで悪化しました。この遅い試行も測定記録へ残し、現在の試作は本文checkpointを有界に並行実行します。

物理書込**件数**と総bytesを区別します。1GiB・毎秒400投稿の最終比較は、現状版約10.2 / 18.3MiBに対し共有WAL版約18.6 / 18.8MiBで、処理できた件数も異なります。1GiB・毎秒200投稿の初期比較では同程度の投稿量で約20.7MiBから約25MiBへ増えました。共有WALへの追加保存により同期の共有と引き換えに総書込量が増える場合があります。

## 保存と復旧

返信バッチは次の順に進めます。公開・成功応答は最後のdecision同期後です。

1. 署名付きproposalを従来の必須journalへ同期する。
2. 本文の既存WAL block、対象キー、世代、追記位置を板の`.posting-group.wal`へまとめて同期する。
3. 個別スレッドWALへ同じblockを書き、非公開状態へ反映する。
4. 署名付きdecisionを同期し、公開する。

共有WALは最大64バッチ・16MiBです。次の保存で上限を超える前に、全参加本文を同期してから共有WALを削除し、親ディレクトリを同期します。個別追記、pack作成、バックアップ捕捉・固定、本文回収、正常終了でも先に同じcheckpointを通します。保存タイマーや、成功応答後にだけ耐久化するキューは使用しません。

異常終了時は公開起動前に全期間の署名検証済みjournalを読みます。共有WALの長さ・CRC・終端、各frameとproposal、既存decisionとの結合、各本文の世代・必須prefix・追記位置を**全対象で検査してから**末尾を再実行します。全本文の同期完了後に共有WALを削除します。世代や署名の不一致は公開を止め、本文を書き換えません。共有本文が同期済みなら、decision保存前に止まった未応答投稿が復旧時に受理される場合があります。

個別WAL・current・packの形式は変更しません。試作を無効にしても、このバイナリは残った共有WALを先に復旧します。

## 検証範囲

- 書込失敗、短い書込、共有同期失敗、本文checkpoint失敗、取消後の停止。
- 全対象の照合前に変更しないこと、所有者・世代・位置・必須prefix・余分な末尾の拒否。
- バックアップ、pack、個別追記、終了時のcheckpointと、64バッチの上限。
- 実子プロセスのSIGKILL後、未同期本文の末尾消失・破損を合成し、署名付き記録と共有WALから復旧すること。
- 隔離サーバーへ実HTTPで応答済み1,000投稿を作り、SIGKILL後のDAT・ETagが完全一致すること。検証完了まで約5.13秒、起動要求から約5.03秒で、5秒以内の復旧を達成した結果ではありません。

全負荷試行で応答済み投稿のDAT欠落・重複なし、旧版prefix一致、回復投稿100/100、OOM killなしを確認しました。実機の電源断、媒体故障、長期稼働、多数板、大規模な既存データ、WAN、閲覧との混合負荷は今回の比較に含みません。

通常のGo全体確認はbootstrapが累積10分の既定上限に達したため、完了済み764件に続く残り95件（fuzz seedを含む）を4分割し、全区分の通過を確認しました。他のパッケージも通過しています。共有WAL有効時の投稿・バックアップ・削除・回収のrace検査、最終保存層のrace検査、解析器の20秒・約49万件のfuzz、`go vet`、文書・fixture検査も通過しています。環境変数で有効にする別の性能試験は、通常のGoテスト一式に含めません。

## 再実行

新規の隔離volumeを作る既存の測定スクリプトを使います。現在のソースでは共有WALが標準有効です。比較用の無効版は`OIMO_DISABLE_SHARED_WAL=1`で作ります。

```sh
docker build -t oimobbs:shared-wal-source .
docker build -t oimobbs:shared-wal-probe -f- . <<'DOCKER'
FROM oimobbs:shared-wal-source
ENV OIMO_DISABLE_SHARED_WAL=0
DOCKER
mise exec -- python3 scripts/probe-thread-resources.py \
  --image oimobbs:shared-wal-probe --cpus 2 --memory 1g \
  --posting-capacity-rate 400 --posting-capacity-seconds 10 \
  --posting-capacity-workers 40 --posting-capacity-threads 16 \
  --output var/shared-wal-capacity.json
```

無効な同じソース版と、変更前の版も別イメージにして比較してください。各出力先は新規ファイルにし、失敗試行も残します。512MiB、正常再起動、SIGKILLは[共通の検証手順](performance.md)の引数を使い分けます。

最初に試した`syncfs`によるファイルシステム全体の同期は、119.7投稿/秒まで悪化する試行があり不採用です。コードは除去し、結果だけ残しています。同期範囲とエラー報告の仕様は[Linux manual](https://man7.org/linux/man-pages/man2/syncfs.2.html)を参照してください。
