# 共有本文WALと投稿準備の実用化検証

2026-10-23に、[共有WALの初期比較](shared-wal-io.md)に続けてCPU診断・保存形式の見直し・隔離HTTP検証を実施しました。集計と生測定のSHA-256は[測定記録](shared-wal-practical.json)へ保存します。実サービスへの反映結果とは区別します。

## CPU診断と変更

変更前の共有WAL版に一時的な診断コードを加え、2CPU・1GiB・16スレッド・40主体・専ブラ80%/Web20%・毎秒400投稿予定で15秒間のCPUプロファイルを採取しました。診断コードは公開HTTP経路を追加せず、専用イメージだけで出力します。通常の比較イメージに診断コードは含みません。

CPU標本21.16秒のうち、`strictjson.Decode`の累積時間は34.12%、板所有列の`runPostingReadyBatch`は48.49%でした。累積時間は入れ子の呼出しを含むため、両者を足し合わせません。割当プロファイルは起動処理も含み、投稿一件あたりの割当量を表すものではありません。診断負荷自体は過負荷でHTTP失敗もあり、処理能力の比較には採用しません。

投稿記録の資格・匿名主体・追加規制を`NewWithProof`で一度に構築します。従来は中間JSONの生成・復号・frame検証を繰り返していました。完全型、Unicode、入力とDATの一致、匿名主体・資格・受理枠の検証は維持します。さらに`ValidateFrameAndMetadata`で得た呼出し専用のmetadataを同じ投稿処理内だけで使い、Token/Override/Cap/HTTP観測成分の再復号を減らします。外部から渡されたcapture検証器、所有列上の認可・受付枠検証は引き続き適用します。

合成入力による構築の単体比較3回では、従来のJSON往復が約494〜507µs・80.6KB・364割当、新しい構築が約237〜241µs・37.9KB・162割当でした。この値をHTTP全体の改善率とは扱いません。

## 保存形式の修正

初期試作の共有WALはJSONでした。書込側が許す大きさと、復旧側の厳密JSON解析の1MiB上限が一致しておらず、大きいバッチを保存できても復旧で拒否される問題がありました。

共有WALを`OIMOGRP2`の有界バイナリ形式へ変更しました。owner・対象数と、各対象のkey・世代・追記位置・block長・既存WAL blockを持ち、全体の長さ・CRC・終端を検査します。既存blockをBase64化せず保持するため、膨張とその符号化・復号も避けます。本文の正規frame、署名付きproposal/decision、個別WAL・current・packの形式は変えません。最大64frame/8MiBの保存候補、共有ファイル最大16MiB/64バッチの制約を維持します。

2MiBのblockの往復、符号化上限、対象数・block長の不整合、完全な破損の拒否、未完了末尾の除外を回帰検査しました。初期試作の`OIMOGRP1`は読み替えません。初期試作を実行したデータを引き継ぐ場合は、その試作バイナリで復旧・正常終了し、`.posting-group.wal`が残っていないことを確認してから更新します。

## 検証範囲

共有WAL有効時のbootstrap親試験859件を8分割して全区分で通過し、他パッケージの全race検査も通過しました。バイナリ形式変更後には保存層・投稿層の回帰/race検査を追加し、共有WAL解析器の20秒・約27万回のfuzz、`go vet`、文書・fixture検査も実施しました。

実子プロセスのSIGKILL、未同期本文末尾の消失・破損を合成した復旧、バックアップ・pack・個別追記・本文回収でのcheckpoint、署名・世代・位置・必須prefix不一致で変更前に止まる条件を維持しています。SIGKILL試験は実機の電源断や媒体故障の実証ではありません。

## HTTP比較と限界

いずれも共有SATA SSD上の新規隔離Docker volume、2CPU、80Mbps、専ブラ80%/Web20%です。速度測定中はビルド・検査・CPUプロファイルを動かしません。無関係な検査と重なった最初の一試行は除外し、生記録と除外理由を残しました。共有ホストのためディスク競合の変動は残ります。

| 条件 | 変更前 | 改善版 |
| --- | --- | --- |
| 1GiB・毎秒200投稿・10秒の成功件数 | 2,000 / 2,000 | 2,000 / 2,000 |
| 同条件の予定起点p95 | 153.2 / 147.4ms | 64.4 / 60.1ms |
| 同条件の物理書込件数 | 3,476 / 3,529 | 2,551 / 2,534 |
| 同条件の物理書込量 | 21.01 / 21.21MiB | 24.75 / 24.77MiB |
| 1GiB・毎秒400投稿・10秒の時間内完了/秒 | 共有WAL初期版263.6 / 243.4 | 295.6 / 290.8 |
| 同条件の未発行 | 1,308 / 1,493 | 1,000 / 1,027 |

各欄の二つの数値は別試行です。毎秒200投稿の比較は従来版とABBA順、毎秒400投稿は前の共有WAL版とABBA順です。400投稿/秒は過負荷で、改善版の一試行では受理後のWeb遷移失敗が1件あります。その投稿の保存はDAT照合で確認しました。総書込量が従来版より増える点と、物理書込件数の削減を区別します。毎秒200投稿を一つのスレッドへ750件ずつ集中させる10秒試験も全2,000件成功、予定起点p95約53.7ms、正常再起動後の全DAT・ETag一致でした。

継続負荷の上限は短時間比較から推定しません。1GiB・毎秒200投稿・60秒は12,000予定に対し10,198成功、764失敗、1,038未発行、予定起点p95約470msでした。正常再起動後の全DAT・ETagは一致しましたが、照合完了まで約48.3秒かかりました。`GOGC=50`でも10,703成功、237失敗、1,060未発行で未達のため、このGC設定は採用していません。2GiBでも10,828成功、2失敗、1,170未発行、p95約485msで、メモリ増量だけで200投稿/秒の継続処理を達成した結果ではありません。

標準有効化した最終イメージの1GiB・毎秒50投稿・60秒では、3,000/3,000成功、HTTP失敗・未発行・欠落・重複なし、時間内完了50.0投稿/秒、予定起点p95約294ms、最大メモリ約480.8MiBでした。全件処理は確認できましたが、250ms以内という測定スクリプトの遅延基準には届かず、`stable_at_tested_rate`はfalseです。混合負荷の通常時の低遅延とは条件を分けます。

1GiB・毎秒100投稿・60秒も6,000予定に対し5,943成功、57失敗、未発行なし、p95約334msで、250ms以内・全件成功の判定は未達でした。512MiB・毎秒200投稿・10秒は7 / 19件のHTTP失敗が残ります。いずれもOOM killなしですが、受付拒否・遷移失敗・未発行を成功扱いにはしません。失敗した負荷条件は実用処理量の根拠にしません。

## 混合負荷と復旧

標準有効化した最終イメージで、WAF、2CPU・1GiB・80Mbps、専ブラ80%/Web20%、毎秒20投稿を使いました。通常閲覧200件/秒を4秒、閲覧2,000件/秒予定を12秒、通常閲覧へ戻す5秒の三段階です。ピーク中は別の一時ファイルへ64KiBの同期を毎秒200回予定し、実際には861回完了しました。これは要求したI/O回数を完全に供給できた試験ではありません。

- 投稿は予定420/420成功、ピーク後の追加200/200成功。未発行・HTTP失敗・応答済み欠落・重複・不正本文・旧版prefix破損なし。
- 通常時は閲覧800/800成功・未発行なし。投稿の予定起点p95は専ブラ約15.5ms、Web約25.0ms。
- 過負荷ピークの閲覧は24,000予定に対し3,170件を発行、20,830件は未発行。発行分のHTTP失敗はなし。**2,000閲覧/秒を処理できた結果ではありません。** ピーク投稿の予定起点p95は専ブラ約1.80秒、Web約4.65秒です。
- 回復区間の最初の1秒は閲覧87件が未発行、予定起点p95約757ms。次の秒から200/200発行・成功へ戻りました。回復区間の投稿p95も専ブラ約636ms、Web約4.53秒で、通常時の低遅延と区別します。
- 先行する応答済み1,000投稿の隔離SIGKILL復旧でDAT・ETag完全一致、WAF設定維持、OOM killなし。SIGKILLから照合まで約5.29秒、起動要求から約5.18秒で、5秒以内は未達です。

## 運用と再現

ソースでは共有本文WALを標準有効にしました。個別同期へ戻す場合は`OIMO_DISABLE_SHARED_WAL=1`で起動します。この設定でも起動前の共有WAL復旧は省略しません。環境変数はプロセス起動時に評価し、稼働中の切替は行いません。標準起動・無効化起動それぞれで投稿し、正常終了後に無効化して開き直した本文・投稿数・再送結果を回帰検査しています。

実サービスへ適用する際は完全データバックアップを保持し、復旧を検証してから対象BBSだけを更新します。今回の作業では稼働中のBBS・edge・データvolumeは交換していません。

再現にはリポジトリのDockerfileでイメージを作り、既存の`probe-thread-resources.py`へ記録内のCPU・メモリ・投稿レート・秒数・分布を渡します。`--posting-capacity-restart`は正常再起動、`--crash-recovery`は通常の1,000投稿経路のSIGKILLです。混合試験は`--peak-mix --io-contention --peak-post-workers 5 --peak-capacity-workers 20 --waf --waf-posting-rate 400 --waf-posting-concurrent 64`を追加します。出力先は試行ごとに新規ファイルにします。

実機電源断、媒体故障、長期稼働、巨大な既存履歴、多数板、WAN・実NICは今回の実証範囲に含みません。既存履歴が増えるとメモリ保持・起動時の署名照合も増えるため、新規サイトの短時間ピークだけで収容件数や復旧時間を保証しません。

## メモリ以外の律速を再診断

後続の[段階別診断記録](posting-bottlenecks.json)では、同じ最終ソースに診断専用のCPUプロファイルと段階別時間計測を一時追加しました。製品ソースには残さず、稼働サービスも変更していません。2CPU・2GiB・16スレッド・40主体・毎秒200投稿を60秒予定しました。

この診断実行は12,000件全件成功、未発行・HTTP失敗なし、予定起点p95約83.9msでした。計測コードが有効で、準備時間も約15.4秒と、以前の通常イメージの約4.2秒から異なります。**性能改善を証明した比較結果や、安定した最大処理能力の認定には使いません。** 以前の遅い区間は今回再現せず、メモリだけでなく実行条件の変動も分離する必要があります。

処理中の35秒分の時間集計は次のとおりです。段階の内訳と全体は重複するため、全行を合計しません。呼出し開始時刻で5秒区間へ分類するため、区間端をまたぐ呼出しも含みます。

| 段階 | 所有列を占有した時間 |
| --- | --- |
| 板の投稿処理全体 | 約34.96秒 / 35秒 |
| うち一括保存全体 | 約17.99秒 |
| proposalの構築・検証・署名・保存 | 約9.11秒 |
| 本文保存 | 約4.44秒 |
| decisionの構築・検証・署名・保存 | 約4.16秒 |
| 公開snapshot交換 | 約0.26秒 |
| 一括保存以外の候補準備・収集・結果確定など | 差分で約16.97秒 |

これはCPU使用時間ではなく、待機も含む所有列の占有時間です。**一つの板の処理列が、準備と保存の完了待ちを含めてほぼ埋まっています。** メモリを増やしても、同じ板を処理する列が増えたり、三つの保存段階を自動的に重ねたりはしません。CPU全体の平均使用量だけで余裕があるとも判断できません。

50秒のCPUプロファイルでは、厳密JSON復号が全CPU標本の約28.6%を占めました。さらに`abuseGuard.prune`は約2.81CPU秒、板所有列の約23.02CPU秒に対して約12.2%です。履歴は最大4,096件ですが、投稿ごとの全履歴走査と公開状態の照合・ロックが残ります。これは追加のソフトウェア側の削減候補です。署名付き記録と本文の保存も同じ所有列の進行を止めるため、CPU準備・検証と耐久化の待ちを分離して評価する必要があります。

測定器も40主体がそれぞれ一要求ずつ送る方式です。待ち時間が伸びると次の予定に追いつけず未発行になります。未発行をHTTP拒否やサーバーの絶対的な処理上限と同一視せず、主体数・受付待ち・実処理・同期I/Oを分けて判断します。現時点では、以前の失敗区間の内訳を測り直せていないため、当時の遅延の主因をCPUかストレージの一方へ断定していません。
