# 文字コード変換の並列化とCPU処理の削減

2026-10-25。UTF-8とsjis-compat-v1のShift_JISの変換を対象にしました。変更前は`0e1c720`です。[全測定と検証記録](textcodec-parallel.json)を保存しています。稼働サービスへの反映は行っていません。

## 削減した処理

エンコードはruneのmap検索とShift_JISのlead/trail算出を、固定配列の直接参照へ置き換えました。デコードも入力byteから出力UTF-8のbyte列を直接引き、文字ごとの除算やUTF-8の再符号化を省きます。追加の固定表は合計257KiBで、従来のエンコード用mapを置き換えます。既存のJIS表は引き続き使います。

ASCIIの連続部分を8byteずつ探して一括コピーします。ASCIIだけの入力は出力のコピーだけで返します。半角カナのエンコードは検証済みUTF-8の3byteからShift_JISの1byteへ直接変換します。デコードの初期容量も調整し、日本語や半角カナの出力拡大に伴う再確保を抑えます。`unsafe`は使っていません。

## 並列化する条件

非ASCIIを含む128KiB以上の入力で、`min(4, GOMAXPROCS, 入力byte数/64KiB)`をworker数の上限とします。呼出元も1区間を担当し、追加workerの空きがなければ直列で処理します。エンコードとデコードを合わせた追加workerは全要求で最大3つです。実行中の大きな文字コード変換も数え、新規の枠確保時にCPU数から差し引きます。枠の待機や処理待ちのqueueは作りません。開始済みworkerは、新しい要求やCPU数変更があっても終了まで処理します。この枠はpackやZstandardのworker枠とは別です。

UTF-8は文字の先頭に分割位置を合わせ、妥当性検査も分担します。別区間の変換不能文字が先に見つかっても、不正UTF-8を優先する従来の条件を維持します。区間ごとの出力が縮む場合は同じ配列内で順に詰め、十進参照でいずれかの区間が拡大した場合は別配列へ結合します。

Shift_JISは直前のlead候補byte列の偶奇から境界を求めます。256byteを超えて遡る必要がある場合は直列に戻します。例えば「日」のShift_JIS byteは両方ともlead候補になるため、長く繰り返す入力はこの経路を通ります。分割した区間でエラーが出た場合も入力全体を直列で走査し、従来と同じエラー種別・byte位置を返します。追加の全入力検査は成功時には行いません。全worker終了後に結果を元の順に結合し、失敗時は部分結果を返しません。

短い投稿・フォーム項目・トリップ用入力は直列の処理削減を使います。大きな一覧やローカルルールなど、既存の`Encode`/`Decode`呼出しには入力長に応じて自動適用します。行ごとに短く分けて呼び出している箇所を、一括変換する変更は含みません。

## 測定条件

AMD Ryzen 5 5500U、Linux amd64、Go1.27.3。1コアは`GOMAXPROCS=1`・CPU 10、4コアは`GOMAXPROCS=4`・異なる物理コアのCPU 4/6/8/10に固定しました。共有ホストで、排他CPU予約やcgroup制限は設けていません。親cgroupまでCPU・メモリの上限がないことを確認しました。性能計測にビルド・検証・プロファイル取得は重ねていません。

同じ合成文字列を変更前→後→後→前の順に別プロセスで測定しました。最終比較は各200msを2回、計4標本の中央値です。入力生成は計時外、返却結果の確保とGCは計時内です。総CPUは全threadのuser+system時間で、1コアでは並列化によらない処理量の削減を確認しました。同時要求は`RunParallel`の処理量を測り、そのns/opを各要求の応答時間とは扱いません。

## 入力長の境界での比較

4コアで、補助workerを無効にした最適化後の直列版と自動並列版を比較します。長さ欄はUTF-8原文の目標長で、パターンの繰返しにより数十byte切り上げています。Shift_JIS入力はこれより短いため、デコードのworker数はエンコードと異なります。原文64KiBとデコードの原文128KiBは両版とも直列です。

| 原文 | 処理 | 経過µs 直列→自動 | 総CPU増減 |
| ---: | --- | ---: | ---: |
| 64KiB | エンコード | 196.2 → 197.8 | +2.0% |
| 64KiB | デコード | 169.1 → 163.1 | -3.7% |
| 128KiB | エンコード | 393.6 → 293.8 | +8.1% |
| 128KiB | デコード | 332.9 → 331.1 | +1.0% |
| 256KiB | エンコード | 779.6 → 355.4 | +5.8% |
| 256KiB | デコード | 681.6 → 522.8 | +19.4% |
| 1024KiB | エンコード | 3,113.1 → 1,224.9 | +3.8% |
| 1024KiB | デコード | 2,561.9 → 1,418.5 | +22.7% |

並列版は分割・起動・結合のCPUを追加します。最適化後の直列版との比較でCPUが増えた結果も上表に残し、変更前からの処理削減と区別します。

両版が同じ直列経路を使う64KiBなどにも小さな差があり、測定の揺れと切り分けていません。

## 割当増加と直列への切替

デコードの並列処理は区間ごとの文字列と最終文字列を確保するため、最適化後の直列版より割当が増えます。十進参照で拡大するエンコードも区間配列の拡張と結合が必要です。これらの入力で変更前より割当が増えた結果も全測定に含めています。B/opは1変換の累積割当で、最大生存ヒープや常駐メモリではありません。

初期の直列試作では半角カナのエンコードが遅くなりました。直接変換を追加した最終版とは分け、初期試作の結果もJSONへ保存しています。ASCIIだけの入力、短い入力、共有枠の飽和時、境界をすぐ求められないShift_JISは直列経路を使います。

## 検証と適用範囲

全1byte・全2byteのShift_JISと、サロゲートを除く全BMP文字のエンコードを、変更前実装と出力・エラー文字列まで照合しました。円記号・上線・マイナスの別名、0x80、半角カナ、私用領域、非BMP文字、十進参照、不正UTF-8の優先順位を含みます。

並列版は1/2/4CPU、大きな日本語・混在文・半角カナ・拡大出力、各分割位置付近の不正byte、末尾の未完文字、曖昧なlead候補列、同時8要求、共有枠の飽和と回収、返却文字列の専有を検査しました。最終版の旧実装照合fuzzは30秒指定・15,753実行、変更に関係する4packageのraceとvet、CGO無効ビルドが成功しました。

製品範囲の`./cmd/... ./internal/... ./tools/...`は、bootstrap以外を最終版で再実行して成功しました。bootstrapは907件を4群の別プロセスに分けて全件成功し、各群の所要時間は約237〜323秒でした。通常の全体実行はbootstrapで合計10分の制限に達しました。最初の分割試行は実行ディレクトリを誤ってfixture不足となり中止し、packageディレクトリから再実行しました。この試行は製品の検証成功に数えていません。試験名・終了コードを含む結果をJSONに保存しています。

実HTTPの性能、ブラウザ、実ディスクの性能、メモリ制限下の負荷、稼働ホストでの性能は今回測っていません。既存の機能試験内のHTTP確認と、実サービスの負荷測定は区別します。
