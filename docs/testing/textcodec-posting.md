## 条件

変更前`0e1c720`、変更後`b78b1bf`。他の製品処理を揃え、同じGo1.27.3・CGO無効・trimpath・同じruntime imageへBBSバイナリだけを差し替えました。AMD Ryzen 5 5500U、共有SATA SSD、各試行に新しい隔離Docker volume、4GiBです。CPUはquotaで、専有物理コアではありません。Goの自動並列数を維持し、1CPU quotaでの診断時もGOMAXPROCSは2でした。

1板16スレッド、120主体のうち専ブラ80・Web40で固定8,000件を専ブラ80%・Web20%へ割り当てます。Webはフォーム・CSRF・確認・303・遷移先l50 gzipまで含みます。予定1600/秒×5秒ですが、遅れた予定も全件試行して完了まで測る方式であり、1600投稿/秒の達成や持続可能上限を表しません。送信予算80Mbps。入力準備・回復100投稿・終了処理は完了処理量の計時外です。

WAFの検査と計算は有効です。隔離試験だけで全体/投稿頻度を100000要求/秒、投稿元を1000要求/秒、投稿同時枠を256へ設定します。通常の全体同時枠128、内側の投稿元POST制限10/秒・burst20は維持しました。稼働設定は変えていません。各CPUで前→後、後→前を交互にし、遅い試行を受けて第4組も追加しました。ビルド・テスト・profile解析と通常計測は重ねていません。

## 大幅に遅くなった試行の原因

2CPUの変更後に約362投稿/秒、4CPUの変更後に約417投稿/秒、追加比較の変更前4CPUにも約485投稿/秒の遅い試行が出ました。CPU時間の増加だけでは説明できず、I/O待ちとCPU稼働率の低下を伴っていました。

通常版と分けた2CPUの診断でも、約585→355投稿/秒の状態を捕捉しました。GOMAXPROCSは両版2、quotaによるCPU抑制増加はなく、GCは両版29回、停止合計は約3.6→3.5msでした。

| Sync対象 | 呼出し回数 前→後 | 呼出し所要時間合計 秒 前→後 | 最長 ms 前→後 |
| --- | ---: | ---: | ---: |
| Writer.commitEncoded | 390 → 391 | 1.418 → 8.536 | 36.4 → 716.6 |
| 共有本文WAL | 159 → 159 | 0.366 → 2.889 | 7.7 → 141.4 |
| 個別本文checkpoint | 48 → 48 | 0.203 → 1.295 | 6.3 → 76.2 |

同期回数はほぼ同じまま、保存同期の所要時間が大きく増えています。これが大幅な悪化の主要因です。Sync計時はスケジューラ待ちも含み、複数writerは並行するため合計をそのままHTTP経過秒へ足しません。共有SSD・カーネルのどの処理が待ちを発生させたかまでは特定していません。Syncの省略・同期順変更・ホストの他サービスの停止は行っていません。

## 文字コード単体ほど投稿が速くならない理由

診断中のEncode最大474byte、Decode最大483byteでした。128KiBからの文字コード並列化はこの負荷では使っていません。Encode/Decodeを含むCPU標本は各診断で1%未満で、JSON検証・符号化、署名検証、圧縮などの比重が大きい結果でした。profileの各分類は累積stackで重なる場合があるため、百分率を単純加算しません。
