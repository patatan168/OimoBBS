# Zstandard復号の計算と割当の削減

2026-10-25。前段の[独立frameの並列展開](zstd-decode-parallel.md)を両版に含めたまま、単一frameの復号器だけを比較しました。**同じCPUコアに固定した測定では、混合入力の総CPUが約6.5%、高エントロピー入力が約5.0%減り、文章はほぼ同じでした。** 追加のliteral作業配列を省き、これら3入力の割当は2回から1回へ減りました。[全試行・不採用候補・検証結果](zstd-decode-efficiency.json)を保存しています。稼働サービスへは未反映です。

後続のHuffmanの深さ定数化は[追加最適化の記録](zstd-decode-tuning.md)を参照してください。この文書の比較には後続の変更を含めていません。

## 採用した変更

Huffman literalを、専有出力配列の未使用末尾へ復号します。各sequenceは、今回のmatch後も未消費literalがすべて収まることを検査してから書き込みます。literalの使用分をコピーした後の出力位置が未消費literalの先頭を越えないため、途中のmatchがこれから読むliteralを壊しません。この条件は従来の出力上限検査も満たすため、余分な比較を追加せずまとめて検査します。入力sliceは変更しません。

4本のHuffman符号列では、先読みwordに含めていないbit数を別に保持します。各symbolで行っていた全体の残り位置の減算を省き、補充時と終端検査時にだけ位置を組み立てます。bitの不足・最終symbol後の余りは従来どおり拒否します。

保存形式、圧縮byte、CRC、対応するframe形式、返却配列の所有権は維持します。workerを追加する変更ではありません。WAL・snapshot・回線分類データ等を含め、共通の`zstddecode.Decode`・`DecodeBounded`を使う箇所に適用されます。

## 1コアの比較

AMD Ryzen 5 5500U、Linux amd64、Go1.27.3。`GOMAXPROCS=1`と`taskset -c 10`で同じCPUへ固定し、入力ごとに別プロセスで実行しました。CPU 10は物理core 5の一方です。排他的なCPU予約ではなく、稼働中のサービスがある共有ホストでの測定です。測定中に別のビルド・検証・性能試験は重ねていません。

変更前→後、後→前の順で各500msを2回、合計4標本の中央値です。返却配列の確保・初期化・GCを含みます。入力は同じ3種類の合成1000レスDATを既存の配信用encoderで圧縮したframeです。rawは固定seedのランダム512KiB、repeatは`abcde`の50万byteです。圧縮処理は計時外です。総CPUは全threadのuser+systemの合計です。

| 入力 | 総CPU µs 変更前→後 | 総CPU増減 | 確保byte 変更前→後 | 割当回数 |
| --- | ---: | ---: | ---: | ---: |
| 文章 | 227.848 → 226.844 | −0.4% | 202,752 → 196,608 | 2 → 1 |
| 混合 | 365.316 → 341.432 | −6.5% | 232,064 → 204,800 | 2 → 1 |
| 高エントロピー | 1,106.110 → 1,051.124 | −5.0% | 548,864 → 442,368 | 2 → 1 |
| raw | 63.610 → 63.954 | ＋0.5% | 524,288 → 524,288 | 1 → 1 |
| repeat | 58.132 → 58.430 | ＋0.5% | 507,904 → 507,904 | 1 → 1 |

文章の速度向上はほぼ確認できません。raw・repeatにも改善は確認できません。約0.5%の増減を測定の揺れと切り分けていません。高エントロピー入力の確保量は約19.4%、混合は約11.7%、文章は約3.0%減っています。

## CPUを固定しない測定とpack

`GOMAXPROCS=1/4`だけを固定した測定も、別プロセスで変更前→後、後→前、各300msを3回、計6標本取得しています。1コアの通常ループでは文章の総CPUが約4.3%増え、混合は約1.1%、高エントロピーは約5.3%減りました。同じ1コアの並行benchmarkでは文章約0.4%、混合約4.4%、高エントロピー約6.2%の削減でした。これらの差があるため、上表では入力ごとにプロセスとCPUを揃えた値を主な比較にしています。

4コア同時展開の総CPUは、最終試行では文章約1.6%、混合約9.9%減った一方、高エントロピーは約5.4%増えました。前の試行では高エントロピーも減っており、共有ホストの揺れと実装差を十分に分離できていません。**全入力・全並列度で総CPUが減るとは扱いません。**

同じ保存Level 6の8frameを両CRC込みで展開した測定では、1コアの逐次処理は混合約2.2%、高エントロピー約5.9%の総CPU削減、文章は約1.6%増でした。pack全復元とDAT全文読取りは、1コアで約0.3〜0.9%、4コアで約1.7〜5.0%の総CPU増でした。JSON・投稿・索引等の検証を含む繰返しの多い129レス入力で、経路全体の速度向上は確認できていません。各250msを2回の前後往復、合計4標本です。

## 検査と不採用候補

出力末尾のliteralと確定済みprefixの非重複、空きが0〜2byte足りないmatchの拒否と3byteある場合の受理、境界guard、literalだけのblockの重複copyを追加検査しています。既存の独立decoderとの照合・全保存profile・最大展開長・破損・入力との非共有・Huffman参照比較も使いました。

store・app・evidence・disclosure・zstd圧縮/展開の通常試験、bootstrapの`TestNetwork`群、store・zstd圧縮/展開のraceとvet、全製品のCGO無効ビルド、設計検査が成功しました。fuzzは復号4,439実行、保存profileの往復317実行で、各30秒指定の試行が成功しました。実行結果は全記録JSONの`validation`に記録しています。

CPUプロファイルではHuffman、sequence実行、履歴copy、メモリの初期化が主な対象でした。長さ計算の表引き化、FSEの追加先読み、短いmatchの専用copy、可変Huffman処理単位、長さ計算の短い経路、copy元sliceの単純化も比較しました。文章・混合の悪化や全体の改善不足があり、不採用としました。試行を全記録JSONに保持しています。

実HTTP・ブラウザ・実ディスク・メモリ制限・継続負荷・稼働ホストの性能は今回測定していません。削減量をそのまま投稿性能や復旧時間へ換算しません。

再実行例です。`taskset`のCPU番号は実行環境に合わせます。

```sh
GOMAXPROCS=1 taskset -c 10 mise exec -- go test ./internal/zstddecode -run '^$' -bench '^BenchmarkDecode$/mixed$' -benchtime=500ms -count=2
GOMAXPROCS=4 mise exec -- go test ./internal/zstddecode -run '^$' -bench '^BenchmarkDecodeParallel$' -benchtime=300ms -count=3
GOMAXPROCS=4 mise exec -- go test -race ./internal/zstddecode ./internal/zstdencode ./internal/store
```
