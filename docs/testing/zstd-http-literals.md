# HTTPのliteralヘッダーと分割情報の削減

2026-10-31。比較元は前回の改善版`5d18ad8`です。**取得済みの圧縮対象16本文すべてが小さくなり、圧縮時間の中央値も約2〜9%短縮しました。** 今回の追加削減は最大約3.9%で、効果は主に小さい本文です。大きいHTMLの追加削減は1byteでした。[全標本と入力hash](zstd-http-literals.json)を保存しています。稼働環境には反映していません。

## 変更

配信用のliteralでは、本文長に合う1〜3byteのrawヘッダーと、3〜5byteのHuffmanヘッダーを選びます。Huffmanのliteralが1,024byte未満なら単一streamを使い、6byteの分割表と終端の余分な詰め物を省きます。形式は[RFC 8878のliteralヘッダー](https://www.rfc-editor.org/rfc/rfc8878.html#section-3.1.1.3.1.1)に従います。Huffmanを試す128byteの下限は維持しています。

追加処理を補うため、32KiB以下のHTTP本文では採用したFSE表を保持して再構築を省きます。bit数の比較中は出力bit値を計算せず、既知の最良値を超えた候補の計算を打ち切ります。Huffman符号の割当ても幅ごとの開始値を先に求め、一度の記号走査で行います。

保存には従来のliteral形式と表精度の選択経路を使います。4種類の保存プロファイル×17本文の68出力を前回版と比較し、byte完全一致を確認しました。保存形式のreader要件は変更していません。復号器は配信用の短い形式にも対応し、長さ・出力上限・stream終端を検査します。配信の強いETagは`-zstd-v10`へ更新しました。

## 検証と再実行

17本文を独立Go復号器とlibzstdで展開し、元byteとの一致を確認しました。1/2/3byteのrawヘッダー、1/4stream、1,024・4,096・16,384byte前後、切り詰め、採用した符号表の所有権を検査しています。実TLSの試験で旧v9条件からの200、新v10の304、無圧縮DAT差分206も確認しました。

fuzzで28byteの特殊入力に対するGo標準復号器の先読み条件も見つかりました。同じ入力は前回版でもGoでは失敗し、libzstdでは正しく展開できます。LL・offsetが単一値で末尾ML表だけが動的な場合に、符号列が1byteだとGoの16bit先読みを満たせないことを確認しました。この場合だけMLの精度を8へ上げ、最低2byteの符号列を作ります。最小入力は`internal/zstdencode/testdata/fuzz/FuzzIndependentFrames/9150d5b35ea8c8db`へ回帰例として残しました。今回測定した17本文と保存68出力のサイズ・byteには影響しません。
