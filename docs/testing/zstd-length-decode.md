# Zstandard復号の長さ計算

2026-10-31。前回版`9f49679`から、literal長と参照長の計算を分離しました。同じframeの1コア比較では、**トップHTML・スレッドHTML・DAT・CSSの復号時間が約2〜5%短縮**しました。JSは約0.5%増え、大きい保存frameの改善は安定していません。[全標本・不採用案・入力hash](zstd-length-decode.json)を記録しています。稼働環境には反映していません。

## 変更

従来は列ごとに同じ関数を2回呼び、引数でliteral用か参照用かを分岐していました。計算をそれぞれの関数へ分離し、種別の分岐を除きました。Go1.27.3ではliteral用計算が呼出元へインライン展開され、各列の関数呼出しも1回減ります。参照長の関数はインライン展開されません。

計算式とcodeの許容範囲は同じです。表の読取りでliteralのcodeを0〜35、参照のcodeを0〜52へ制限し、展開先・履歴offset・残りbit等の検査を継続します。全89codeの基準長と追加bit数を、[RFC 8878の表16・17](https://www.rfc-editor.org/rfc/rfc8878.html#section-3.1.1.3.2.1.1)の固定値で照合します。

圧縮器・frame形式・圧縮済みbyte・返却配列の所有権を変えず、workerとキャッシュも追加していません。測定した全入力で返却配列のヒープ割当1回と確保byte数を維持しています。

## 前回版との比較

Go1.27.3、AMD Ryzen 5 5500U、`GOMAXPROCS=1`、`taskset -c 10`です。CPUを排他的には予約しておらず、共有ホストでの変動があります。測定中に自分の別ビルド・試験は重ねていません。

公開URLから前回取得した本文の固定frameと、保存Level 6と同じ精度8のframeを使用しました。新旧に同じ圧縮byteを渡し、毎回新しい出力へ復号します。圧縮・ファイル読取り・独立復号確認は計時外、返却配列の確保とGCは計時内です。総CPUはプロセス全threadのuser+system時間です。

入力ごとに前→後→後→前の順で、各500msを2回、各版4標本の中央値を比較しました。比較バイナリは前回コミットの復号器と今回の復号器で、同じbenchmarkを使っています。

| --- | ---: | ---: | ---: |
| トップHTML | 16.247→15.897 | -2.2% | 16.244→15.894 |
| スレッドHTML | 38.095→36.216 | -4.9% | 38.087→36.206 |
| DAT全文 | 14.182→13.945 | -1.7% | 14.181→13.942 |
| 共通CSS | 28.883→27.536 | -4.7% | 28.875→27.532 |
| 共通JS | 4.853→4.875 | +0.5% | 4.851→4.873 |
| 保存・文章 | 210.026→227.624 | +8.4% | 209.986→227.581 |
| 保存・混合 | 335.273→323.312 | -3.6% | 335.192→323.238 |
| 保存・高エントロピー | 971.795→987.169 | +1.6% | 971.616→986.922 |
| raw frame | 68.576→66.299 | -3.3% | 68.562→66.281 |
| repeat frame | 47.181→47.816 | +1.3% | 47.168→47.806 |

表のCPU値を含む未丸め値と全標本はJSONにあります。保存・文章の増加を確認するため、同じバイナリを各1秒・4標本で再測定したところ210.360→202.638µs、約3.7%短縮へ反転しました。初回の短い探索では保存frameも短縮しましたが、再現性が不足しています。変更対象外のrawにも約3.3%の変動があり、大きいframeの高速化を断定しません。全入力で速くなる保証はありません。

この数値はサーバー内の復号単体です。ブラウザー側の展開速度、通信時間、実HTTPの応答速度、投稿・pack全体の処理量は測っていません。

## 不採用案と検証

FSE表のcellを32bit整数へまとめる案、参照列のbit読取りをキャッシュする案は遅くなり、不採用です。短いcodeだけ分岐し長いcodeを従来関数へ送る案も、大きいframeで遅くなったため戻しました。全標本と試作ソースは`var/zstd-decode-second-20261031/`に残しています。

取得本文17件、配信用3件、保存用3件、raw・repeatの計25frameについて、元本文・独立Go復号器・libzstdとの一致と圧縮入力の非破壊を確認しました。通常試験とraceはzstddecode・zstdencode・compat・storeを通過しました。破損frameを含む復号と保存profile往復のfuzzを各20秒指定で実行し、それぞれ6,142件・359件を通過しています。

bootstrapの回線圧縮キャッシュ・診断の関連試験、全製品・ツールのvet、CGO無効ビルドも成功しました。全bootstrap試験、変更後の公開URL、実HTTP負荷、実機は検証対象に含めていません。

```sh
OIMO_ZSTD_DECODE_CORPUS="$PWD/var/zstd-decode-20261031/corpus" \
  GOMAXPROCS=1 taskset -c 10 mise exec -- go test ./internal/zstddecode \
  -run '^$' -bench '^(BenchmarkHTTPDecodeCorpus|BenchmarkArchiveDecode)$' \
  -benchtime=500ms -count=4
```

CPU番号は実行環境に合わせます。元の取得本文とframeは`var/zstd-decode-20261031/corpus/`、今回の生標本・計測スクリプト・新旧バイナリは`var/zstd-decode-second-20261031/`に保存しています。前段の変更は[小さいframeの復号](zstd-small-frame-decode.md)を参照してください。
