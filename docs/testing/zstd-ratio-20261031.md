# Zstandardの一致探索と保存RLEの圧縮改善

2026-10-31。比較元は`325193a`。**同じ25本文のHTTP用圧縮後合計は30,411→30,310byte、0.33%減でした。最大の追加削減は1.48%です。** 保存の通常25本文は圧縮byteを維持し、一様なblockだけRLEへ縮めます。[入力hash・全標本・資源・検証結果](zstd-ratio-20261031.json)を保存しています。通信時間・稼働環境のディスク使用量・HTTP全体のCPUの測定ではありません。

## 変更

- 512byte〜32KiBのHTTP本文では、3byte一致の候補を直近2個まで保持します。最新候補が短い場合にも、その前の長い一致を比較できます。追加探索表は圧縮器あたり32KiBで、対象外の入力では初期化・探索しません。
- HTTPの非repeat一致は、従来の4〜31byteに加え32〜127byteでも1byte先を確認します。より長い一致があれば、literalを1byte待って符号化します。保存用の探索順序は維持します。
- 保存でも一様なblockは[RFC 8878のRLE block](https://www.rfc-editor.org/rfc/rfc8878.html#section-3.1.1.2.2)を使い、payloadを1byteにします。raw/RLEではrepeat履歴を進めません。保存literalの3byte/5byteヘッダーと4streamは維持します。
- 復号器・保存reader要件・圧縮worker数・8MiBの作業予約は変更していません。HTTPの強いETagは`-zstd-v13`へ更新し、静的資産のzstd本文も再生成します。

## 同じ入力での条件

Go1.27.3、AMD Ryzen 5 5500U、`GOMAXPROCS=2`、`taskset -c 10,11`。取得済み17本文と、現在の縮小済み管理CSS/JS等8本文を合わせた25本文です。同じ固定入力と再利用encoderで、毎回の圧縮・専有出力の確保・GCを計時します。圧縮済みキャッシュ、入力読取り、復号確認、初期準備は計時外です。

前→後→後→前の順で各200msを2回、各版4標本の中央値を比較しました。総CPUは全threadのuser+systemです。RSSは`wait4`で得た各benchmarkプロセスの最大値で、各版2プロセスの中央値です。測定中に自分の他のビルドや検証を重ねていません。稼働サービスがある共有ホストで、CPUを排他的には確保していません。

82byteのsubject.txtも参考として強制圧縮していますが、通常のHTTPでは圧縮しません。gzip9も同じbyteから生成してサイズを記録しましたが、gzipの速度比較はしていません。

31配信対照入力と3保存入力の標本では、総CPU差は約-10.2〜+11.7%でした。キャッシュ非命中の圧縮1回の比較で、BBS全体のCPU差や全入力に対する上限ではありません。

通常の25本文をlevel 1/6/9で圧縮した75出力は、比較元とbyte完全一致でした。実際の`EncodePackChunk`を通した大きい合成DATも、サイズは同じです。

一様な入力などの制御例では、次の結果になりました。全ゼロはRLE確認のための人工入力で、実ログ全体に同じ削減率が出る結果ではありません。

| 制御入力・level 9 | 保存byte 前→後 |
| --- | ---: |
| 500,000byteの全ゼロ | 66 → 25 |
| 500,000byteの5byte周期 | 72 → 72 |
| 圧縮→一様な128KiB→圧縮 | 20,090 → 20,079 |

`v1.0.3`（`fc0c585`）の製品decoderを別packageへ隔離して実行し、新旧の保存168frameを展開できることを確認しました。新旧の通常25本文と3制御入力、4profileの計224出力は、独立Go復号器・製品復号器・libzstdで元byteと一致し、encoderによる入力変更も検査しています。既存pack fixtureは更新せず、従来の読出し・再圧縮byte一致の検査も通します。

プロセス最大RSSの中央値は、配信対照が13.76→13.76MiB、保存対照が16.03→16.08MiBでした。fixture・Go runtime・GCを含む値で、稼働BBSの増分の保証ではありません。探索表は1処理枠あたり32KiB増えます。

## 不採用試行と範囲

単純な全位置探索、長いprefix候補の追加、大きいhash表、Huffman長、repeat優先度、保存への先読みも比較しました。サイズが増える、削減が小さい、資源に見合わない候補は外しました。途中のソース・frame・比較バイナリと生標本は`var/measurements/zstd-ratio-20261031-223316/`に残しています。

保存用にも短いliteralヘッダーを使う試作では、通常25本文の合計が約0.5%小さくなりました。しかし旧版製品decoderはこの形式を読めません。保存の互換性とreader要件を保つため、この変更は採用せず、固定幅ヘッダーを維持しました。旧版が受け付けるRLE blockだけを保存にも適用しています。未配備の試作イメージ・計画には`SUPERSEDED.txt`を付け、稼働環境には適用していません。

圧縮・復号・compat・保存・webui・生成器の通常/race、HTTP TLS・回線キャッシュ、CLI/公開入口の通常試験が成功しました。圧縮の独立復号・保存profile往復・破損frame復号のfuzzは各20秒指定で、それぞれ3,832・924・6,445件を通過しました。vet、CGO無効ビルド、生成物と文書も検査しています。全bootstrap試験、実機、WAN、稼働環境のピーク負荷・512MiB負荷は今回の範囲に含めません。稼働反映は別の配備記録で扱います。
