## 変更と費用の上限

512byte未満の配信本文では追加の3byte候補表を使いません。この場合、literalの推定平均費用が4.5bit以上なら、既存の候補表のprefixを5byteから4byteへ縮めます。5byte目が異なる4byte一致も拾い、候補表の個数・初期化量・探索回数を増やしません。低い平均費用の本文、512byte以上の本文、保存用のprefix方針は維持します。

32KiB以下のHTTP用FSE表は、構築前に正確な費用の下限を求めます。精度をL、記号への正規化状態数をnとすると、遷移幅は最低でも`L - ceil(log2(n))`です。表ヘッダーと初期状態のbit数に、各記号の出現回数×最小遷移幅を足します。最後の記号は初期状態から読むため、遷移回数から1回引きます。追加bitは全候補に共通なので、従来と同じく比較費用へ入れません。

この下限が最良候補以上なら、その表の状態配置・逆引き表・実遷移の計算を省きます。精度5〜9（offsetは8まで）の候補範囲と同値時の優先順を維持し、勝てる可能性がある表は従来通り実bit数で比較します。全候補を完全構築する参照選択と、読み出す全要素・header・状態・逆引き表の一致を検査します。

一つの参照がblock全体を覆い、先頭literalが0〜1byte・参照周期が8byte以下の場合は、最大9byteの確認で同じbyteだけのblockを判定します。HTTPではこの場合、[標準のRLE block](https://www.rfc-editor.org/rfc/rfc8878.html#section-3.1.1.2.2)を使い、payloadを1byteにします。blockの長さ欄は展開長です。raw/RLEでは[repeat履歴を進めず](https://www.rfc-editor.org/rfc/rfc8878.html#section-3.1.1.5)、後続の圧縮blockにも元の履歴を使います。保存用には適用しません。

さらに、block末尾まで一致するrepeatを見つけた場合、同じ範囲を別候補として読み直す処理を省きます。残る候補は一致長を上回れず、同じ長さならrepeatを優先するため、採用する参照は変わりません。短いrepeatの後ろに長い候補がある場合は、従来通り比較します。

worker・新しい候補表・圧縮結果のキャッシュ・依存ライブラリは追加していません。HTTPの強いETagを`-zstd-v12`へ更新しました。保存用の264出力は比較元とbyte完全一致です。
